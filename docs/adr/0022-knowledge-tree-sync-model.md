# 0022. Knowledge-tree sync model: config-only monorepo + separate per-store repos

- **Status:** Accepted
- **Date:** 2026-07-27
- **Scope:** Workspace-wide (trusty-agents multi-machine sync, trusty-tools monorepo policy)
- **Reversibility Cost:** Low — the decision defers knowledge-tree sync to a follow-up; implementations of config-only (Phase 1–4 of DOC-56) are unaffected and remain shippable
- **Decision Drivers:** Knowledge tree growth profile (unbounded, per DOC-55 extractors/connectors), storage coupling (config vs. corpus have opposite constraints), merge semantics (append-only ledgers produce multi-machine conflicts), data sensitivity (distinct content classes require distinct repos), independent lifecycle (knowledge trees are regenerable by ingest; configs are hand-curated)
- **Closes DOC-56 §5.3:** Open question left for owner sign-off

## Context

DOC-56 (Agents Monorepo Sync Spec) defines a private repository (`bobmatnyc/trusty-agents-agents`) to sync agent configuration across machines. Section 5.3 leaves one decision open: **do OKG knowledge trees sync alongside configuration, or separately?**

This is not a rhetorical question. Both options are specified with measured sizes and growth profiles. The decision determines:

1. **Repo growth and clone latency.** Today:
   - All agent config: **516 KB** on disk, 34 tracked files, whole repo ~260 KiB packed
   - `bob-kb` distilled tree (measured knowledge corpus for one agent): **2.7 MB**
   - Raw sources: 3.1 MB (already excluded from sync)

2. **Conflict semantics.** DOC-55 (Universal OKG Importer §2.2) establishes idempotency invariants on which multi-machine sync depends. Knowledge trees use append-only ledgers (`_sources/<id>.jsonl`) per §4.3 of DOC-55, which create a conflict class (concurrent multi-machine ingest appends) not present in config sync.

3. **Content sensitivity boundary.** Knowledge trees contain business and personal content (the cto-assistant tree is Duetto material; izzie's tree is the owner's personal profile). Agent config is comparatively shareable and lighter on PII. Mixing content classes in one repo forces the strictest access rule onto everything.

4. **Independent lifecycle.** Configuration is hand-curated, persistent state (edited by the user, version-controlled as undo stack). Knowledge trees are derived state (generated by ingest, regenerable by re-running ingestion). They have opposite update patterns and opposite conflict resolutions.

### Known measurements (DOC-56 §5.3)

**Option A — Config only:**
- Monorepo holds `agents/<agent>/` plus platform config (`config.toml`, `user.toml`, `skills/index.json`)
- Knowledge trees stay out; a new machine re-ingests from registered sources
- Repo stays ~0.5 MB, clones instantly
- Growth bounded by agent count
- No merge conflicts for machine-generated markdown

**Option B — Config plus distilled knowledge trees:**
- Adds `knowledge/<tree>/` (entities + `_sources/registry.toml` + `_sources/*.jsonl`)
- A clone is immediately complete; distilled entities (costly to generate) are preserved
- Knowledge-tree sync spans two repos plus manual management; sync story fragments
- Ledger conflicts on multi-machine concurrent ingest (no merge strategy yet)

### The binding code establishes knowledge-tree identity

The actual resolution of `okg://<agent>` to filesystem location is in `crates/trusty-agents/src/stores/binding.rs:52–62`:

```rust
pub fn okg_tree_path(knowledge_dir: &Path, tree_uri: &str) -> Option<PathBuf> {
    let tail = tree_uri.strip_prefix(OKG_SCHEME)?.trim();
    if tail.is_empty() {
        return None;
    }
    let slug = slugify(tail);
    if slug.is_empty() {
        return None;
    }
    Some(knowledge_dir.join(slug))
}
```

(Lines 52–62; `knowledge_dir` defaults to `$KB_KNOWLEDGE_DIR` or `~/.trusty-agents/knowledge`.)

This establishes that every knowledge tree has a stable identity: `knowledge_dir / slugify(agent_name)`. That identity is unambiguous and machine-independent. A separate per-store repo would retain this identity and reuse the same sync machinery.

### DOC-55 growth argument

DOC-55 (Universal OKG Importer §4) introduces extractors for `.docx`, `.xlsx`, `.pdf`, and `pptx`, plus connectors for any system reachable via authenticated APIs. The spec is explicit (§4.2):

> "DOC-55 (the universal importer) is explicitly designed to make this [knowledge tree size] grow fast — every new extractor and connector multiplies corpus volume…. `xlsx`/`pdf` extraction produces large text bodies. Ledgers only ever append."

This is not a bug or oversight; it is the spec's design. Knowledge trees are *intended* to grow, and they grow unbounded by agent count. The monorepo's size is therefore unbounded if Option B is chosen, forever coupling config clones to the corpus's growth.

## Decision

**The monorepo holds configuration only. Knowledge trees sync in separate per-store repositories.**

Concretely:

1. **`bobmatnyc/trusty-agents-agents` (monorepo) contains:**
   - `agents/<agent>/agent.toml` — manifest
   - `agents/<agent>/persona.md` — instructions
   - `agents/<agent>/events/*.md` — per-connector event instructions
   - `agents/<agent>/attachments/**` — small reference material (subject to size gates per DOC-56 §5.2)
   - `config.toml`, `user.toml`, `skills/index.json` — platform config (secrets excluded per DOC-56 §5.1)
   - `.provisioning/bundle-stamp` — the merge-base marker (DOC-56 §6)

2. **Knowledge trees sync via separate per-store repositories (e.g., `bobmatnyc/trusty-kb-<tree>`):**
   - Each store binding (`[[stores]]` in `agent.toml`) may declare an optional `sync_remote` field naming a git remote for the tree
   - Sync machinery is identical to the monorepo (secret gate, three-way merge templates branch if ledger conflicts arise, auto-commit on ingest, debounced auto-sync)
   - A tree's repo is opt-in per store; stores may omit the field and ingest-only to local disk

3. **The `[[stores]]` binding already provides identity.** From DOC-56 §3.1 and the code, each store has a `name`, `tree` (the OKG URI), and `index`. Adding an optional `sync_remote` field is a natural extension of that binding, not a new concept.

4. **A new machine's bootstrap (DOC-56 §7.4) reports missing data:**
   - Configuration and platform files are restored from the monorepo (all required)
   - Knowledge trees are noted as missing if their store has a `sync_remote` declared; the bootstrap report surfaces them so the user can pull them explicitly or re-ingest

## Consequences

### Easier / Positive

- **Repo sizes remain proportional to config footprint.** The monorepo stays ~0.5 MB and clones instantly, no matter how many knowledge trees exist or how large they grow. A user with 10 agents and 3 trees does not pay the corpus cost for any tree they are not actively syncing.

- **No bind between config and knowledge lifespans.** Configuration versioning is human-driven; knowledge-tree versioning is ingest-driven. Separating the repos means a knowledge tree can be rebuilt or reset independently of configuration history, without polluting the config repo's git log.

- **Distinct access policies per store.** A sensitive knowledge tree (e.g., cto-assistant's Duetto material) can live in a private repo shared only with relevant team members, while configuration (even with secrets excluded) can be shared more broadly. Content classes have distinct sharing models; separate repos honor that.

- **No merge conflicts for machine-generated ledgers.** The append-only ledger (`_sources/<id>.jsonl`) never conflicts if it is in its own repo. Multi-machine concurrent ingest appends the same entries to the same file (via the existing `Ledger::is_current` idempotency gate); git's union merge resolves it correctly because both machines added the same lines.

- **Ingest-driven regeneration remains the escape hatch.** If a knowledge tree's repo is lost or corrupted, re-running the ingest pipeline from the registered sources recreates it. The tree is reproducible; the choice to sync it is optional.

### Harder / Negative / Trade-offs

- **Multiple repos to provision per agent with per-store sync.**
  - A user with one agent bound to one tree syncs one monorepo. A user with one agent bound to three trees (e.g., for Duetto, personal, and public knowledge) provisions three separate repos.
  - **Mitigation:** The `tagent sync` CLI abstracts this. The user runs `tagent sync init --remote <monorepo-url>` once, then `tagent sync pull`/`push` pulls/pushes both the monorepo and all declared per-store repos in one command. No user-facing fragmentation.

- **No single clone that reproduces an agent end-to-end.** A git clone of the monorepo yields configuration and platform files but not knowledge. A restore requires:
  1. Clone the monorepo
  2. For each agent with a `sync_remote`, clone its knowledge repo(s) into `knowledge_dir/<tree_slug>`
  3. Run `tagent sync` to merge and start

  **Mitigation:** The bootstrap report (DOC-56 §7.4) surfaces the missing tree repos. A scripted restore is a 3-liner. A future convenience layer (e.g., a `tagent bootstrap --full` that fetches all declared remotes) is trivial to add.

- **Sync story now spans two mechanisms.**
  - Config syncs via the monorepo; trees sync via per-store repos.
  - Both use the same underlying git-merge machinery, same secret gate, same debounced auto-sync.
  - **Mitigation:** The `tagent sync` command is the single user-visible API; it orchestrates both repos transparently. The split is an implementation detail. If a simpler unified mechanism is desired later, all trees can be re-consolidated into the monorepo by mirroring per-store repos back into `knowledge/<tree>/` (reversing this decision), without breaking the configuration parts.

- **Requires explicit follow-up for ledger-merge semantics (if ever used).**
  - If a per-store knowledge repo ever gets `templates` branch merge semantics (to handle conflicting re-ingests), the ledger union-merge strategy must be verified against `Ledger::watermark()` (DOC-56 §5.3 sub-question).
  - This is not a blocker for shipping config-only sync (Phases 1–4 of DOC-56); it is deferred to Phase 5 if Option B is ever chosen later.

No prior decisions contradict this choice. The decision extends ADR-0008's identity principle and is consistent with all existing workspace-wide ADRs. Summary: consistent with prior decisions; no silent contradictions.

## Notes

**Implementation sequence:** This decision does not block DOC-56's Phases 1–4 (config-only sync to the monorepo). Those phases are fully specified and shippable without knowledge-tree sync. Phase 5 (knowledge trees, if Option B is chosen) is deferred; this ADR closes the question so Phase 1–4 can proceed with architectural clarity.

**Future reversal:** If Option B is preferred later, the decision is revisable: knowledge trees can be consolidated into the monorepo by mirroring per-store repos into `knowledge/<tree>/`, and the sync story can unify. This ADR is not a permanent lock; it is a decision made on available evidence, revisable if evidence changes (e.g., if append-only ledger merge conflicts prove manageable, or if UX simplification of a single repo outweighs size concerns).
