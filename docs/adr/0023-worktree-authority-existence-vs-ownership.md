# 0023. Worktree authority split: git decides existence, a rebuildable index decides ownership

- **Status:** Accepted
- **Date:** 2026-07-28
- **Scope:** crate `trusty-mpm` (worktree provisioning, `SessionManager`, orphan-GC / reclamation tooling; operationalized under epic #4207)
- **Reversibility Cost:** Medium — the split is additive over ADR-0020's existing sentinel/registry mechanism (no data migration), but every reclamation code path and dashboard built against it would need rework if the authority assignment were reversed.
- **Decision Drivers:** git's data model has no concept of "who ran `git worktree add`"; two independent registries have already diverged in production with data-loss consequences; a 201-candidate measurement shows branch naming cannot serve as an ownership boundary today; the 1.3.0 one-worktree-per-writer model (epic #4207) needs an explicit, non-negotiable existence/ownership boundary before its provisioning and reclamation code is rewritten.
- **Supersedes / Superseded by:** Amends **ADR-0020** (`0020` status updated to `Amended by 0023`; ADR-0020's Context/Decision/Consequences are left as originally accepted per the ADR immutability rule — DOC-46 §4 — this ADR is the record of the refinement, not an edit to that history).
- **Topology note (2026-08-05):** The `.base` bare-clone worktree store referenced below (Context, and the 2026-07-21 incident in Consequences) is retired by owner ruling; worktrees now provision exclusively under `./.worktrees` at the project root, with no protected `.base` intermediate clone. Context, Decision, and Consequences below are left as originally accepted per the ADR immutability rule (DOC-46 §4) and describe the topology as it stood on 2026-07-28; they are not an edit to that history. The existence/ownership authority split this ADR establishes is topology-agnostic and remains in force for the current `./.worktrees` shape.

## Context

**Provenance is not recoverable from git — a limit of git's data model, not our usage.** Nothing in `git worktree list --porcelain`, nor anything in the `.git/worktrees/<id>/` administrative directory, records who ran `git worktree add`, on whose behalf, or as part of which unit of work. git can answer "does this worktree exist, where does it live, and what branch is it on" — it cannot and never will answer "who is entitled to reclaim it." Any system that needs the second answer must carry it somewhere git does not look.

**ADR-0020 (Accepted, 2026-07-22)** already introduced a sentinel (`.trusty-mpm-worktree`, carrying a JSON `{owner_session_id, created_at}` payload — the mechanism issue #3649 established) plus a `SessionRecord.worktree_owner` registry field, and already treats a KNOWN-owner reclaim candidate as approved only if "`git worktree list` on the owning checkout agrees the path is a real, still-registered worktree." That check is directionally correct but was applied narrowly, as one gate inside one reclaim path — not as a workspace-wide principle. Separately, ADR-0020's orphan-GC (`find_orphaned_worktrees`) discovers candidate worktrees by *walking directories* under known store shapes (`.worktrees/<name>`, `.base/.worktrees/<session-id>`), not by querying git's own worktree registry. That gap is exactly what let two incidents happen:

1. **2026-07-21:** `rm -rf .base/*` destroyed the shared bare-clone's git internals and orphaned ~70 of 77 worktrees across every session. Because the on-disk directories were not cross-checked against what git itself still recognized, the divergence between "directory exists" and "git recognizes this worktree" was invisible until it was a data-loss incident.
2. **A recurring dual-registry divergence:** two independent worktree registries have been found holding entries with **zero overlap** — 53 and 45 entries respectively, with 14 worktrees physically located under `.base` registered to the *parent* repo and structurally unreclaimable through either registry. Each registry believed it alone knew what existed; neither could be cross-checked against ground truth.

Both incidents share a root cause: something *other than git* was treated as authoritative for whether a worktree exists. This ADR closes that gap by making the authority split explicit rather than implicit-and-partial as it was left in ADR-0020.

**Measured evidence that branch role cannot serve as the ownership boundary today** (a design alternative that was seriously considered — see "Alternatives," below): across 201 live worktree candidates, branch-name prefixes distribute as `fix/` 88, `feat/` 44, `docs/` 12, detached 10, `session/` 9, `chore/` 9. The operator's own manual checkouts, Claude-native `agent-*` harness worktrees, and genuinely tm-owned worktrees all draw from `fix/` and `feat/` indiscriminately. A `session|ws|workstream`-prefixed branch gate would admit only 9 of the 201 candidates and 0 of the 3 known sentinel-bearing (i.e., actually tm-provisioned) ones. Adopting branch role as the ownership boundary today would silently collapse reclamation eligibility to zero while every health dashboard kept reading green.

**The model this decision serves:** epic #4207 rebuilds the worktree subsystem so that every WRITING agent gets its own short-lived worktree, every workstream gets a durable branch, and worktree enumeration moves from filesystem-walking to `git worktree list --porcelain` ("derive, not walk" — #4207 Slice 1). That rewrite needs a settled, citable answer to "what decides existence, and what decides ownership" before the provisioning and reclamation code paths are rewritten against it — this ADR is that answer. It also directly informs an open question raised in issue #4208 (a proposed DOC-52 amendment) asking whether git-derived proof — a merged branch, a clean tree, no live session cwd — should *replace* the #3649 sentinel outright. This ADR's answer is no (see Decision and "Alternatives," below); #4208's git-derived checks are a valid strengthening of the ownership record's *inputs*, not a replacement for the record itself.

## Decision

We will split worktree authority into two non-overlapping questions, answered by two different sources, and never allow a third source to answer either:

1. **git is authoritative for EXISTENCE.** `git worktree list --porcelain` decides what worktrees exist, where they live, and what branch each is on. Nothing else — not a directory walk, not a registry, not a sentinel — may answer "does this worktree exist." Any tool that currently enumerates worktrees by walking known store-shape directories (as ADR-0020's `find_orphaned_worktrees` does today) is expected to migrate to querying git directly (tracked under epic #4207, Slice 1).

2. **A registration record is authoritative for OWNERSHIP** — which workstream or agent owns a given worktree. It answers "who may reclaim this" and nothing about "does this exist." It may never be consulted to decide existence, and existence-checking code may never fall back to it when git disagrees.

3. **The #3649 sentinel is retained** as the per-worktree provenance carrier — this is the owner's explicit decision, made with the alternative (removing the sentinel in favor of a purely git-derived ownership proof, as floated in issue #4208) considered and rejected. See "Alternatives," below.

4. **The registration index MUST be rebuildable** from ground truth — the set of on-disk sentinels plus `git worktree list --porcelain` — with no other durable input required. This is a new, explicit requirement this ADR adds on top of ADR-0020's mechanism: ADR-0020 introduced the sentinel and the registry field but did not require that the registry be reconstructable if lost.

5. **On the destructive path, a missing, empty, or stale index MUST fail CLOSED.** A worktree can never be made to look reclaimable by an absent, empty, or out-of-date index. This preserves and generalizes ADR-0020's existing "owner-unknown candidates are never auto-deleted" behavior to cover index loss/staleness specifically, not only per-worktree sentinel absence.

6. **Branch role as an ownership signal is DEFERRED.** We reject using branch name/prefix as an ownership or reclamation boundary at this time, per the measured evidence above. This is gated on provisioning actually enforcing a workstream-branch convention at write time (epic #4207's `branch = workstream` model) — once every newly provisioned worktree reliably carries a workstream branch, branch role becomes a viable *additional* signal. Until then, branch name proves nothing about ownership and must not be treated as if it does.

This ADR records the decision and its rationale only. It deliberately does **not** specify the registration index's storage location, file format, record schema, or concurrency/locking mechanism — a separate design pass (tracked against epic #4207 and the DOC-52 amendment in issue #4208) is underway on exactly those questions, and the owner reviews that design before any code implementing the index is written.

## Consequences

### Positive

- **Losing the index becomes an inconvenience, not an incident.** Because the index must be rebuildable from sentinels + `git worktree list --porcelain`, its loss is recovered by rebuilding it, not by a forensic data-loss investigation — directly closing the failure mode behind the 2026-07-21 `.base` incident and the dual-registry divergence.
- **A third registry cannot diverge about existence, because it is structurally incapable of answering that question.** Any future registry, cache, or dashboard is scoped to ownership (or derived views of it) and can never be the thing two tools disagree about when asking "does this exist."
- **Generalizes a check ADR-0020 already had in one narrow place** (git-list cross-check on the KNOWN-owner reclaim path) into a workspace-wide principle that governs every enumeration path, not just one gate.
- **Settles the open question in issue #4208** in favor of keeping the sentinel: a per-worktree, colocated marker survives failure modes an aggregate index does not (see "Alternatives"), even as git-derived checks (merged branch, clean tree, no live session cwd) are folded in as additional *evidence feeding* the ownership record, not a replacement for it.

### Negative / Trade-offs

- **The cutover problem.** Pre-#4207-model worktrees will never acquire a workstream branch — they were provisioned before that convention existed and nothing will retroactively rewrite their branch names. Whenever branch role is later promoted from deferred to an active ownership signal (per point 6, above), that promotion needs an explicit long-tail story for these pre-model worktrees, or it inherits exactly the silent-collapse-to-zero failure measured in this ADR's Context (the `session|ws|workstream` gate that admits 9 of 201 candidates and 0 of 3 sentinel-bearing ones). This is recorded here as a known future obligation, not a footnote to be forgotten when that promotion is eventually proposed.
- **The sentinel remains a single per-worktree point of loss.** It is a file that can be deleted, hand-edited, or never written (a provisioning bug). The index does not remove this exposure — it aggregates *over* sentinels, so an individual lost sentinel degrades that one worktree to owner-unknown (fail-closed, per point 5), while a lost *index* degrades nothing permanently (it rebuilds). These are different risk classes and this ADR does not conflate them.
- **Ownership recovery has a floor set by sentinel survival.** If a sentinel is lost, its worktree's ownership cannot be rebuilt from git alone — git only ever answers existence. In that specific case, only existence is recoverable, not ownership; the worktree becomes owner-unknown and fails closed under point 5, exactly as ADR-0020 already established for owner-unknown candidates today. This is a residual risk inherent to keeping the sentinel (rather than deriving ownership purely from git state, per the rejected alternative below) and is accepted as the cost of the sentinel's other advantages.

### Neutral / Follow-up work (explicitly deferred, not decided here)

- The registration index's storage location, file format, schema, and concurrency model — owner reviews a separate design pass against epic #4207 / issue #4208 before implementation.
- Migrating ADR-0020's `find_orphaned_worktrees` from directory-walking to `git worktree list --porcelain`-based enumeration (epic #4207, Slice 1) and replacing its `is_dir()`/grandparent-inference liveness checks (Slice 2).
- The dual-registry reconciliation itself (epic #4207, Slice 3 — explicitly flagged there as riskiest and dry-run-first).
- Whether and how git-derived ownership evidence (merged branch, clean tree, no live session cwd — issue #4208's proposal) is folded in as *additional input* to the ownership record, once the index design lands.
- The long-tail story for branch role's eventual promotion from deferred to active signal (see "Cutover problem," above).

## Alternatives Considered

- **Branch role as the ownership boundary** — rejected. The 201-candidate measurement in Context shows a `session|ws|workstream` branch gate admits 9 of 201 candidates and 0 of 3 known sentinel-bearing worktrees; `fix/` and `feat/` are drawn from indiscriminately by operator checkouts, harness `agent-*` worktrees, and genuinely tm-owned worktrees alike. Adopting this today would silently collapse reclamation to near-zero while dashboards continued to read healthy — precisely the failure shape this ADR exists to prevent, not reproduce.
- **Pure-git ownership with no side record** — rejected as impossible, not merely undesirable. git's data model does not record who ran `git worktree add`; there is no query against `git worktree list --porcelain` or the `.git/worktrees/` admin directory that answers "who owns this," now or after any conceivable git version. Something outside git must carry provenance; the only question was what, not whether.
- **Replacing the sentinel with the index** (issue #4208's proposed direction) — rejected. The owner decided the sentinel stays. A per-worktree marker colocated with the thing it describes survives a failure class (index loss/corruption) that an aggregate index does not; conversely the index survives a failure class (single sentinel loss) the sentinel alone does not. Keeping both, with the index required to be rebuildable *from* sentinels, is a fail-closed layering, not a redundancy to be pruned to one representation.
