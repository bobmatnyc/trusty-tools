# 0039. Operator-named sessions are unique by construction; the per-project serial stays scoped to auto-creation

- **Status:** Accepted
- **Date:** 2026-08-10
- **Scope:** crate `trusty-mpm` (`session_manager::naming`, `rename`, `adopt`; `core::session_launch::workstream_label`), crate `trusty-common` (`session_naming` module) — including an explicit, owner-ruled future-only rule for the `ws/<session-name>` GitHub label convention's interaction with rename
- **Reversibility Cost:** Medium-High — this changes a user-visible naming convention (two name shapes now carry different semantics an operator must learn) and the collision behavior operators see when they type a name that already exists; existing tooling, scripts, or muscle memory built against "every session ends in `-NN`" is invalidated for the operator-named case
- **Decision Drivers:** owner ruling 2026-08-10, closing the open question research raised ("let's also make session names an entity"); PR [#4978](https://github.com/bobmatnyc/trusty-tools/pull/4978)'s get-or-create ask, which is incoherent while a name resolves to a leaf rather than a session; issue [#3692](https://github.com/bobmatnyc/trusty-tools/issues/3692)'s existing auto-suffix precedent; issue [#5327](https://github.com/bobmatnyc/trusty-tools/issues/5327)'s slot-retention window, deliberately not adopted here
- **Supersedes / Superseded by:** none. Partially reverses #3692's "auto-suffix, never reject" policy, scoped precisely (Decision, point 2). Answers [DOC-66](../specs/DOC-66-session-workstream-model.md) §7 question 2 for the session-*name* half only — workstream identity stays [ADR-0030](0030-sessions-own-many-workstreams-from-the-tm-checkout.md)'s and DOC-66's to decide.

## Context

**Session names are not unique today, by design.** `allocate_serial` (`crates/trusty-common/src/session_naming/mod.rs:351-359`) hands the lowest free `NN` to each new session for a project leaf, and its own doc comment states the reason: "operators run several concurrent/historical sessions per project; the serial must be stable, glanceable, and REUSE gaps left by decommissioned sessions" (`session_naming/mod.rs:337-342`). `tm-foo-01` and `tm-foo-02` coexisting is intended, not a defect — a bare leaf `foo` was never meant to resolve to one session.

**A narrower uniqueness already exists, underneath that, unexposed.** The FULL generated name (`tm-foo-01`) is already treated as a de facto unique key among non-terminal records, enforced at every write path via the issue-#3692 "auto-suffix, never reject" convention: `SessionManager::rename` (`crates/trusty-mpm/src/session_manager/rename.rs:159-167`), `adopt_existing` (`crates/trusty-mpm/src/session_manager/adopt.rs:254-274`), and the create path's final safety net (`dedupe_session_name`, `crates/trusty-mpm/src/session_manager/naming.rs:219-231`) all route through the shared `taken_name_set`/`dedupe_name_against` pair (`naming.rs:134-180`), which auto-suffixes a colliding candidate rather than ever rejecting it. A terminal (decommissioned/deleted) record's name is excluded from "taken" and is reusable immediately, unsuffixed (`naming.rs:129-131,143`).

**PR #4978 exposed the gap.** It adds an `n [name]` picker command whose owner-stated intent is get-or-create: create a session named `<name>` only if one does not already exist. That is incoherent under the current model — a bare name identifies a leaf, which may already have several live sessions (`tm-foo-01`, `tm-foo-02`, …), so "does `foo` already exist" has no single answer to get-or-create against. #4978 ships first with always-create semantics (Related Decisions, below); this ADR is what get-or-create implements next.

**DOC-66/ADR-0030 do not answer this.** They give a `workstream_id` identity to the worktree+branch+PR bundle a session drives ([DOC-66](../specs/DOC-66-session-workstream-model.md) §1.2, `docs/specs/DOC-66-session-workstream-model.md:96-108`) and, in reversing DOC-52 §1.5's "the session name IS the workstream name" exception, explicitly leave open what (if anything) replaces session-name-derived identity: "Do they re-key on `workstream_id`, and what happens to labels already on merged and open PRs?" (DOC-66 §7 question 2, `DOC-66-session-workstream-model.md:338`). This ADR closes that question for the session's own name; it does not touch `workstream_id` or decide anything DOC-66/ADR-0030 own.

**Session and workstream overlap, and this ADR only covers half of it.** Owner framing, verbatim: "it's clear that workstream and session overlap to some degree, though we can rename a workstream to reflect changed priorities." The overlap is real and is exactly what DOC-52 §1.5 encoded and ADR-0030 partially reversed: in trusty-mpm a session's tmux name has always doubled as the only identity a workstream (via `ws/<name>`) had. ADR-0030 keeps the session hosting many workstreams but moves the *workstream's* durable identity to `workstream_id`, decoupling it from the session name. This ADR governs the other half — what the session's own name resolves to, for lookup, attach, and (Decision point 4, below) labeling — and stops there. Where the overlap begins and ends: a session's name is the operator-facing handle a workstream's GitHub label is still derived from today (`ensure_workstream_label`, unaffected by DOC-66/ADR-0030 while they remain Draft/Proposed); once `workstream_id`-keyed labeling ships, the two axes fully decouple, and that is DOC-66/ADR-0030's transition to specify, not this ADR's.

## Decision

**1. The split is by origin, not by two competing naming conventions.** Owner clarification, verbatim: "The serial is only used when auto-creating a session based on project." So:

- **Auto-created from a project directory** (no operator-supplied name) → `tm-<leaf>-NN`, unchanged. The serial exists because the system derived the name from the directory alone and has nothing else to disambiguate concurrent sessions on the same project.
- **Operator-named** (`n <name>`, a future `tm launch --name-hint`, or equivalent) → `tm-<name>`, no serial. The operator supplied the distinguishing part, so there is nothing left for a serial to disambiguate.

This narrows nothing in the existing serial mechanism — `allocate_serial`'s own doc comment already describes exactly this role ("several concurrent/historical sessions per project," `session_naming/mod.rs:337-338`). The decision states that role's *scope* explicitly (auto-creation only) rather than leaving it assumed to cover every session.

**2. Collision behavior for an operator-named session: attach if live, create if terminal.** `n foo` resolves to the literal name `tm-foo`. If a non-terminal record currently holds that name, the operator attaches to it. If the only record holding it is terminal (decommissioned/deleted), a fresh session is created under that name, reusing it exactly as the existing terminal-tombstone rule already allows (`naming.rs:129-131`).

**This partially reverses issue #3692's "auto-suffix, never reject" policy — for operator-typed names only.** Auto-suffix stays fully intact for every case #3692 was written for: a *system-chosen* candidate that collides — `rename`'s and `adopt_existing`'s dedupe against `taken_name_set` (`rename.rs:159-167`, `adopt.rs:254-274`, `naming.rs:149-167`) — and the create path's final pre-tmux-create safety net (`naming.rs:219-231`). Those are unchanged by this decision. The two are different questions that happened to share one code path: #3692's policy exists because the *system* chose a name and must never fail to produce one; get-or-create exists because the *operator* chose a name, and silently suffixing it (`tm-foo-2`) would defeat the entire point of typing `foo` a second time — the operator wants back the session they named, not a sibling of it.

**3. The name is a mutable key onto a stable id, not the identity itself.** `ManagedSessionId` is, and remains, the durable primary key (`crates/trusty-mpm/src/session_manager/record.rs`). `tmux_name` — the field this decision governs — is a mutable, overwritable field: `SessionManager::rename` sets it in place (`updated.tmux_name = new_name.clone()`, `rename.rs:202-203`) with no secondary record kept. "Session names as an entity" means a name *resolves reliably* to a session (its id), on attach and lookup — it does not mean the name is itself a durable identity a session carries for life. This distinction is stated explicitly because DOC-52 §1.5 made the opposite mistake once, declaring the session name "permanent, documented, sanctioned" as the workstream's own identity, and ADR-0030 had to reverse it. A reader who takes "name as entity" to mean "name IS the identity" will repeat that mistake at the session-name grain the moment the next rename happens.

**4. On rename, the old name frees immediately — the same posture as a terminal tombstone, extended to cover this case.** A rename is not a termination, so the existing rule ("a terminal record's name is reusable as-is, unsuffixed," `naming.rs:129-131`) does not literally apply — but no third option was invented for it. `rename` already only ever holds one current name per record (`rename.rs:202-203` overwrites in place; there is no alias table anywhere in the record or store), so "alias — the old name still resolves" would require inventing new state that does not exist, and "tombstone — blocks reuse for a window" would require inventing a new reclamation policy where three (per-leaf serial immediate-reuse, `naming.rs:129-131`'s terminal-tombstone-immediate-reuse, and `SlotRegistry`'s unrelated 7-day slot window, [#5327](https://github.com/bobmatnyc/trusty-tools/issues/5327)) already coexist and disagree. Extending the immediate-free rule to renames is the option that adds no new state and no fourth policy: the moment `rename` persists the new `tmux_name`, the old string is simply absent from every non-terminal record's name and is available the next time it is requested — by `n <old-name>`, a fresh auto-create, or another rename.

**This reading is confirmed, not assumed — the code was checked for anything that would contradict it.** Point 5 below is what removes the last candidate obligation: once `ws/<name>` labeling is future-only (owner ruling), the old name has no reader anywhere that expects it to keep resolving to anything after a rename. `rename.rs` (read in full) touches only `tmux_name`; no alias, mapping, or secondary index of prior names exists in `SessionRecord`, the store, or `SlotRegistry` (which is keyed on `ManagedSessionId`, not name, and untouched by rename — `slots.rs:96-126`). With the label question settled as future-only, immediate release is not merely convenient — it is the only reading with zero outstanding obligations to discharge, which is what makes it "cheap and consistent" rather than a corner cut.

**Accepted residual risk, same class as the codebase's existing #3707 acknowledgment:** because nothing locks the old name across a rename's own TOCTOU window (`rename.rs:126-138`'s documented gap, and `naming.rs:66-77`'s parallel documented gap for create), a name freed by one rename could in principle be claimed by an unrelated concurrent `n <freed-name>` before the renaming operator acts on it. This is accepted, not closed, on the same terms `naming.rs:204-212` already accepts the equivalent race for fresh creates.

**5. Rename affects `ws/<session-name>` labeling going forward only. No retroactive relabeling, aliasing, or reconciliation of labels already applied.** Owner ruling, verbatim: "the github labeling issues I'm not concerned about, though it should affect only FUTURE agent work." This is a closed decision, not an open gap: a workstream's history splitting across two labels after a rename is an **accepted consequence** — stated, chosen, and cheap — not a defect owed a future fix.

Verified against the source, for the record: `ensure_workstream_label`/`spawn_workstream_label_ensure` (`crates/trusty-mpm/src/core/session_launch/workstream_label.rs:93-189`) is called from exactly four sites, all of them session *launch* paths — `daemon/managed_routes/lifecycle.rs:782,1081,1280` and `daemon/managed_routes/launch_on_main.rs:201` (re-exported at `core/session_launch/mod.rs:221`). `SessionManager::rename` (`rename.rs`, read in full) calls none of it. That absence is now the specified behavior, confirmed to match the ruling, not a gap this ADR leaves for someone else to close.

Real-world instance, so the shape is visible rather than hypothetical: session `b6cf22d0` was renamed `tm-trusty-tools-03` → `tm-code` on 2026-07-30. Both `ws/tm-trusty-tools-03` (on everything filed before the rename) and `ws/tm-code` (on everything filed after) exist on that workstream's history, by design.

## Consequences

### Positive

- **Get-or-create becomes coherent.** `n foo` now reliably resolves to at most one live session; PR #4978's owner-stated intent has a name to resolve against, closing the gap that motivated this ADR.
- **No new reclamation policy invented.** Point 4 reuses the existing immediate-free rule rather than adding a fourth, alongside the per-leaf serial's immediate reuse and `SlotRegistry`'s unrelated 7-day window.
- **The existing #3692 auto-suffix guarantee is untouched for every case it was built for** — system-chosen candidates in `rename`/`adopt`/create's final safety net keep failing over to a suffix, never a rejection.
- **Leaf-name collisions are already clean, confirmed from the source, no guard needed.** `tm-trusty-tools` (operator-named) and `tm-trusty-tools-01` (auto-created on the same project) coexist without ambiguity: `parse_serial_for_leaf` (`session_naming/mod.rs:324-333`) strips `PREFIX`, then the leaf, then requires a literal `-` before exactly two ASCII digits; for `tm-trusty-tools` the leaf-strip leaves an empty remainder, `strip_prefix('-')` on an empty string returns `None`, so it never parses as a serial for that leaf. `allocate_serial`'s scan (`:351-359`) therefore never counts `tm-trusty-tools` as an occupied serial, and a subsequent auto-create for that leaf still gets `-01` cleanly. `is_managed_session_name`/`strip_managed_prefix` (`:107-143`) check the `tm-`/`tmpm-`/`trusty-mpm-` prefix only, so `tm-trusty-tools` is still correctly recognized as managed and correctly display-stripped. No function inspected in this repo assumes every managed name ends in a two-digit serial.
- **Rename affects `ws/<session-name>` labeling for future work only — stated as a rule, not left as an implied gap (owner ruling, 2026-08-10).** No relabeling, aliasing, or history reconciliation happens on rename, and none is owed: `ws/<old-name>` stays on everything it already tagged, `ws/<new-name>` governs everything an agent labels from the rename forward, and a workstream's history splitting across both is accepted as cheap and intended. In the wild: session `b6cf22d0` carries both `ws/tm-trusty-tools-03` (pre-rename) and `ws/tm-code` (post-rename, 2026-07-30) on its history, by design.

### Negative / Trade-offs

- **Two name shapes now carry different semantics.** `tm-<leaf>-NN` (many-per-project, serial-disambiguated) and `tm-<name>` (one-per-name, attach-on-collision) coexist and an operator or a script must know which kind a given name is to predict its behavior on reuse.
- **The rename-race residual (Decision point 4)** is accepted on the same terms as the codebase's existing #3707/`naming.rs:204-212` acknowledgment — a narrow, documented TOCTOU window, not closed by this decision.
- **`n foo` no longer means "always create a new session"** — a behavioral change from #4978's initial always-create ship (Related Decisions, below) that any caller relying on the original always-create contract must account for.

### Neutral / Follow-up work

- Implementation is separate from this ADR. PR #4978 lands first, as already reviewed, with its shipped always-create semantics unchanged; get-or-create is the follow-up PR that implements this ADR's Decision.
- Issue #5301's idempotent `tm-` prefix normalizer touches the same `session_naming` module this decision touches, for an unrelated, narrower defect (hint-prefix idempotency: `tm-foo` hint becoming `tm-tm-foo-01`). It is adjacent, not folded into this decision.

## Alternatives Considered

- **Auto-suffix operator-typed names too, staying fully inside #3692's existing policy.** Rejected — this is exactly what makes #4978's get-or-create incoherent: typing `n foo` a second time would produce `tm-foo-2` (or similar) instead of reattaching, defeating the reason an operator names a session in the first place.
- **Reject a collision on an operator-typed name instead of attaching.** Rejected — inconsistent with this repo's own #3692 precedent of never failing a session-naming request outright, and strictly worse for the operator than attach-if-live: a reject forces the operator to look up and re-type an existing session's exact name themselves.
- **Give the old name a tombstone/blocking window on rename, mirroring `SlotRegistry`'s 7-day retention.** Rejected — would add a fourth reclamation policy where three already coexist and disagree (per-leaf serial, terminal-tombstone, `SlotRegistry`'s 7 days); no evidence in the code that a name needs the same conservatism a worktree-backed slot does, since a name carries no filesystem state of its own to protect.

## Related Decisions

- **ADR-0030 (A session owns many workstreams and lives in the tm checkout, Proposed):** **Consistent, and this ADR is the session-name counterpart to it.** ADR-0030 gives identity (`workstream_id`) to the worktree+branch+PR bundle a session drives; this ADR gives the session's *own* name a resolvable-by-construction identity for the operator-named case. Different grains, no overlap in mechanism. ADR-0030's point 7 (agent worktrees are children "by record, not by location") and DOC-66 §5 are untouched — this decision governs session-name lookup/attach/collision only.
- **ADR-0036 (All worktrees are siblings under `.claude/worktrees/`):** **No interaction.** Governs worktree topology; this decision touches no worktree path or directory naming.
- **ADR-0037 (PM placement precedence — main checkout by default):** **No interaction, orthogonal axis.** 0037 decides WHERE a session runs (main checkout vs. a requested worktree); this ADR decides what a session is CALLED and how that name resolves. An operator-named session under this decision is placed exactly as 0037 already specifies, unaffected.
- **DOC-52 §1.5 (trusty-mpm's "permanent, sanctioned" session-name-IS-workstream-identity exception):** **Conflict already resolved by ADR-0030, not reopened here.** This ADR explicitly avoids repeating DOC-52 §1.5's error (Decision point 3): a session name is a mutable key onto `ManagedSessionId`, never the identity itself.
- **DOC-66 (Session/workstream model) §7 question 2** ("Do they re-key on `workstream_id`, and what happens to labels already on merged and open PRs?"): **Answers both halves of the question as posed, differently.** This ADR settles what a session's OWN name resolves to (Decision points 1-4). For "what happens to labels already on merged and open PRs" specifically, the owner ruling in Decision point 5 answers it directly: nothing happens to them — they stay on `ws/<old-name>` by design, future work uses `ws/<new-name>`, no reconciliation is owed. Whether `ws/<name>` labels eventually re-key onto `workstream_id` once it ships remains DOC-66/ADR-0030's open question; this ADR does not decide that half.
- **Issue #3692 (auto-suffix, never reject):** **Partially reversed, scoped precisely.** Stays in force for system-chosen candidates (`rename`/`adopt` collision dedupe, `naming.rs:149-167`, `rename.rs:159-167`; the create path's final safety net, `naming.rs:219-231`). Reversed only for operator-typed get-or-create names (Decision point 2), which now attach-if-live instead of suffixing.
- **PR #4978 (`n [name]` picker):** **Sequencing, not conflict.** Ships first with always-create semantics as already reviewed; this ADR is the design the get-or-create follow-up implements.
- **Issue #5301 (idempotent `tm-` normalizer + `tm launch --name-hint`):** **Adjacent, not folded in.** Shares the `session_naming` module; addresses a narrower, unrelated defect (hint-prefix idempotency).
- **Issue #5327 (`tm ls` slots held 7 days after decommission, `SlotRegistry`):** **Not adopted, deliberately.** This ADR aligns name reclamation with the existing per-leaf/terminal-tombstone immediate-free convention (`naming.rs:129-131`, extended to renames by Decision point 4) — explicitly NOT `SlotRegistry`'s 7-day window, which is a separate, `ManagedSessionId`-keyed, daemon-lifetime axis this decision leaves untouched.

No conflict with any Accepted or Proposed ADR that was not already resolved by ADR-0030 before this decision.
