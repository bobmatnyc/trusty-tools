# 0036. All worktrees are siblings under `.claude/worktrees/`; ownership tracking is unchanged

- **Status:** Accepted
- **Date:** 2026-08-09
- **Scope:** crate `trusty-mpm` (worktree provisioning paths, orphan-GC, reclamation tooling, bundled skills), with path-constant propagation into `trusty-common`, `trusty-memory`, `trusty-agents`, and `trusty-search`
- **Reversibility Cost:** Medium — the decision itself is a path constant and its propagation, but every provisioning call site, reclamation sweep, doctor probe, bundled skill, and operator habit is written against the current `./.worktrees` shape, and worktrees already on disk under the old shape are not relocated by it
- **Decision Drivers:** owner ruling of 2026-08-09; the Claude Code harness hardcodes `.claude/worktrees/` and exposes no relocation setting, so it is the one store this repo cannot move; a tm session worktree at `./.worktrees/<uuid>` makes every harness-forked agent worktree land NESTED inside it; two worktree homes means two places every tool must look
- **Supersedes / Superseded by:** Amends **ADR-0020** (`0020`'s header gains a dated topology note pointing here and its status becomes `Amended by 0023, 0036`; ADR-0020's Context/Decision/Consequences are left as originally accepted per the ADR immutability rule — `docs/adr/README.md`, DOC-46 §4 — this ADR is the record of the refinement, not an edit to that history). Qualifies **ADR-0030** point 7 (Proposed) on path shape only. Reverses nothing in **ADR-0023**.

## Context

**ADR-0020 named this ADR before it existed.** ADR-0020's "Out of scope: the harness `.claude/worktrees/` store" section states that it reserves "the SAME sentinel filename/shape (`.trusty-mpm-worktree` with the JSON payload) as forward-compatible in case a future ADR unifies ownership tracking across all three stores," and its "Neutral / Follow-up work" list carries "Consider whether the harness `.claude/worktrees/` store should eventually share this ownership model." This ADR is that future ADR. It answers the reserved question — and answers a second one ADR-0020 did not ask, about where the stores live rather than how they are tracked.

**The harness home is the one location this repo cannot move.** Claude Code hardcodes `.claude/worktrees/` in both worktree-creating surfaces — the `EnterWorktree` tool and `Agent(isolation: "worktree")` — and exposes no setting to relocate it. A prior investigation checked the project `.claude/settings.json`, `~/.claude/settings.json`, and the codebase for such a key and found none; `~/.claude/settings.json` was re-checked while drafting this ADR and still carries no worktree key. Every other worktree home in this workspace is a path constant we own and can change. That asymmetry, not a preference between two directory names, is what decides the destination: unification is only achievable at `.claude/worktrees/`.

**How the current shape got here, stated accurately.** ADR-0020 and ADR-0023 both carry a "Topology note (2026-08-05)" recording that the `.base` bare-clone store was retired by owner ruling and that worktrees "now provision exclusively under `./.worktrees` at the project root." That was a ruling to retire `.base`. `./.worktrees` is where the change landed — it is not a considered rejection of `.claude/worktrees/`, and nothing in either ADR weighs the two locations against each other. This ADR is therefore not reversing a deliberate prior choice; it is making a choice that was never made.

**The concrete defect.** `crates/trusty-mpm/src/assets/skills/tm-delegation-patterns.md:225-231` instructs the PM to pass `isolation: "worktree"` whenever it dispatches two or more parallel agents that modify files. The harness resolves `.claude/worktrees/` relative to the dispatched agent's cwd, and that cwd is the session's worktree. So when a session worktree lives at `./.worktrees/<uuid>`, following the repo's own delegation guidance creates `./.worktrees/<uuid>/.claude/worktrees/<name>` — an agent worktree nested inside a session checkout. This is not a projected risk. `crates/trusty-mpm/src/session_manager/worktree_git_fixture.rs:301-306` documents the incident that forced a test fixture for the shape: "seven of them were live inside `.base/.worktrees/2eb72dca-…` while the parent reported `dirty_files = 0`," because `main` gitignores the path. A live instance of the same shape exists on this machine right now at `.worktrees/tm-trusty-tools-05/.claude/worktrees/website-local`.

Nesting is what makes that dirty-tree report wrong. A parent checkout does not see, and cannot report on, a gitignored worktree of the same repo living inside it. Siblings have no such blind spot: a worktree that is not inside another worktree cannot be hidden by it.

**Ownership tracking is not the thing under discussion.** ADR-0020's sentinel payload, `SessionRecord.worktree_owner`, the owner-gated `decommission`, the owner-gated orphan-GC, and `resolve_ownerless_with_grace` / `OWNERLESS_GRACE` are all keyed on identity, never on path. Since #4207/#4288 orphan enumeration is git-derived and location-agnostic, and `crates/trusty-mpm/src/session_manager/prune_orphan_tests.rs:238` (`prune_orphaned_worktrees_never_deletes_claude_native_worktree`) already asserts that a worktree under `<repo>/.claude/worktrees/` is discovered, reported owner-unknown, and never deleted. The mechanism already works at the destination.

## Decision

We will adopt a single worktree topology, stated as two independent claims that are decided separately and must not be collapsed into one:

1. **Ownership tracking stays exactly as it is.** Worktrees are tracked to sessions by ADR-0020's mechanism — the `.trusty-mpm-worktree` sentinel with its JSON payload, the `SessionRecord.worktree_owner` registry field, owner-gated decommission, owner-gated orphan-GC, and the `resolve_ownerless_with_grace` / `OWNERLESS_GRACE` fail-closed rule — under ADR-0023's existence/ownership authority split. This ADR changes none of it, and nothing below may be read as weakening it.

2. **Every worktree is a sibling under `.claude/worktrees/`.** Both trusty-mpm-provisioned session worktrees and Claude Code harness worktrees live as flat siblings in one `.claude/worktrees/` directory. There is no nesting of one worktree inside another and no second worktree home. `./.worktrees` at the project root ceases to be a provisioning destination.

The destination is chosen because it is the only one the harness will accept, not because it is otherwise preferable. Consolidation on any path we control would leave the harness store where it is and preserve exactly the two-home problem this decision exists to remove.

This ADR records the decision and its rationale only. It does not perform the migration, does not specify the path constants' names or where they live, and does not decide what happens to worktrees already on disk under the old shape.

## Consequences

### Positive

- The nesting shape is eliminated at its source. Following `tm-delegation-patterns.md`'s own instruction can no longer put an agent worktree inside a session checkout, so the gitignored-nested-worktree blind spot — the one that reported `dirty_files = 0` over seven live worktrees — has no shape to occur in.
- One home means one place to enumerate. Every reclamation sweep, `tm doctor` probe, dashboard, and operator `ls` looks at a single directory rather than reconciling two, which removes a standing source of the dual-registry divergence ADR-0023's Context documents.
- The harness store stops being a special case. ADR-0020 declared it out of scope and reserved the sentinel shape for a future unification; after this decision the harness store is simply where worktrees live, and ADR-0020's reservation is spent rather than pending.
- Nothing about safety changes. Because the ownership mechanism is keyed on identity and enumeration is git-derived, the fail-closed guarantees carry over unexamined — `prune_orphaned_worktrees_never_deletes_claude_native_worktree` already proves the destination behaves correctly today.

### Negative / Trade-offs

- **The migration is rung 5 and touches five crates.** Path constants and their propagation reach `trusty-common`, `trusty-memory`, `trusty-agents`, `trusty-mpm`, and `trusty-search`. It is a cross-crate contract change to a persistence-adjacent location under active process lifecycle, so it owes `--include-ignored` integration coverage, failure-path tests, and a `code-critic` round. None of that is done here.
- **Existing worktrees are not relocated by this decision.** Worktrees already living under `./.worktrees` keep working and keep their sentinels; the two shapes coexist until something explicitly moves them. Whether that is a migration, an attrition policy, or permanent dual-read is not decided here, and until it is, "one home" describes newly provisioned worktrees only.
- **Relocating a worktree changes its project identity.** ADR-0008 point 4 keys a worktree's canonical project id on its own working-directory path, so a worktree that moves gets a different id — and therefore a different trusty-search index and trusty-memory palace. This is inherent to any relocation, not to this destination, but the migration must account for it rather than discover it.
- **The sibling rule is not self-executing under the harness.** The harness resolves `.claude/worktrees/` relative to the dispatched agent's cwd. If an agent is dispatched with a workstream worktree as its cwd and uses `isolation: "worktree"`, the harness will still create `.claude/worktrees/<name>` under that worktree. Flat siblings therefore require that such dispatches originate from the checkout that owns the shared `.claude/worktrees/` directory — which is what ADR-0030's "the session's home is the tm checkout" already arranges, but which is a real precondition rather than a consequence of the path constant alone. The migration must close this or the nesting returns through the same door.
- **`crates/trusty-mpm/src/assets/skills/tm-cli-operations.md:300`** describes `tm session prune-worktrees` as removing "orphaned `.worktrees/` dirs". That line becomes wrong the moment the migration lands and must be updated with it.
- **`.gitignore` and dirty-tree reporting need a second look.** The nesting blind spot depended on `main` gitignoring the nested path. Moving the store does not by itself decide whether `.claude/worktrees/` is ignored, or what a checkout should report about a sibling; that interaction is worth an explicit answer during the migration rather than an inherited default.

### Neutral / Follow-up work (deferred, not decided here)

- The migration itself: the path constants, their propagation across the five crates, the provisioning call-site changes, and the rung-5 gate. This ADR is a prerequisite for it, not a substitute.
- The disposition of worktrees already on disk under `./.worktrees` — relocate, dual-read, or let attrition handle them.
- Whether ADR-0020's reserved sentinel shape should now actually be *written* into harness-created worktrees, giving them a resolvable owner instead of the permanent owner-unknown status they hold today. This ADR unifies the location; it does not decide whether the harness store gains provenance, and today it cannot, since the harness writes no sentinel.
- Updating ADR-0023's own 2026-08-05 topology note, which likewise says worktrees "now provision exclusively under `./.worktrees`" and becomes stale when the migration lands. Left alone here deliberately: the header amendment this ADR makes is to ADR-0020, the ADR whose reserved follow-up this answers.
- Reconciling `docs/reference/worktree-discipline.md`, `CLAUDE.md`'s "Parallel Worktree Discipline" section, and the bundled `tm-workflow` / `tm-pr-workflow` skills, all of which document the current shape. Deliberately untouched by this ADR — those files are under concurrent edit elsewhere, and prose that describes a topology should change when the topology does, not before.

## Alternatives Considered

- **Consolidate on `./.worktrees` instead, moving harness worktrees there.** Rejected as not achievable. The harness hardcodes its destination and offers no relocation setting; a decision to consolidate anywhere else consolidates only the stores we control and leaves the harness store exactly where it is, which is the two-home problem restated rather than solved.
- **Keep two homes and teach every tool to read both.** Rejected. This is the status quo, and it is what produced the dual-registry divergence in ADR-0023's Context and the seven-nested-worktrees incident in `worktree_git_fixture.rs`. Each new consumer must independently learn both shapes, and the failure mode of forgetting one is silent — a sweep that reads one home reports healthy while the other accumulates.
- **Forbid `isolation: "worktree"` dispatches instead of moving the store.** Rejected as fixing the symptom. It would remove one route to the nested shape while leaving the two-home topology, and it costs the parallel-dispatch capability `tm-delegation-patterns.md` exists to enable. `EnterWorktree` reaches the same shape by a different path.

## Related Decisions

Vetted against prior ADRs (`docs/adr/INDEX.md`) on 2026-08-09:

- **ADR-0020 (Session-owned worktrees: ownership registry + owner-gated reclamation):** **Amends.** ADR-0020 explicitly reserved this question in two places — the "Out of scope: the harness `.claude/worktrees/` store" section, which holds the sentinel shape open "in case a future ADR unifies ownership tracking across all three stores," and the "Neutral / Follow-up work" item "Consider whether the harness `.claude/worktrees/` store should eventually share this ownership model." This ADR answers where the stores live and changes none of ADR-0020's mechanism: the sentinel, the registry field, owner-gated decommission, owner-gated orphan-GC, and the ownerless-grace rule all stand unmodified, because every one of them is keyed on identity rather than path. ADR-0020's status becomes `Amended by 0023, 0036` and its header gains a dated topology note pointing here; its Context, Decision, and Consequences are untouched per the immutability rule.
- **ADR-0023 (Worktree authority split: git decides existence, a rebuildable index decides ownership):** **Consistent.** ADR-0023's principle is that `git worktree list --porcelain` is the sole authority for existence and a rebuildable record the sole authority for ownership. Both are location-agnostic by construction — neither authority mentions a path — so relocating the store cannot disturb either. This ADR is in fact ADR-0023's principle paying off: because enumeration is git-derived rather than directory-walked (#4207 Slice 1, operationalized in #4288), changing where worktrees live does not change how they are found. Point 5's fail-closed rule on the destructive path is likewise untouched. No contradiction.
- **ADR-0030 (A session owns many workstreams and lives in the tm checkout, Proposed):** **Conflict (resolved on wording), and mutually reinforcing on substance.** ADR-0030 point 7 says "Agent worktrees are children of a workstream, not workstreams. They are created **under** the workstream that dispatched them" — read as a path claim, that is the nesting this ADR forbids. The resolution is that "child" there is a *parentage and lifecycle* concept, not a directory one: DOC-66 §5 encodes it as a `parent_workstream_id` field in the sentinel payload, and its stated purpose is reapability — "Giving them a parent is what makes them reapable at all." Parentage survives this ADR unchanged; only the path shape is decided against. ADR-0030 being Proposed, its wording should be tightened to say "children of" without "created under" when it moves to Accepted. On substance the two decisions need each other: ADR-0030's point 3 (the session's home is the tm checkout, never `cd`-ed away) is precisely the precondition that lets the harness's cwd-relative `.claude/worktrees/` resolve to one shared directory rather than one per worktree. Neither decision fully delivers a flat topology without the other.
- **ADR-0008 (Project-identity convention: full-path slug of the nearest git root):** **Consistent, with a migration obligation.** ADR-0020's and ADR-0023's vetting notes both characterize ADR-0008 as an `<owner>/<repo>` nesting convention; that is inaccurate — `<owner>/<repo>` is the `repos_root` layout, while ADR-0008's actual rule is a canonicalize-then-slug of the nearest git root, with point 4 giving each worktree its own id keyed on its own working-directory path. That rule is unaffected by where worktrees live: a worktree under `.claude/worktrees/` gets an id by exactly the same derivation as one under `./.worktrees`. What follows is an obligation on the migration, not a conflict with the convention — a *relocated* worktree's path changes, so its id changes, so its trusty-search index and trusty-memory palace change with it. Recorded under Consequences.
- **ADR-0012 (Per-instance GUID and marker-file identity):** **Consistent.** The `.trusty-mpm-worktree` sentinel remains a colocated on-disk marker carrying identity, exactly the pattern ADR-0012 established. A marker moves with the thing it marks; relocating the marked directory changes nothing about the pattern.
- **ADR-0016 (Orchestration Hierarchy: Engineering Lead / PM / Assistant, Proposed):** **No interaction.** ADR-0016 governs role-level authority; this ADR governs a directory layout. Neither makes a claim the other can contradict. Checked because ADR-0020 and ADR-0023 both vetted against it.
- **DOC-66 (Session/workstream model)** *(spec, not ADR, cited per DOC-46's ADR↔Spec cross-linking rule)*: **Consistent on mechanism, needs a path update.** §5 ("Agent worktrees as children") and §3's per-worktree sentinel extension (`workstream_id`, `parent_workstream_id`) are identity-keyed and survive intact. §5's prose about children being created under their parent needs the same wording correction as ADR-0030 point 7 when the migration lands.

No conflict with any Accepted ADR. The one conflict found is with ADR-0030, which is Proposed, and it is confined to a path-shaped reading of one sentence whose substance (parentage for reapability) this ADR preserves.
