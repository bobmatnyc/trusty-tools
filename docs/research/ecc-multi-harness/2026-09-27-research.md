# ECC multi-harness lessons for Trusty

Date: 2026-09-27. Status: research and recommendations for future work; not an implementation commitment.

## Conclusion

ECC offers useful examples for making multi-harness support explicit, installable, and testable. Trusty already has the architectural direction in [ADR-0059](../../adr/0059-canonical-agent-behavior-has-generated-host-adapters.md): canonical host-neutral behavior, deterministic host adapters, provenance, and explicit treatment of unsupported semantics. The opportunity is to turn that direction into a coherent capability registry, native integrations, and evidence-backed support claims.

## Review scope and evidence

- ECC: [affaan-m/ECC](https://github.com/affaan-m/ECC), inspected at commit `e482e579415fde18357cafce70f177ae19fd7f03` (package version 2.2.2).
- Trusty: local source at commit `4cc23fe86c3fa7c942d4771402a5d937751de8b1`.
- Source review plus targeted ECC tests. No ECC installation into the user's harnesses, no live cross-harness qualification, and no Trusty implementation changes.
- Trusty search reported no usable `trusty-tools` index, so discovery used direct workspace inspection.

These findings describe the inspected revisions. Recheck host versions and official extension contracts before implementation.

## What Trusty already has

The shared [`HarnessAdapter`](../../../crates/trusty-agents-common/src/adapters/traits.rs) contract recognizes and observes harnesses through terminal output and exposes pause/resume commands. Its [registry](../../../crates/trusty-agents-common/src/adapters/registry.rs) includes Claude Code, Claude MPM, Codex, Gemini, Augment, Trusty Agents, and shell adapters.

MPM's separate [`RuntimeKind`](../../../crates/trusty-mpm/src/runtime/mod.rs) managed-launch selector supports Claude Code and Trusty Code. Recognizing a Codex session does not establish support for provisioning, launching, resuming, or enforcing policy within it. Trusty also has [Codex MCP registration](../../../crates/trusty-common/src/codex_config.rs), so new integration work should reuse that rather than duplicate it.

[ADR-0059](../../adr/0059-canonical-agent-behavior-has-generated-host-adapters.md) already requires a neutral canonical source and explicit compatibility dispositions. Its implementation-status prose was not treated as current implementation evidence; the observations above come from source.

## Lessons worth applying

### 1. One capability registry, with support recorded per feature

ECC's [capability catalog](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/scripts/lib/harness-capabilities.js) records installation channel, scope, destination, hook configuration, and guided-install readiness. The tested catalog covers 15 registered installation targets across 14 harnesses; only Claude, Codex, and Kimi are guided-ready. This is installation coverage, not proof of equivalent runtime behavior.

Trusty should maintain one registry driving setup choices, documentation, diagnostics, and conformance tests. Record skills, agent definitions, MCP, startup context, blocking hooks, launch, resume, and observation separately. Include host version and CLI/desktop execution mode. Distinguish native, adapter-backed, instruction-only, and unsupported behavior, and separately record declared, installed, fixture-tested, and live-verified evidence.

### 2. Shared behavior with thin native adapters

ECC's [Cursor adapter](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/.cursor/hooks/adapter.js) translates event payloads and invokes shared hook scripts. Its [OpenCode plugin](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/.opencode/plugins/ecc-hooks.ts) maps native lifecycle and tool events.

Reuse this boundary pattern, but normalize into a neutral Trusty event contract rather than making Claude payload fields the universal internal format. Keep host-specific loading, event translation, packaging, and limitations at the edge. Preserve restrictions and delegation rules; reject unsupported requirements explicitly instead of silently reducing enforcement to instructions.

### 3. Useful integration without mandatory orchestration

ECC's [installation profiles](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/manifests/install-profiles.json) select modules. Its OpenCode default excludes hook runtime, which is an explicit opt-in.

Trusty should separate using its tools and skills in a host from allowing MPM to manage that host. Provide small useful profiles and use native extension points where available. MPM-managed launch/resume is an independent capability and deliverable.

### 4. Installation provenance and ownership

ECC's [install-state schema](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/schemas/install-state.schema.json) records source revision, target, selection, and operations. Its [multi-harness setup](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/scripts/lib/multi-harness-setup.js) validates ownership, identity, and changed files before trusting prior installation state.

Extend Trusty's existing provenance work across generated host exports, upgrades, and removal. Preserve user-owned configuration and expose conflicts or edited generated artifacts. Favor native plugin lifecycle management where supported.

### 5. Structured observation independent of control

ECC's [session registry](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/scripts/lib/session-adapters/registry.js) and [canonical session schema implementation](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/scripts/lib/session-adapters/canonical-session.js) normalize Claude history, Codex rollouts, OpenCode, and tmux orchestration into a shared snapshot.

Prefer structured session evidence where available, retaining source, timestamp, host version, and confidence. Keep terminal pattern recognition as a fallback. Being able to inspect a session must not imply authority or capability to control it.

## Caution: passing checks can preserve inconsistent support claims

ECC's [public compliance matrix](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/docs/architecture/harness-adapter-compliance.md) labels Codex instruction-backed, while its capability catalog describes native plugin hooks and its [Codex hook manifest](https://github.com/affaan-m/ECC/blob/e482e579415fde18357cafce70f177ae19fd7f03/hooks/codex-hooks.json) implements SessionStart.

The matrix consistency check and both native-hook tests passed. They validate separate surfaces; they do not reconcile the overall support claim. The implementation demonstrates a startup hook boundary, not general hook or blocking-policy parity. Trusty should use one capability authority and validate claims against specific implemented features and evidence. Do not copy ECC's broad harness labels or assume all installed targets are equally supported.

## Recommended delivery sequence

1. **Capability registry and generated support matrix.** Inventory current source and installed behavior, distinguish host versions and modes, and generate documentation and diagnostics from the same data. This supplies the contract for later work.
2. **Complete a Codex native integration.** Generate shared content under ADR-0059, reuse MCP registration, and verify supported native loading and lifecycle features. Keep MPM-managed Codex launch/resume as a separately accepted outcome.
3. **Cross-harness conformance scenarios.** Prove content loading, configuration preservation, hook semantics, exact-session resume where supported, and explicit rejection of unsupported requirements. Run fixture checks in CI and record actual host/version evidence for live qualification.
4. **Structured observation and broader host adoption.** Improve session evidence without conflating it with control; add OpenCode or Gemini once Claude/Codex validate the contract. Choose additional hosts based on actual user demand.

Track these outcomes through the existing future epic without starting implementation or creating duplicate child issues.
