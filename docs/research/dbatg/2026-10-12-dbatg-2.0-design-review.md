# DBATG as general PM behavior: design review for 2.0 (research, read-only, 2026-10-12)

Owner request (Bob, 2026-10-12 03:30Z): confirm that Decisions, Briefs, Asks, Tasks and Goals (DBATG) are general PM behavior, structured JSON, not committed, owned by the PM only and deterministically migrated to the Architect; review the design adversarially; include it in 2.0; weigh event bus against files.

Nothing was filed, sent or committed. trusty-tools was read through `origin/main`. Figures come from the files named in each row.

## 0. Verdict

The PM-side store (DATG) works on two PMs. It is not general PM behavior, it has no Briefs, and nothing migrates it deterministically. Four of six properties are partly met or not met. The design below closes the gaps without moving the PM's source of truth off disk.

Recommendation on storage: files are the PM's source of truth; the daemon event bus carries only a notification. Reason: the bus is lossy by design (section 4).

## 2. Proposed 2.0 design (one page)

**Principle.** Every PM keeps its own plan: goals, decisions, asks, tasks, briefs. The PM writes. The Architect reads copies and resolves what it can.

**Location and files.** `<project>/.trusty-mpm/dbatg/` per PM session, not per project (a shared checkout holds five PMs in trusty-tools: `datg-hook.sh` needs a session filter today). Path: `<project>/.trusty-mpm/dbatg/<session>/`. Contents:
- `state.json`: snapshot, `schema` (int), `v` (int, +1 per write), `code`, `session`, `epoch` (random id set at init; changes if the store is re-initialised), `next` counters, `goals[]`, `items[]` (kind D or A), `tasks[]`, `briefs[]`.
- `log.jsonl`: append-only change log. Each line has `seq` (per-session, gapless), `t`, `id`, `ev`, optional `note`.
- `outbox.jsonl`: append-only up-flow records, one per item revision the Architect must see. Written in the same locked write as `state.json`.
- `acks.json`: written only by the Architect-side ingest: `{epoch, acked_seq}` (the one file the PM does not write; the PM reads it).
- `.lock`.
`.trusty-mpm/dbatg/` joins the tm scaffold ignore block, and `tm` writes the rule on first init. Not committed, not pushed.

**Ids.** `<code>-<Prefix><2 hex>`: G, D, A, T, and new B (`th-B04`). The code is unique per host, assigned from a registry the Architect keeps (section 3, failure 5). Counters per prefix in `next`; never renumber; retire done items after 7 days into `log.jsonl` only.

**Kinds and states.**
- Goal: active | done | parked, rank, `finish`, `maps` (Architect goal id).
- Decision D (question): open | answered | done; `opts` with `markers` {work, scope, risk}, `specs`, `esc` (null | architect), `answer`, `outcome`.
- Ask A (owner action): same states.
- Task T: open | running | done; `goal`, `to`, `outcome`, `links` [{issue, pr, spec}].
- Brief B: one paragraph `answer` to a question, optional `doc` under `docs/briefs/`, `goal`, status open | done. Same one-paragraph cap as the dashboard Briefs section. The PM writes the paragraph; long text goes to a committed `docs/briefs/` file in the project, as the dashboard rule already says.

**Write path.** PM only, at the end of each turn, through `tm dbatg <verb>` (batch form takes `--file`, not only stdin). A PM that cannot run shell (P10) uses a `tm` MCP tool or a daemon method with the same checks. The writer takes the flock, validates, bumps `v`, replaces `state.json`, appends `log.jsonl` and `outbox.jsonl`, and fsyncs. Refused input exits 2 with files untouched. A Stop hook reminds the PM when `v` did not move in the turn (not built today: score section 3, item 1).

**Up-flow (deterministic).**
1. Source of truth: `outbox.jsonl` lines with per-session `seq`. Each line carries the full item revision (`id`, `rev`, `kind`, `status`, `esc`, content hash).
2. Trigger: the tm daemon watches the `dbatg/` directories it knows (it launches the sessions) and ingests every `seq` above `acked_seq`; a bus notification only makes it wake sooner. Polling every 600 s by the existing poller is the fallback.
3. Ingest into the Architect store: key `(code, id)`, apply only if `rev` is higher than stored. A repeated or reordered line changes nothing. A gap in `seq` is logged and triggers a resync from `state.json` (the snapshot is authoritative).
4. Ack: the ingest writes `acked_seq` and `epoch` to `acks.json`; the PM sees it in its next hook line. An item the PM sees as un-acked after N turns shows in the hook line as `UNACKED`.
5. What moves: D and A with `esc=architect` (full item); G (rank/status, for the goal map); T (state, as counts and open titles for the dashboard session row); B (the paragraph, into the dashboard Briefs section, with `doc` link). A, D answered by the Architect or Bob go back as a relay, then the PM writes `answer` and `outcome`.
6. Order: per session by `seq`; across sessions no ordering is promised or needed.

**Architect side.** The Architect keeps two things apart:
- Choose which sessions run: it maps the user's request and ranked goals (`local/goals.md`) to PM sessions, using each PM's goals and open tasks from the ingested copy, and proposes start, pace or park decisions (stop and park stay owner decisions, `ARCHITECT.md` "Authority and limits").
- Handle D/A: for each ingested item it recalls rulings, answers by relay at the confidence bar ("High confidence" in ARCHITECT.md; routine and already-ruled only), and passes the rest to the owner as a dashboard question with the PM's options and markers. Briefs are read as status and shown in the Briefs section; they do not wake it.
Everything else (hold, digest) reuses the D10 classes: decision and blocker wake; done wakes only when it frees a slot or closes a goal; progress waits for the digest (`local/briefs/2026-10-12-d10-message-intake-design.md` section 3).

**Rust versus instructions and hooks.**
- Rust (`trusty-architect` crate, #9171, and the tm daemon): schema types and JSON Schema, the writer verbs (`tm dbatg ...`), the lock and atomic write, id allocation, outbox/ack/ingest, the directory watcher, the registry of codes, the migration of `datg.py`, `pm_intake.py`, `pm-notify.sh`, `pm-digest.py`. Callable as daemon methods and MCP tools, as AGENTS.md "Prototype installation" requires.
- Instructions: the PM rules text (about 160 tokens) as a section in the PM instruction package, deployed by tm, replacing the per-project hook relay.
- Hooks: SessionStart (rules and goals), UserPromptSubmit (one status line), PreToolUse Agent (goal id check), Stop (write reminder). Generated and owned by tm, not by hand-edited `settings.local.json`. All fail open.
- Judgment (LLM): which session to run for a request; whether the Architect is confident in an answer; what the Brief says.

## 3. Adversarial review

Fix-bar class (ARCHITECT.md r-043, r-078): wrong behaviour, security or credential exposure, data loss, crash/hang/leak, pileup, broken gate. "Blocks" means it must be fixed before 2.0 ships the feature.

| # | Failure mode | What breaks | Blocks? | Mitigation |
|---|---|---|---|---|
| 1 | Two PMs in one checkout (five PMs share trusty-tools) | Today `datg/` is per project: one `state.json`, one `next` counter, one `v`. Two PMs would interleave goals and ids; the hook filter hides this by serving one PM only (`datg-hook.sh`). | Blocks (wrong behaviour) | Store per session: `dbatg/<session>/`. The code (`df`) is per session, not per repo. Registry rejects two live sessions with the same code. |
| 2 | Same PM in two worktrees, or a worktree removed | `.trusty-mpm/` is per checkout. A PM that works in a worktree writes to the wrong tree; removing the worktree deletes the store. The 28 KB things file exists only on disk. | Blocks (data loss) | Anchor the store to the session's launch directory (the base checkout path the daemon records), never the worktree cwd; the daemon resolves it. Outbox plus Architect copy make the loss bounded to un-acked items. Worktree removal is PM-run and already gated; add the store path to its check. |
| 3 | Crash mid-write | `state.json` replace is atomic, but `state.json` then `log.jsonl` are two files: a crash between them leaves state ahead of the log. `outbox.jsonl` the same. | Does not block | Write the outbox/log line first, then replace the snapshot (log ahead of state). On start, replay lines with `seq` above the snapshot's `v` to rebuild. The ingest treats the snapshot as authoritative and resyncs on a `seq` gap. |
| 4 | Lost migration | A queued message is dropped: `pm-notify` fails (logged, never fatal: `datg.py:355-363`), SendMessage lost, bus drops under pressure. The Architect never sees the escalation. The PM believes it flagged it. | Blocks (data loss) | Outbox plus `acked_seq`: nothing is lost until acked. UNACKED shows in the hook line and in the Architect's dashboard feed (count of un-acked items per session). |
| 5 | Duplicated migration and id collisions across PMs | Replays create duplicate dashboard items; two PMs choose the same code (`th`, `tg`, `ai`). Coded ids (`th-D03`) are only unique if codes are. | Blocks (wrong behaviour) | Idempotent ingest keyed `(code, id)` with `rev`; dedupe on `origin` as in the pilot. Code registry at init: `tm dbatg init` takes a code, daemon refuses a collision, stores `code -> session -> project` in `~/.trusty-mpm/`. Architect ids stay bare (`D06`), so no overlap. |
| 6 | PM drift: stops writing, or writes stale | Pilot evidence: things went silent 47 h (Bob's pause) then 5 idle notes; dogfood batches by design with an 8.5 h gap. The Architect then plans on stale goals. | Does not block, if detected | `v` age and last-turn time shown per session on the dashboard; Stop hook reminder; the Architect marks a PM `stale` when `v` has not moved while its pane shows work. Staleness is a signal, never a ruling. |
| 7 | Stale items inside the store | No prune verb: things holds 31 items and 50 tasks after 3 days; the 7-day drop has never run (score section 3, item 4). The file reaches 28 KB, 14 times the target, and costs about 7k tokens if read. | Blocks the token bar (waste) | `prune` verb run by the writer after each write; cap: done items older than 7 days leave `state.json` (kept in `log.jsonl`); hooks never read the file whole, only a derived line. |
| 8 | Schema evolution | `datg.py` strictness (`ID_RE`, `STATUS`) rejects a new kind; a Rust writer and a Python reader disagree; a PM on an older `tm` writes an older shape. | Does not block | `schema` int in every file; readers ignore unknown keys; the writer refuses a store with a newer `schema` than it knows (fail closed on write, open on read); a `tm dbatg migrate` verb that rewrites in place with a `.bak`. |
| 9 | Uncommitted data loss on machine move or disk loss | The store is machine-local by design and `.trusty-mpm/` is ignored. A new host starts empty; goals and open items vanish. | Does not block (accepted) | The Architect copy and the dashboard mirror (`local/owner-queue/`, committed in the Architect repo) are the backup; `tm dbatg restore --from-architect` re-seeds a PM from them. State this in the owner-facing text. |
| 10 | Multi-user and multi-host | Two owners, or a PM on another host (the pilot assumes one host and a shared filesystem). A file watcher cannot see another host. | Does not block 2.0 (single-host scope) | Declare 2.0 single-host, one owner. Cross-host uses the daemon method (`architect.notify`), not file reads. Record this as a stated limit. |
| 11 | Secret leakage into items | Item titles, answers and briefs are free text, copied to `log.jsonl`, `outbox.jsonl`, the dashboard and the Architect copy. A PM could paste a token or the owner's data. | Blocks (credential exposure) | The writer runs the existing secret-shape check (as `memory_remember` does) and refuses the write; rules text says locations only; the outbox never carries more than the item; `.trusty-mpm/` stays ignored. A refusal is logged without the value. |
| 12 | Architect restart or hang | Ingest state lives in the process: a restart loses its place; the poller wakes only on a new alert. | Does not block | All state is on disk: `acks.json`, `inbox/pm-messages.jsonl`, dashboard `origin` keys. Ingest is a pure function of those; a restart re-reads from `acked_seq`. |
| 13 | Context cost | things `state.json` 28 KB; hooks add 160 tokens once plus 30-80 per turn (design target); Architect reading every PM store costs more than the saving. | Does not block if capped | Hooks emit a derived line only; the Architect reads a digest (counts, esc items, unacked), not the files; briefs show one paragraph. Bar: hooks plus write <= 150 tokens per turn (score section 2). |
| 14 | Hook strength and Bash rule conflict | Dogfood rule P10 (no non-git Bash) forbids the per-turn call; the batch agent writes stale state; a block mode could stall work. | Blocks (broken gate) before block mode | Daemon method or MCP tool replaces the Bash call; block mode stays off until false blocks are 0 over two days (score section 5). |
| 15 | Writer rule not enforced | "PM is the only writer" rests on convention. An agent, a human, or the Architect can edit the file; the Architect already shares the machine. | Does not block | Writes go through one function that checks `session` against the caller; a `v` mismatch on read-modify-write detects an outside edit and logs `tamper`; the Architect never writes the PM store (it writes only `acks.json`, which is its own). |

## 4. Event bus versus files

What exists on main: `trusty-console` hosts the one event bus (owner ruling 2026-09-05; `origin/main:crates/trusty-console/src/event_bus/mod.rs`). UDS ingest of `HarnessEvent` frames; an in-memory ring of 8192; dedup by `EventId`; a day-rotated NDJSON durable log kept 7 days (`log/config.rs:34`, `DEFAULT_RETAIN_DAYS = 7`). Ingest is a non-blocking `try_send` into a channel of 4096 and drops are counted, not retried (`log/writer.rs:134`). Replay returns persisted events plus explicit `Gap` markers (`log/replay.rs`). The bus runs only while the console runs. The release map puts the 1.9.0 event-bus work (milestone 124, 62 open) before 2.0.0.

| Criterion | Event bus as the store | Files (per-PM `dbatg/`) |
|---|---|---|
| Durability | Weak: ring is volatile; `try_send` drops under load; log keeps 7 days only. Drops are acknowledged in the code. | Strong: fsynced local files with no expiry other than the PM's own prune. |
| Ordering | Console assigns `seq` globally; per-producer order depends on delivery. | Per-session `seq` in the file; no global order needed. |
| Replay | Built in, with Gap markers; limited to 7 days of log. | Replay from `log.jsonl` or `outbox.jsonl` after `acked_seq`; unbounded. |
| Observability | Good: SSE fan-out, counters, a dashboard consumer. | Needs a reader; `cat`, `jq`, `datg.py show`. |
| Daemon or console down | Producers cannot publish; events are lost or must be buffered by the producer (which is a file again). | Fully offline: the PM writes, the Architect ingests later. |
| Tooling | Rust-only client, UDS, `HarnessEvent` schema; a new event type is a code change in trusty-console. | Any language; `jq`, git-ignored plain JSON. |
| Portability | Single host, UDS. A second host needs a network bridge. | Single host as built; a daemon method can bridge hosts later. |
| Debugging | Frames are ephemeral; the 7-day log is the record. | The state is a file you can open, diff and fix by hand. |
| Cost | Needs the 1.9.0 bus finished and the console up; adds a dependency of 2.0 on 1.9.0 slice work. | Already built (Python prototype); port cost only. |
| Security | One more UDS surface carrying free text (secrets risk, failure 11). | Per-checkout files, owner-only mode. |
| Fit to a rule | Bob: "only the PM writes/updates after each turn" (trusty-tools palace). A bus event is a record of a change, not the PM's current plan. | Snapshot plus log is exactly "the PM's plan, rewritten after each turn". |

**Recommendation: hybrid, files as the source of truth, the bus as the doorbell.** The PM writes its files. The tm daemon, after a successful write and outbox append, emits one small `HarnessEvent` (`dbatg.changed`, session, `seq`) to the console bus. Subscribers (Architect ingest, dashboard) wake sooner. A lost event costs only latency, because the 600 s poll and `acked_seq` recover from the files. This also gives observability and a replay of "what changed when" for 7 days without making the bus the system of record.

Choose a pure-bus design only if the owner wants no per-checkout files at all; that moves the PM's plan into a lossy channel and puts the PM's loss of state on the console's uptime.
