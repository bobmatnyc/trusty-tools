# Research: standards and auth for shared engineering-project memory sync (trusty-memory)

Date read for every source: 2026-10-04. Scopes A and D. Primary sources only.
Method note: pages were read through a fetch tool that summarises the page. Quoted text and numbers come from that
output. Items marked VERIFY-RAW are single-summary claims worth a raw re-read before they go into a normative spec.
Codex items in the brainstorming note are proposals, not Bob rulings. The labels "(Codex proposal)" below keep that visible.

Constraints used to judge each source:
- C1 sync-only connector, recall always local, no synchronous remote fetch in recall.
- C2 interchangeable backends, mesh of several endpoints, stable originator ids, globally unique memory ids, client-mediated sync first, federation optional.
- C3 mandatory project identity on every memory; no personal/global profiles.
- C4 explicit update/supersede/retract/delete events; idempotent retries; offline divergence; no re-export loops of imported memories.

## 2. Provenance

Findings:
- PROV-O gives the vocabulary: Entity = memory revision; Agent = Person / SoftwareAgent; Activity = capture, edit, publish, replicate, consolidate. `wasAttributedTo` for author; `wasRevisionOf` for supersession; `wasInvalidatedBy` for retraction; `actedOnBehalfOf` for an agent acting for a human. https://www.w3.org/TR/prov-o/
- CloudEvents `source` + `id` is the duplicate key. https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md
- Matrix and Git show the other pattern: derive the id from a hash of the content so any replica can check it. https://spec.matrix.org/latest/rooms/v11/ ; https://git-scm.com/book/en/v2/Git-Internals-Git-Objects
- AT Protocol signs every commit with the account key, so a replica can verify origin without trusting the host. https://atproto.com/specs/repository
- ActivityPub copies the actor into `attributedTo` on Create and leaves origin verification to the implementation. https://www.w3.org/TR/activitypub/

Adapt (design inference, not vendor behaviour): separate five roles per revision, named after PROV: author, editor, publisher (the connector that pushed it), host (endpoint), replicator (a client that carried it). Only the author and editor are claims that need authentication; the others are transport facts. Each role is a stable id, never a login. The Codex note already asks for this separation (Codex proposal).

Loop prevention (C4): CloudEvents `source` + `id` identifies the event; add an `origin_endpoint`/`imported_from` marker so a connector never re-publishes a revision whose publisher is not itself unless policy allows. No source defines this rule; it is our own.

## 3. Identity

- Originator id: must not be a hostname (ActivityPub ties object ids to hosts, so a move changes ids). AT Protocol's DID is the cleanest counter-example: permanent id, mutable handle, handle verified both ways. https://atproto.com/specs/did
- Memory id: globally unique, assigned by the author side (UUID or content-derived). Revision id: unique per revision, ideally a hash of the canonical body (Git/Matrix pattern) so replicas can check integrity and dedupe.
- Endpoint id: separate from the above. Endpoint migration then changes only where a memory is hosted.
- Human principal (GitHub): numeric user `id`; `login` can change (GitHub Users API). https://docs.github.com/en/rest/users/users#get-a-user ; best practice "Always use the `id` of the user". https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app
- Provider-qualified form (design proposal, in line with the Codex note): `github:user:<id>`, `github:repo:<id>`, `github:org:<id>`. Keep `node_id` as an alias only: the docs say to persist it but give no stability promise. https://docs.github.com/en/graphql/guides/using-global-node-ids
- Workload identity: GitHub Actions OIDC `repository_id` / `repository_owner_id` claims, and `actor_id` for the human who triggered the run. https://docs.github.com/en/actions/reference/security/oidc A cloud agent should authenticate as a workload and be recorded as SoftwareAgent acting on behalf of a human (PROV `actedOnBehalfOf`; RFC 8693 `act`).

## 4. Conflicts

- CouchDB keeps all conflicting revisions in the `_rev` tree and picks a deterministic winner; clients must resolve. https://docs.couchdb.org/en/stable/replication/protocol.html Useful behaviour: conflicts are kept, not dropped.
- Matrix state resolution v2 is deterministic convergence over a DAG with power levels. https://spec.matrix.org/latest/rooms/v11/ Too heavy for per-memory text.
- Ink & Switch: users rarely hit conflicts with fine-grained CRDT merge; also notes history growth and weak tooling. https://www.inkandswitch.com/essay/local-first/
- None of these decide which engineering claim is true. Convergence only makes replicas agree.

Recommendation (adapt, our design): immutable revision events; each carries `parents` (the revision ids it supersedes). Two revisions with the same parent, or no common ancestor, form a recorded conflict set that is stored with evidence and surfaced until an explicit later revision supersedes both. Do not use "newest timestamp wins" as authority. Use RFC 9110 `If-Match` on the current revision id for publish/amend; 412 on mismatch. Who may issue authoritative corrections is a policy decision for Bob (open question).

## 5. Deletion and revocation

Deletion models seen:
- ActivityPub Delete + optional Tombstone, 404/410. https://www.w3.org/TR/activitypub/
- CouchDB tombstone revision with `deleted` flag in the changes feed. https://docs.couchdb.org/en/stable/replication/protocol.html
- Matrix redaction: keep skeleton, strip content. https://spec.matrix.org/latest/rooms/v11/
- AT Protocol: record removed with no tombstone in the tree; account-level status events `deleted`, `takendown`, `deactivated` propagate hop by hop and "intermediaries are responsible for timely respect". https://atproto.com/specs/sync
- MCP tasks: receivers may purge after TTL; says nothing about durable deletion. https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks

Recommendation (design):
1. Three distinct events: supersede (new revision, old kept), retract (mark invalid, content kept for audit), delete (content purged, a tombstone with ids, time, reason and issuer kept so offline replicas learn of it). AT Protocol's no-tombstone model fails for replicas that were offline; keep tombstones for a published retention window and state that window.
2. Redaction-style tombstone (Matrix): keep id, project id, author id, timestamps, hashes; drop body.
3. "Cannot unsee" cache policy (design, no source defines it): on access revocation, the connector stops pulling and stops pushing for that project/principal at once; it marks the local project partition `access_revoked` at the next successful reconciliation; policy then chooses retain / quarantine (excluded from recall, kept on disk) / purge. Default proposal: quarantine, then purge on operator action or after a configured age. Already-read content and already-exported copies cannot be recalled; the spec should say so plainly. For delete events, a replica MUST purge the body on receipt.
4. Revocation latency is bounded by token lifetime and reconciliation interval, not by webhooks (section 7). RFC 7009 notes that self-contained access tokens may stay valid after revocation. https://www.rfc-editor.org/rfc/rfc7009.html Use short-lived endpoint tokens plus an explicit revocation event stream (SSF/CAEP shaped). https://openid.net/specs/openid-sharedsignals-framework-1_0.html

## 6. Access scopes

- Project id is a mandatory envelope field and the authorization key (C3). No source gives this; every standard above is silent or opposite (Solid is pod-per-person; ActivityPub is audience-addressed).
- Access control sits at the endpoint, not in client tags: ActivityPub's own guidance is "should not trust client submitted content". https://www.w3.org/TR/activitypub/
- MCP's profile is the practical template: protected resource metadata, `resource` indicator, audience validation, no token passthrough, scope challenge with 403 `insufficient_scope`. https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization Define scopes such as `memory:read:<project>` and `memory:write:<project>` (design proposal).
- Mesh with several authorization servers: RFC 9700 4.4 REQUIRES mix-up defense; use RFC 9207 `iss` where the AS supports it, else a distinct redirect URI per AS. https://www.rfc-editor.org/rfc/rfc9700.html Plus RFC 8707 `resource` so a token for endpoint A cannot be replayed at B. https://www.rfc-editor.org/rfc/rfc8707.html
- MCP requires a client to refuse tokens not issued by the server's own AS and servers to refuse other tokens (token passthrough banned): the same rule applies between endpoints.

## 7. GitHub as authentication provider: recommendation and options (design only; nothing created)

Facts established from docs.github.com (read 2026-10-04):
- GitHub recommends GitHub Apps over OAuth apps for fine-grained permissions, installation scoping and short-lived tokens. https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps
- OAuth app `repo` scope covers all repos the user can reach; no per-repo restriction. https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps
- A user-to-server token has only permissions both user and app have; app must also be installed on the repo. Authorization is not installation. https://docs.github.com/en/apps/using-github-apps/authorizing-github-apps
- User token 8 h; refresh 6 months, single use. Installation token 1 h. https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens ; .../generating-an-installation-access-token-for-a-github-app
- Apps get implicit read on public resources when acting for a user. https://docs.github.com/en/apps/creating-github-apps/setting-up-a-github-app/choosing-permissions-for-a-github-app

Options:
- Option 1 (recommended starting point, design inference): GitHub App for sign-in and project binding. Human login by GitHub App user token (device flow for the headless connector, RFC 8628 shape). The memory endpoint treats GitHub only as an identity and repo-access oracle: it verifies the user token once, records `github:user:<id>`, then issues its OWN short-lived, audience-restricted, project-scoped token (RFC 8693 shaped, RFC 8707 `resource`). The GitHub token never travels to other endpoints and is never stored as a memory (matches the Codex note: "do not circulate personal GitHub tokens"). Revocation: short endpoint-token TTL plus reconciliation.
- Option 2: OAuth App login. Simpler, but `repo` scope is all-or-nothing and tokens are long-lived by default. Rejected: cannot be limited to bound projects. Only needed for enterprise-object access, which we do not need.
- Option 3: pure GitHub-derived tokens at every endpoint (the endpoint accepts GitHub tokens directly). Rejected: breaks audience restriction (MCP and RFC 9700 forbid token passthrough and recommend audience-bound tokens) and couples every backend to GitHub.
- Option 4 (later, for cloud agents): workload identity via Actions OIDC. Bind trust to `repository_id` and `repository_owner_id`. Record the agent as workload principal; keep `actor_id` as the human it acted for.
- Option 5 (optional hardening): installation access tokens used only by the endpoint's own backend to read repo membership/state (1 h tokens, repository-narrowed), never given to clients.

Repository access: necessary, not sufficient (design position, not a Bob ruling).
- Necessary: the user must be able to see the repo through the App-intersection rule, so a user without repo access never gets project memory access.
- Not sufficient: a public repo gives anyone read, and apps get implicit public read. An explicit project binding, created by a repo admin, must exist (`project_id` <-> `github:repo:<id>`), and the memory service holds its own per-project membership/role. A private-repo collaborator should not automatically see memory unless policy says so. Whether a public repo's memory may ever be world-readable is an open policy question.
- Binding is by numeric repo id. `full_name` changes on rename/transfer; GitHub returns 301 for moved repos, so slugs only resolve through redirects. The Actions OIDC docs say `repository_id` / `repository_owner_id` stay constant across renames and transfers (VERIFY-RAW), which is the best support found for repo id stability. https://docs.github.com/en/actions/reference/security/oidc

Org policy:
- SAML SSO: users need an active SSO session when authorizing a GitHub App; default session 24 h; apps must be re-authorized after enforcement. https://docs.github.com/en/authentication/authenticating-with-single-sign-on/about-authentication-with-single-sign-on Expect refresh failures when an SSO session lapses; the connector must degrade to "no sync" and keep local recall.
- OAuth app access restrictions are on by default for new orgs; GitHub Apps are governed by installation and owner approval. https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions Permission changes need installation-owner approval. https://docs.github.com/en/apps/creating-github-apps/setting-up-a-github-app/choosing-permissions-for-a-github-app
- Not found in docs read: what happens to existing user tokens when a user is removed from the IdP or the org. Treat as unknown; plan for reconciliation to detect it.

Revocation signals (what GitHub sends, and the gap):
- `installation` (deleted, suspend, unsuspend, new_permissions_accepted), `installation_repositories` (added, removed), `github_app_authorization` (revoked), `member`, `membership`, `organization`, `team`, `repository` (publicized, privatized, deleted, renamed, transferred, archived), `public`. https://docs.github.com/en/webhooks/webhook-events-and-payloads
- Webhooks are best effort: "GitHub does not automatically redeliver failed deliveries" and a delivery times out after 10 s. https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries
- Delivery has a GUID (`X-GitHub-Delivery`) for dedup and a signature header for authenticity.
- Org `member` / `membership` events need the Members permission, so some revocations (repo collaborator removal vs org removal) arrive on different events.

How revocation reaches asynchronous replicas (design proposal):
1. The endpoint translates GitHub webhooks into its own signed, idempotent `access.revoked` / `project.binding.changed` events in the change feed, per project, with a sequence number.
2. A reconciliation job per project (re-read `GET /installation/repositories`, collaborator permission, membership) repairs lost webhooks. Interval bounds the staleness; publish the bound.
3. The endpoint refuses push and pull as soon as it knows; its own tokens are short-lived (minutes to an hour; installation token is 1 h and user token 8 h as upper bounds from GitHub).
4. A replica learns on its next successful contact with ANY subscribed endpoint that carries the event, or on token failure (401/403 as in the CouchDB rule: do not retry rejected operations). Applying the cache policy of section 5 is local and offline-safe.
5. Offline replicas hold data until they reconnect: say so; no protocol can unsee.
6. Mix-up defense and `resource` audience binding stop a malicious endpoint from harvesting tokens during revocation races.

## 8. What each candidate does NOT supply (against our constraints)

- CloudEvents: no replication, no authz, no ordering.
- MCP 2025-11-25: no revision, replication, conflict, supersession or memory semantics; resource update notification is URI-only. Tasks are experimental. Authorization is optional and bases on an IETF draft (OAuth 2.1 draft-13).
- ActivityPub: open authentication; host-bound ids.
- CouchDB protocol: MVCC `_rev` trees; single logical database per replication.
- PROV-O: vocabulary only.
- Idempotency-Key draft: expired; header-level only.
- GitHub: no SSF/CAEP emission seen; webhooks lossy; IdP-removal effect on tokens undocumented in pages read.
