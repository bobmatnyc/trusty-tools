**The pinned-index FAIL, root-caused.** `.mcp.json` pins
`--index 2eb72dca-de08-481b-8dfa-22ab7f81b1f9`; that id is absent from
`list_indexes`, and bare `search`, `search_lexical`, and `index_status` all
return `404 unknown index`. This is not one session's bad luck — it is the
repo's documented **fail-open shape**: an operation fails, the failure is
downgraded to a log line, state advances anyway, and the only symptom
surfaces downstream, disconnected from the cause.

- **Mechanism, cited.** `crates/trusty-mpm/src/core/session_launch/mod.rs:654-658`
  calls `register_project_index`, a wrapper over
  `trusty_common::search_index::ensure_project_indexed`
  (`crates/trusty-common/src/search_index.rs:106-136`). That function's own
  doc comment states the contract: it *"ALWAYS returns the derived id … so
  the caller can still pin the id even if the daemon is unreachable."* It
  attempts `POST /indexes` on a 1–2s-capped background thread and swallows
  every failure — daemon down, non-2xx, timeout — at warn level. **It never
  verifies the index exists before returning `Some(id)`.** The launch site's
  own comment: *"Either way the session launches."*
- **Never created, not pruned.** The daemon's durable registry
  (`indexes.toml`, `roots.toml`) has no entry for `2eb72dca-…` at all — not
  even a stale one. The orphan reaper only removes entries whose root no
  longer exists, and this root still does. A daemon restart cannot explain
  it.
- **Blast radius — the number that matters:** registered-but-dead is 0 of 28.
  Of **75 live worktrees for this repo, only 4 carry a registered index —
  ~6% coverage, ~94% miss rate.** Systemic, not a one-off. Already recorded
  in [#5045](https://github.com/bobmatnyc/trusty-tools/issues/5045).

### (e) Memory UserPromptSubmit hook — NOT MET

Standard: **either relevant info or nothing at all.** Confirmed failing by
code inspection and a live probe against the same `recall()` the hook calls.

**Mechanism:** `UserPromptSubmit` → `trusty-memory prompt-context` → palace
drawer recall at a fixed `DEFAULT_TOP_K = 5`.

**No confidence floor exists anywhere in the chain.** `retrieve_l2` sorts
then `truncate(top_k)`; `recall()` merges L0 + L1 + L2, sorts, then
`truncate(top_k)` — no minimum score at any step. L1 "essential" drawers are
*always* included: when a query has no vector match they are rescored to
`importance × L1_NO_SIMILARITY_PENALTY` (0.15), a nonzero score that still
competes for a slot. No recency weighting exists in the scoring path.

**Live probe results:**

| Query | Result |
|---|---|
| "merge train PR merge on green" | 5 layer-2 hits, scores 0.437–0.563, genuinely on-topic |
| "BM25 index on a worktree" | 5 layer-2 hits, scores 0.397–0.470, genuinely on-topic |
| "what is the capital of France" | 5 drawers, **all layer-1, all scoring exactly 0.15** — the penalty floor. Content: computer-use gating, agent-tier decisions, a session-pause target. Zero relation to the query |
| "recipe for sourdough bread" | 5 drawers, scores 0.150–0.173, same shape. Zero relation |

Both zero-relevance prompts produced a full, correctly-formatted 5-drawer
"Relevant memories" block. Nothing in the rendering distinguishes a 0.15
non-match from a genuine 0.56 hit — the "or nothing at all" half of the
standard fails outright. This is also the cause of a previously reported
symptom (stale [#2949](https://github.com/bobmatnyc/trusty-tools/issues/2949)
drawers firing on a merge-queue prompt): same mechanism, not tag-weighted
recall — any L1 drawer survives to the final top-K whenever nothing beats its
floor score.

### Two criteria reverse Accepted ADRs

**(c) contradicts ADR-0018 (Accepted).** Its Decision names both crates
verbatim: *"Sibling daemons (search, memory, **analyze, review**, agents,
mpm) may each run their own loopback-only HTTP server… this is a supported
pattern, not a violation."* Undaemonizing removes services the ADR assumes
are always running, and leaves unanswered how trusty-review's GitHub webhook
and trusty-analyze's `/webhooks/github` reach an on-demand process. No
amending ADR is scoped.
[#5028](https://github.com/bobmatnyc/trusty-tools/issues/5028) carries no
spec reference.

**(d.2) reverses ADR-0014 (Accepted, 2026-07-14).** DOC-27 *is* the
unified-crate spec this criterion describes, and its own header records it
was **not adopted**, citing ADR-0014: each MCP surface ships as its own
in-workspace crate for one install/signing story per surface. Sharpening the
conflict: `crates/trusty-gworkspace/src/bin/gworkspace-mcp.rs` is being
actively built out in the separate-crates direction right now. Consolidating
is not filling a gap — it is walking back a decision with a recorded
rationale.

Both need an amending ADR **before** work starts, not a PR that silently
reverses them.

## Release mechanics

changelog directly from the `changelog.d/` fragments instead; do not hand-edit

version bump after this one.
