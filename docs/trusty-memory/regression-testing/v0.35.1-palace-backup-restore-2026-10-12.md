# trusty-memory 0.35.1 palace backup and restore: live-run record, 2026-10-12

**Date**: 2026-10-12
**Issue**: [#9282](https://github.com/bobmatnyc/trusty-tools/issues/9282) (PR 4 of 4)
**Procedure**: [backup-restore-upgrade.md](../backup-restore-upgrade.md), followed in order.

This is a functional record, not a performance baseline. It shows that the
backup, restore and re-embed procedure in the guide works against a real
daemon. An earlier run of the same checks used a debug binary built from the
PR 2 branch. This record replaces it with a run on a binary built from `main`.

## Step 5: stop the daemon, offline refusals, restore

Daemon stopped with the script's own path: `scripts/sandbox_memory_daemon.sh --stop <sandbox>`
printed `stopped pid 1372560`, exit 0. The socket file was gone. (The guide's
`trusty-memory stop` would act only on this sandbox here, because
`TRUSTY_DATA_DIR_OVERRIDE` was set; the script is the required path for a live
check.)

Offline refusals (daemon down, each exit 1, nothing written):

```
restore <backup> --palace other
  -> is a backup of palace live-9282, not other; nothing was written
restore <copy of backup whose manifest.json names palace "../evil">
  -> the manifest names palace "../evil", which is not a valid palace id; nothing was written
restore <backup> --palace ../evil
  -> is a backup of palace live-9282, not ../evil; nothing was written
restore <backup>, target palace dir still present
  -> restore target <root>/live-9282 is not empty; restore writes only into an empty palace root
```

Disaster simulation: the palace directory `<root>/live-9282` was moved out of the data root.
Then, against the empty target:

## Divergences between the guide and what was observed

Two divergences from the earlier run are fixed in the guide at `fe13f2e97c` and
no longer hold: the `trusty-memory stop` scope (the guide now states it stops
every daemon unless `TRUSTY_DATA_DIR_OVERRIDE` is set, and names `service start`
under launchd), and the first `dry_run=false` call reporting pre-repair counts
(the guide now says to call `palace_reembed` a second time). The rest hold on
the `main` build.

1. **Manifest `writer_version` is `0.63.1`**, the trusty-common crate version,
   while the binary is `0.35.1`. The guide does not mention the field. A reader
   comparing it to `--version` will see two different numbers.
2. **Recall before re-embed is not empty, and not ranked.** The guide says recall
   finds the restored drawers only after `palace_reembed`. Observed: recall
   returned three drawers from layer 1 at a flat score of 0.075. With top_k 3,
   the drawer that matches the query best was not among them. The guide's
   statement holds for ranked (layer 2) recall.
3. **Layer 2 scores fell by a constant 0.150 after restore and re-embed**
   (0.6393 to 0.4893, 0.6181 to 0.4681, 0.4504 to 0.3004), with identical text
   and ranking order. A fixed offset on every hit points to a term outside the
   backup, such as a recency or `last_used` boost. The record does not confirm
   the cause.
4. **Refusal order.** With the daemon up, `--palace other` is refused as a
   mismatch, but a plain restore of the same backup is refused for the serving
   daemon. The guide lists the refusals without an order.
5. **Backup files in this run.** The guide lists `identity.txt`, deletion journals and
   `drawer_counts.jsonl` lines as backup contents. A fresh palace has none of
   these, so the backup held three files. Consistent with the guide, but those
   three paths are untested by this run.
