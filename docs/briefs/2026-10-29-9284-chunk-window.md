# D83: chunk trusty-search to the embedder window (#9284)

Drafted 2026-10-29 for Bob. Supersedes the option list in `docs/briefs/9284-options-brief.md` (2026-10-29, tm-search-01); that brief had no chunk measurement.

## Decision asked

Which of options 1, 2 or 3 closes #9284? Option 4 is built (PR #10472, open) and is not a decision.

Today 29.9% of trusty-search chunks exceed the MiniLM 256-token window, and the embedder never sees 52.1% of all chunk tokens. The vector for a long chunk describes only its head. No option other than 1 and 2 changes that.

## What #10472 delivers

PR #10472 ("report the sidecar's embedder input window", Refs #9284, rung 5, 551 additions) delivers **option 4 only**.

- Sidecars add an optional `result.window` to success frames. The stdio client, the lazy adapter and the embed pass read it.
- On the default sidecar path `index_status.embed_window.window` becomes a number instead of `null`, and `truncated` starts counting there. Before the PR it counted nothing on that path (`crates/trusty-search/src/core/embed.rs:104-112`; #10185 body, "Known gap").
- It changes no chunk size, no chunker and no cap. Stored data and indexes are unchanged.
- It does not satisfy the acceptance criteria of #9284 on its own. Criterion 1 (chunks sized to the window) stays open. Criterion 2 (uses E7's window API) is met in part by the wire field.
- Live evidence of the gap: this index (`trusty-tools-4e2cf878`, 144,293 chunks, daemon 0.62.1) reports `embed_window: {window: null, truncated: 0, unmeasured: 0}`. That zero is blindness, not health.

Already merged: Q6, PR #10185 (1c38175320), the in-memory truncation counter and per-file WARN.

## The four options

The issue text (#9284 and comments 6345506766, 6346520273, 6347319759) lists the open questions but does not number options. The numbering below is the one in `docs/briefs/9284-options-brief.md`. Issue question Q1-Q5 map as: Q1 re-chunk vs full re-embed, Q2 sidecar window reporting, Q3 256 vs 128 candle cap, Q4 `TRUSTY_MAX_CHUNKS`, Q5 not named in the comments; Q6 is the counter.

1. Re-chunk to the window and re-embed every index.
2. Re-chunk new and changed files only; no forced migration.
3. Accept truncation, keep the counter, drop the gate (needs a D6 amendment).
4. Sidecar reports its window (PR #10472).

Notes on the table:

- A new splitter changes chunk text. M005 reuses vectors by text hash and re-embeds nothing (`migration/m005.rs:18-26`). A re-chunk to the window produces text no vector exists for, so option 1 must embed.
- The existing chunker already splits an AST chunk over 200 lines into 100-line windows at stride 50 and keeps an umbrella parent (`core/chunker/walk.rs:28-34, 440-488`). Only 47 of 5,306 sampled chunks reach 200 lines. The 200-line cap is not the cause; most over-window chunks are shorter than 200 lines. A fix must count tokens, not lines.
- Option 2 on a live index never finishes by itself. Files that rarely change keep truncated vectors. The `embed_window.truncated` counter (#10185, #10472) measures the remainder.

## M005 budget impact

**What M005 is.** M005 is a trusty-search schema migration (schema version 4 to 5), not a milestone. It is the corpus clear plus re-chunk that adds the end line to named chunk ids (#6581; `crates/trusty-search/src/core/migration/m005.rs`, `CURRENT_SCHEMA_VERSION` in `migration/mod.rs`).

**The budget.** One number. The owner ruling of 2026-09-05 on #6581 (comment 5546058592): "4. Zero." The ruling text reads "re-embed budget zero by design", with re-embed only "where the chunk text hash changed (expected none)". Code comments cite it: `core/indexer/mod.rs:455` and `migration/m005/tests.rs:94-112`, where a test fails if M005 embeds. I found no other number.

**How each option moves against it.**

| Option | Against the zero re-embed budget |
|---|---|
| 1 | Breaks it. Every chunk with changed text is re-embedded; the data below puts that at all chunks over the window and their new neighbours, up to the whole corpus. Needs an explicit amendment of the 2026-09-05 ruling. |
| 2 | Within it. No migration, no forced embed. Embedding happens only through the ordinary embed path for changed files. |
| 3 | Within it. |
| 4 | Within it. No chunk or vector changes. |

Limit of this finding: the ruling governs M005 and #6581. Whether it also binds a later migration is Bob's call; the 2026-10-22 comment on #9284 says full re-embed is "against the M005 no-re-embed budget" and treats it as binding. I found no GitHub milestone named M005 (`gh api repos/bobmatnyc/trusty-tools/milestones --paginate`, no title matched) and no ADR, spec or doc defining a budget beyond the #6581 ruling. Searched: `docs/`, `crates/trusty-search/` source and CLAUDE.md, milestones, issues mentioning "M005" (#6581, #6910, #8777, #8726, #9447, #9450, #9414, #8659, #8438, #9284).

## Data: chunks over 256 tokens

No prior measurement exists. #9284 comments, PR #10185, PR #10472 and `docs/briefs/` hold none. I measured.

**Method.**
- Corpus: the live trusty-search index of this repo (`trusty-tools-4e2cf878`, 144,293 chunks, 9,300 files: crates, docs, website). The chunks are the chunker's real output, read through `mcp__trusty-search__list_chunks`. No chunker was reimplemented.
- Sample: 5,306 unique chunks (3.7% of the index) from 25 windows of the chunk order (offsets every 12,000 chunks at two phases; 300 and 150 chunks per window). Each window is consecutive, so it is a cluster sample. A first run of 3,506 chunks gave 29.7% over and 53.7% lost; the second sample, with different offsets, gave 29.9% and 52.1%. The figures are stable to about two points.
- Tokenizer: `Qdrant/all-MiniLM-L6-v2-onnx` `tokenizer.json` from the fastembed cache, special tokens included, truncation off. Text counted is chunk `content`, which is what `core/indexer/ingest/embed.rs:430` sends to the embedder.
- Scripts and raw results: `/private/tmp/claude-502/-Users-masa-trusty-mpm-projects-bobmatnyc-trusty-tools/a578a90c-7388-4a6b-a117-ebd3855bfa15/scratchpad/d83/measure.py`, `.../d83/result.txt`, `.../d83/result2.txt`.
- Approximation: the daemon's own tokenizer and window were not queried (`window` reads null). 256 is the window the issue names. The sample is of this repo, which is Rust-heavy; it says nothing about prose or other-language indexes.

Projections from the sample (arithmetic, not measured on a rebuilt index):

- Splitting each over-window chunk into pieces of at most 254 body tokens adds 4,346 chunks (+82%). This is a lower bound: real splits at line or declaration boundaries leave pieces short of full. On this index that is about 144,293 to 262,000 chunks.
- Embedded tokens rise from about 800,000 to 1,670,000 in the sample, about 2.1x.
- A 128-token window would put 55.5% of chunks over and add 10,750 chunks (+203%). The Q3 choice of 256 vs 128 sets the cost.
- Chunk-count headroom on this index: `bm25_corpus_cap` 400,000; `chunks_dropped_by_cap` 0 now. The other indexes on this host (329,589 chunks total) would grow by a similar share.

## Recommendations

Cite check, 2026-10-29: the 503 string is in `crates/trusty-search/CLAUDE.md:124`, not the root `CLAUDE.md`. The `~83` figure is stated in the changelog as "cps" (chunks per second), `crates/trusty-search/CHANGELOG.md:3506-3516`. The MiniLM `config.json` cache file was not located in this session (unverified).

### A. Is 256 a hard limit? No. It is our setting.

- MiniLM `max_position_embeddings` = 512 (cached `config.json`, unverified: file not located this session). `max_seq_length` = 256 (`sentence_bert_config.json`, unverified: file not located this session).
- We pin `MINILM_MAX_SEQ_LENGTH = 256` and `FASTEMBED_MAX_LENGTH`. Sources: `crates/trusty-common/src/embedder/fast_embedder.rs:338` and `:350` (#9275).
- Candle caps at `MAX_SEQ_LEN` 128: `crates/trusty-common/src/embedder/candle_embedder.rs:54` and `:353-356`.
- fastembed 5.13.4 defaults to 512 (unverified: research note, source not re-read).
- The model was trained on 128-256-token inputs (model card, unverified). Positions 257-512 run but receive little training.
- No published degradation figure was found. A retrieval A/B on our chunks is needed to measure the loss.
- Raising MiniLM to 512 embeds more tokens. 13.2% of sampled chunks exceed 512 (`result.txt`, sample of 5,306). The "about 20% more tokens" figure is unverified. The per-long-chunk cost of "1-2x" is unverified.
- Current throughput is about 83 chunks/s (`crates/trusty-search/CHANGELOG.md:3506-3516`, batch 64 on M4 Max).
- Raising to 512 keeps the same vector space. The 29.9% of chunks over 256 still need re-embedding before they benefit.

### B. Model options

fastembed 5.13.4 variant support is verified in source per the research. Figures other than window and dimension are unverified.

| Model | Window | Dim | Params | MTEB retrieval nDCG@10 | Speed vs MiniLM | fastembed variant |
|---|---|---|---|---|---|---|
| all-MiniLM-L6-v2 (today) | 256 set / 512 max | 384 | 22M | ~41 (unverified) | 1x | `AllMiniLML6V2` |
| bge-small-en-v1.5 | 512 | 384 | 33M | ~51.7 (unverified) | ~2x slower (unverified) | `BGESmallENV15` |
| snowflake-arctic-embed-s | 512 | 384 | 33M | ~51.9 (unverified) | ~2x slower (unverified) | `SnowflakeArcticEmbedS` |
| snowflake-arctic-embed-m | 512 | 768 | 110M | ~54.9 (unverified) | ~5-6x slower (unverified) | `SnowflakeArcticEmbedM` |
| nomic-embed-text-v1.5 | 8192 | 768 (Matryoshka) | 137M | ~53 (unverified) | ~6x slower (unverified) | `NomicEmbedTextV15` |
| jina-v2-base-code | 8192 | 768 | 161M | n/a | ~6x slower (unverified) | `JinaEmbeddingsV2BaseCode` |

Any model change starts a new vector space, even at 384-d. Every index re-embeds in full.

### C. Backward-compatible path: a staged swap to bge-small-en-v1.5 or arctic-embed-s

- The new models are 384-d. The usearch dimension is fixed at index creation (`crates/trusty-search/src/core/store/usearch_store.rs:446`), so it does not change.
- Old MiniLM vectors cannot mix with new-model queries. They keep serving until a side index is complete and verified.
- Precedent: the off-to-the-side rebuild in `crates/trusty-search/src/core/store/usearch_requant.rs:263`.
- Not built yet:
  - A per-index model id. None exists; `FastEmbedder` is one global model.
  - Dual read plus an atomic swap.
  - An M006 migration (schema v5 is current, `crates/trusty-search/src/core/migration/mod.rs:64`).
  - Estimated rung 5, not sized.
- The #10194 degrade path (`crates/trusty-search/src/core/indexer/search/embed_degrade.rs:60-110`) can serve unpinned queries during the rebuild if a "re-embedding" flag triggers it. Pinned semantic queries receive `EmbedderUnavailable`.
- Other routes considered:
  - A linear query adapter into MiniLM space loses most of the gain (unverified).
  - Hybrid lexical plus vector is a bridge, not a fix.

### D. Re-embed time

Projections at about 83 chunks/s (`CHANGELOG.md:3506-3516`). All figures unverified; they are arithmetic on the chunk counts and the throughput.

| Scenario | This repo (144,293 chunks) | All 7 host indexes (329,589 chunks) |
|---|---|---|
| Small model (MiniLM-512, bge-small, arctic-s), same chunks | ~29 min | ~66 min |
| Small model plus token-aware re-chunk to the window (1.8-2.1x) | ~55 min | ~2 h |
| Base model (768-d, 5-6x slower) | ~2.5-3 h | ~6 h |

### E. #6581 amendment wording (proposed)

The current ruling is #6581 comment 5546058592 (2026-09-05, "re-embed budget zero"). The comment was not re-read on GitHub in this session (unverified). The ruling text is quoted in this brief at line 58.

Proposed text:

> A schema or model migration may re-embed an index only as an opt-in, per-index background job that keeps the existing vectors serving until the new index is verified, returns no `index_migration_in_progress` error to queries, and deletes old vectors only after verification. Forced, blocking full re-embeds remain out of budget.

### F. Ranked recommendation

1. **Recommended.** Merge #10472 (option 4, window visibility, already through review) now. Then take token-aware chunk splitting at the model window (option 2) for new and changed files. Then a staged, opt-in swap to bge-small-en-v1.5 (or arctic-embed-s) under the amended #6581 wording.
   - Cost: one rung-5 build for the per-index model id plus dual read.
   - Cost: about 1-2 h of background re-embed per host (unverified).
2. **Alternative, with no ruling change.** #10472 plus option 2, plus raising MiniLM to 512 for new embeddings only.
   - Low risk.
   - Small and unmeasured quality gain.
   - Old over-window chunks stay truncated until touched.
3. **Not recommended now.** A base-sized 768-d or 8192-window model (nomic, jina-code, arctic-m).
   - Requires a dimension change.
   - Embedding is 5-6x slower (unverified).
   - Re-embeds take about 6 h per host (unverified).
   - Gain over bge-small is a few retrieval points (unverified).
