Status: DESIGN ONLY. Nothing here was built, run or executed. Every verdict below is

## 0. Summary

- The #7266 file rule cuts every argv token at each byte a path cannot contain
  (`pm_guard_secret_words.rs:103` `is_path_byte`) and judges each fragment as a
  possible filename. Two things then misfire on inert text: `normalize_bracket_classes`
  (`pm_guard_secret_words.rs:125`) rewrites the regex class `[.]env` to the glob `?env`,
  which overlaps the `.env` entry (`pm_guard_bash/secret_file_copy.rs:452`
  `globs_overlap`, reached from `:419`); and a regex-escaped dot (`process\.env\.TZ`)
  is cut at the backslash into the fragment `.env`.
- The only release for printer text today is #8723 (`pm_guard_bash/bash_tokens.rs:405`
  `prose_write_indices`), and it applies only when the printer writes to a FILE and
  the command is one segment. A `printf` to the terminal, a multi-line printer script
  and a `cat <<'EOF'` to stdout get no release.
- Static trace result: of the 5 harmless fixtures, only #2 (regex literal) is refused
  today. #1, #3, #4, #5 trace as ALLOWED on main (see section 1). The issue itself says
  the before-state is unconfirmed, and the refusals reported on 1.11.1 may predate
  #10568/#10623/#10629. Section 4 handles the consequence for "red first".

## 3. Minimal design

Principle: do not parse any interpreter language and add no lexer. Add one POSITION
rule (like `pattern_argument_index`, `text_payload_indices`, `prose_write_indices`)
that marks inert operands of programs that only print, applied only after the
existing shlex tokenization succeeded. Everything else, and every failure, keeps the
existing deny scan.

### 3.1 Where a read operand differs from inert text

An operand is READ (screened as today) when its program can open it: `cat`, `sed`,
`head`, any other verb, an interpreter's program text (`node -e`, `python -c`, script
bodies via `pm_guard_secret_script`), and every redirect target. An operand is INERT
when all of the following hold (new module `pm_guard_secret_printed_text.rs`, logic
only, called from three places):

A. Closed printer text. The whole command (or script body) is made only of segments
   that are closed printer calls. A segment is closed when: `tokenize` succeeds; the
   program token itself is `printf` or `echo` (basename; no wrapper, no assignment
   prefix, no `xargs`); `printf` carries no `-v`; `runs_a_nested_command(segment)` is
   false (`bash_tokens.rs:457`: no unquoted `$`/backtick/`(`, quoting balanced); and no
   token contains `<` or `>` (no redirect, here-string, heredoc or process substitution).
   A text with any other segment (a reader, a keyword like `for`/`if`, `{`, `exec`, a
   terminator line) is not closed; the whole text falls back to today's scan.
   Why all segments, not "this one": a printer segment next to
   `exec > s.sh`, `{ printf ...; } > s.sh` or `| tee s.sh` can write a script that a
   later `bash s.sh` runs unseen (documented residual 1, `pm_guard_secret_script.rs:44-49`;
   `fc_a_script_written_and_run_in_one_command_refuses_10548`). Printer-only text has
   no writer and no reader, so nothing it prints can reach a file or a pipe.

B. Inert-shaped operand. Within a closed printer text, an operand token is inert when
   it contains at least one byte that `is_path_byte` rejects (whitespace, quote, `(`,
   `)`, `|`, `:`, `=`, `\`, `%`, `"`, ...). Such a token is prose, a regex, JSON or a
   format string, not a filename. A token made only of path bytes (`.env`,
   `./dummy-project/.env`, `.e*`, `tokens.length`) stays screened exactly as today.
   This keeps the standing ruling that `echo .env` and `printf '%s' .env` DENY
   (`denies_a_secret_read_beside_a_prose_write_8723`, `pm_guard_secret_read.rs:2098-2121`).
   Fixture 2's token (`(secret|credential|token|[.]env)`) and the escaped-dot
   variant are inert; fixture 3's token is inert; fixture 1's token is a plain word
   and stays screened (it matches no family).

C. Heredoc to stdout. A body is inert when `lone_inert_heredoc`
   (`pm_guard_bash/destructive_delete.rs:321`) accepts the command (single data body,
   quoted delimiter so it does not expand, operator line first with no `| ; & $ ``
   ( ) \`, nothing after the terminator) AND the operator line lexes to exactly
   `cat <<WORD` (no redirect, no operand). This extends `body_written_to_a_file`
   (`pm_guard_secret_handling.rs:175`), which refuses the same shape only because it
   requires a `>` target. Per-line conservatism, matching B: a body line that is
   exactly one path-byte token is still scanned (`.env` alone on a line denies);
   every other line is inert. The operator line and terminator keep their argv scan,
   so `cat ./dummy-project/.env <<'EOF'` and `cat > .env <<'EOF'` still deny.

D. Gate on the bytes the framing depends on. The release applies only if the command
   has no CR and no NUL, and no C0 control other than LF/TAB. (The earlier candidate's
   failures were a bare CR and a coding cookie; this gate removes the CR class for the
   shell framing. Non-ASCII prose is allowed: nothing here interprets identifiers.)

### 3.2 Wiring (three call sites, ~10 lines in `pm_guard_secret_read.rs`)

`pm_guard_secret_read.rs` sits at its line cap (comment at `pm_guard_secret_handling.rs:171`),
so the logic lives in the new module; measure with `scripts/check_line_cap.sh` before editing.

1. `:668-678`: compute `printed = closed_printer_text(&argv_text)` once; pass it to
   `secret_words_in_segment`, which at `:808` extends `text_payloads` with
   `inert_operand_indices(segment, &argv)` when `printed` (beside the existing
   `lone`-gated `prose_write_indices`; the two compose, neither is removed).
2. `:701-708`: next to `body_written_to_a_file(command)` add the stdout-`cat` check
   and the per-line filter for C.
3. Scripts need no new wiring: `judge_text` calls `evaluate_secret_file_read_command(body)`
   (`pm_guard_secret_script.rs:387`), so a shell body of printer lines gets A and B for free.
   Non-shell script bodies (Python/JS wrapped as heredocs by `inline_equivalent`) are NOT
   covered; they keep the full scan (fail closed). See Q3.

### 3.3 Parse failure fails closed

The release is a GRANT consulted only inside the `Ok(argv)` branch of
`secret_words_in_segment` and only after A-D hold. Any of these keeps the deny scan:
shlex returns `None` (`:798` raw-byte fallback), unbalanced quoting
(`runs_a_nested_command` is true), a segment that is not a printer, a redirect/`<`/`>`
token, a heredoc `data_bodies` does not claim (`split_heredoc_bodies` returns the text
unchanged), a CR/NUL, a computed or nested expansion (`$`, backtick, unquoted `(`).
This is the same asymmetry the module already documents (`pm_guard_secret_read.rs:27-30`:
lexing is only ever consulted to GRANT).

### 3.4 Why the earlier candidate's discrepancies do not recur

The branch `fix/10685-pm-guard-source-text` (HEAD fddeecdac4, unpushed) released `\.`
regex escapes by lexing Python (`pm_guard_secret_python_regex.rs`,
`pm_guard_secret_program_text.rs`). Review findings (issue comment 6616507236): round 0
CRITICAL denylist-style release and HIGH `-c` via pipe; round 1 CRITICAL non-ASCII
identifier (NFKC fold) and CRITICAL t-string prefixes; round 2 CRITICAL bare CR ends a
Python comment, CRITICAL `# coding: utf-7` hides a newline. All are "our lexer and the
interpreter disagree about where a comment or literal ends".

This design contains no interpreter lexer, no comment/literal/identifier/prefix/encoding
handling and no regex-escape cut. It decides from (1) program identity `printf`/`echo`/
`cat`, (2) the shlex tokenization the guard already trusts for every other GRANT, and
(3) a byte-shape test on a token. A printer/`cat` never evaluates its operand or body,
so there is no second language whose boundaries could disagree. Mapping:

| Earlier finding | Here |
|---|---|
| denylist-style release | allowlist: closed printer text only; everything else unchanged |
| `-c` program through a pipe | pipes/redirects/non-printer segments make the text not closed |
| NFKC identifier, t-string prefix | no identifier or string-prefix handling exists |
| bare CR comment end | gate D rejects CR/NUL/C0; no comment lexing |
| utf-7 coding cookie | no decoding of any body; only `cat`'s stdout |

Remaining shlex-vs-bash differences (documented class #10567): the design cannot mistake
a non-printer for a printer (program word compared literally), and `$`/backtick/`(`/`<`/`>`
tokens disable it, which covers ANSI-C `$'..'`, process substitution and heredoc forms.
Residual: a shell function/alias named `printf`/`echo` (same residual as #8723).

## 5. Risks

1. Policy change inside #7266 round 5 ("the FILE decides, not the verb"). Inert operands
   with spaces/quotes/regex bytes are now allowed under a printer-only text. The pinned
   `echo .env` / `printf '%s' .env` denies are kept by rule B.
2. Rule B is a shape heuristic. A prose operand that embeds a name (`echo 'cat .env'`)
   is allowed; it is safe only because rule A guarantees nothing can run or read the output.
   The guarantee is local to one tool call; state carried across calls (a prior `exec >`,
   an alias) is the standing residual.
3. Rule A is strict on purpose: `printf 'a>b'` loses the release (any `<`/`>`).
4. `shlex::split` is the tokenizer (known lexer-vs-bash gap, #10567). The design relies on
   it only to GRANT, and only for text made of literal `printf`/`echo` words.
5. Non-shell script bodies and interpreter program text keep their false positives
   (`re.compile(r"\.env$")`, `tokens.length` in JS, `token-hourly.jsonl` per #10570). They
   fail closed. A real grammar (tree-sitter-bash, #10567) is the Architect's call.
6. `pm_guard_secret_read.rs` is at its line cap; the new module must stay under 500 SLOC
   and the doc header (`:1-366`) needs a "#10685" paragraph and `Test:` pointers.

## 6. Open questions for the Architect

- Q1. Is printing a secret-shaped NAME to the transcript a read? This note keeps
  `echo .env` denied (rule B) because `denies_a_secret_read_beside_a_prose_write_8723`
  pins it, and #7833 releases a whole `cat > file` body but #8093 keeps `/dev/stdout`

  "closed printer text / stdout-`cat` body is wholly inert" and those pins flip.
- Q2. Closed printer text for scripts: accept the all-segments-are-printers rule (multi-line
  printer scripts pass), or only the one-segment `lone` case (smaller change; real
  multi-line scripts still refuse)?
- Q3. In scope: shell printers only, or also the Python/JS regex escape that motivated the
  dropped branch? This note says shell only; the branch stays unmerged.
- Q4. Gate D: reject only CR/NUL/C0 (this note), or the stricter printable-ASCII-plus-LF/TAB
  rule from the issue's "next design"? The strict rule would refuse em-dash prose such as
  Matt's ledger lines.
- Q5. Is the before-state run (five fixtures through `tm hook --pm-guard` on a main debug
  build) done before approval, given that four fixtures trace as already allowed? If they
