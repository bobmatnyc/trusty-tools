# D87: immutable releases block the D61 tag rewrite (df-G01)

Read-only research, 2026-11-03. Nothing was changed on GitHub. GET output: /tmp/d87_rel.tsv (release list), `gh api repos/bobmatnyc/trusty-tools/immutable-releases`.

## Facts from GET calls
- Setting: `{"enabled":true,"enforced_by_owner":false}`. The owner is a User account (`owner.type=User`), so no org or enterprise policy applies.
- All 384 releases report `immutable: true` (67 of 67 rewrite tags; 317 of 317 others). None is draft or prerelease.
- The 67 rewrite-tag releases: 67 have assets, 442 assets in total, 4,505,642,826 bytes (4.2 GiB). Repo-wide: 380 releases with assets, 2,256 assets, 22.6 GB.
- Latest release is `trusty-mpm-v1.11.1`; it IS among the 67.
- Sample asset: `trusty-mpm-v1.10.0` release ID 428663051, asset IDs 690961284/6, each with a `sha256:` digest. Homebrew formulas use `https://github.com/bobmatnyc/trusty-tools/releases/download/<tag>/<asset>` (scripts/test-data/homebrew/expected/trusty-mpm.rb:15,23).

## Answers
1. Disabling the setting does not unlock existing immutable releases; they stay immutable. Source: "Disabling immutability doesn't affect releases created while it was enabled" and they "remain immutable" (https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/). Corroborated in a user report (community discussion 178351, commonquail, 2025-11-14).
2. Release deletion: the docs say "If you delete the immutable release, you can delete the tag, but you cannot reuse the same tag name" (https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases). So the release can be deleted; INFERRED from that sentence, since the docs never state it as a separate rule. While the release exists, the tag cannot be deleted or moved; this holds with the setting on or off, because the lock belongs to the release (INFERRED from answer 1). Deleting the release frees the tag for deletion but not for reuse: recreating gives 422 "tag_name was used by an immutable release" (https://github.com/orgs/community/discussions/178351, commonquail, who disabled the setting first and still failed). The repo's own release.yml:1880-1910 records the same failure seen on trusty-installer-v0.5.0. `GET /immutable-releases` returns only `enabled` and `enforced_by_owner`; there is no per-release or per-tag endpoint. Per release, the `immutable` field is read-only data.
3. Delete+recreate on the same tag name is not possible, so the question of what carries over does not arise for the rewritten tag name. A burned name cannot be republished. What would be lost if it were done under a new tag name: release ID (new ID), asset IDs and `/releases/download/<tag>/<asset>` URLs (tag name changes, so every Homebrew formula URL and sha256 pointing at the old tag breaks, INFERRED from formula URL shape), "latest" status (trusty-mpm-v1.11.1, the current latest, is one of the 67, so "latest" would lapse or move), reactions (INFERRED; they attach to the release object), and the old release attestation (attestation covers tag, commit SHA and assets; docs: "cryptographically verifiable record of a release containing the release tag, commit SHA, and release assets"). Assets could be re-uploaded byte-identically only if you still hold the originals; the 442 assets total 4.2 GiB. Release notes are editable and can be copied (docs: "You can still edit the title and release notes"). The new release would get a fresh attestation bound to the new tag and commit.
4. Option 3 is not reversible. Deleting an immutable release burns its tag name for good (docs and community report above). Disabling the setting is itself reversible (re-enable it), but it relocks nothing and unlocks nothing: "Existing releases remain mutable unless you republish them" and only new releases are immutable, so re-enabling does not touch the old ones. Republishing an existing release in place is not possible for an immutable one (INFERRED).
5. No tag-only route exists. Tags cannot be deleted or moved while the release exists, and deleting the release burns the name. I found no GitHub doc or report of Support clearing a burned tag or unlocking an immutable release; one community report calls the state permanent. Whether Support can act is UNKNOWN, not documented either way. This repo's release.yml:1909-1910 concludes the only remedy is a new tag.

## Routes
Recommendation: neither route as stated; keep the 67 tags at their current (pre-rewrite) commits. Route 4 (Support) is the only one that could restore the exact tag names, but it is unconfirmed and cannot be done by us.
- Route 3, setting change: infeasible alone. Disabling the setting frees nothing (answer 1). Delete+recreate removes the 67 releases and burns the 67 tag names; the rewritten commits could then never carry those names. Loss: 442 assets and every download URL, Homebrew formula URL, attestation. Irreversible.
- Route 4, Support: feasibility unknown (no documented process). Loss: none if it succeeds. Reversibility: Support-side only. Ask for a one-time exemption to re-point 67 tags and keep the releases; expect a refusal given the supply-chain purpose of the feature.
- Alternative (INFERRED, not requested): rewrite everything except the 67 tags, which keep pointing at old commits that must remain reachable (GitHub keeps them while a tag references them). This needs a decision on whether history is still "rewritten" for those commits.
