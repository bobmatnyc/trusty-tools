## [0.1.0] — 2026-10-11

### Added

- A pure CommonMark → Slack canvas-markdown translator (`slack::canvas_markdown`, epic #3744 slice 2) and a new `slack_canvas_push` tool built on it — the adapter now exposes 22 live tools total. The translator losslessly round-trips bold/italic/strikethrough/inline-code/code-blocks, h1-h3, bulleted/ordered lists, dividers, quote blocks, task-list checkboxes (`- [ ]`/`- [x]`), and links; it downgrades h4-h6 to h3, strips HTML blocks/inline, and flattens footnotes to inline `[n]` markers plus a trailing "Footnotes" section — every downgrade is recorded as a warning string rather than applied silently. A table over Slack's documented 300-cell-per-table cap is a hard `TranslationError`, never a silent truncation. Slack's own mention syntax (`![](@U…)`, `![](#C…)`) passes through byte-for-byte with no invented name-to-id mapping. `slack_canvas_push` takes `canvas_id`, `markdown` (CommonMark), and `mode` (`"append"` | `"replace_all"`): `append` issues a single `insert_at_end` `canvases.edit` call; `replace_all` looks up the canvas's existing header-delimited sections via `canvases.sections.lookup` and issues **sequential** single-operation `canvases.edit` calls — one `delete` per existing section, then one final `insert_at_end` — since Slack's `changes` array accepts only one operation per call in practice; this is **not atomic**, and a canvas with no header-delimited sections (empty, or all-non-header content) falls back to appending with a warning, since `canvases.sections.lookup` cannot address non-header content for deletion. A transient `canvas_editing_locked` response is retried with a small bounded backoff. The tool response is `{ok, canvas_id, operations_applied, warnings}` — never Slack's raw envelope. Part of #3744
- Two new live Slack canvas tools (epic #3744 slice 1, `slack_canvas_*` namespace): `slack_canvas_create` (thin `canvases.create` wrapper — `title`/`channel_id` optional, `markdown` required, sent as `document_content: {type: "markdown", markdown}`; free-tier Slack teams must pass `channel_id` or Slack rejects with `free_teams_cannot_create_non_tabbed_canvases`) and `slack_canvas_lookup_sections` (thin `canvases.sections.lookup` wrapper — `canvas_id` required, optional `section_types`/`contains_text` criteria; Slack has no full-canvas-content-read API, so this returns section ids/anchors only, never document content). No markdown translation, push/pull, or sync state in this slice — that is slices 2-4. **Scope-grant caveat**: the app manifest declares `canvases:write`/`canvases:read`, but an installed app's live token may not carry newly-added scopes until the Slack app is reinstalled/re-authorized — expect `missing_scope` until then. Part of #3744
- Ten new live Slack tools for parity with the claude.ai Slack connector (epic #3611): `slack_create_canvas`, `slack_update_canvas`, `slack_read_canvas` (closes #3612); `slack_create_conversation`, `slack_list_channel_members` (closes #3613); `slack_get_reactions` (closes #3614); `slack_read_file` (closes #3615); `slack_schedule_message` (closes #3616); `slack_search_emojis`, `slack_search_users` (closes #3617) — the adapter now exposes 19 live tools total. `slack_read_canvas`/`slack_create_canvas`/`slack_update_canvas` require newly-added `canvases:read`/`canvases:write` OAuth scopes; see the README for the full per-tool scope table
- `slack_search_messages` gained an optional `scope` argument (`"public"` | `"public_and_private"`, default `"public_and_private"` — unchanged prior behaviour) that client-side-filters matches by channel privacy, in lieu of adding claude.ai's separate `slack_search_public`/`slack_search_public_and_private` tools (#3617)
- Cursor pagination for `slack_read_channel` and `slack_read_thread`: both tools now accept an opaque `cursor` (echo back a prior call's `next_cursor` to fetch the next page) plus `oldest`/`latest` ts time-window bounds, and both return `next_cursor`/`has_more`. Lets a caller walk a channel's or thread's full history across repeated calls instead of being capped at one page (closes #2996)
- New `policy` module: a channel-neutral, deny-by-default route table for gchat, Slack and Telegram, built from already-parsed data (no file loading yet). `ChannelPolicy::build` fails, never trims, on a name or (channel, recipient) shared by two routes (both entries named), an empty kind list, `review_notice` on a Slack or Telegram route, a malformed name or recipient (Slack takes a user ID, Telegram a positive chat id), and a rate limit that is zero, negative, out of range or looser than the default (a higher limit or a shorter window). `check_egress` allows only a route naming the exact recipient with the kind listed; `check_inbound` accepts only a routed sender's answer to exactly one open, unanswered question its route owns. `RateLimiter` keeps an in-memory sliding-window admit log per (channel, route) that admits at most `limit` messages in any `window_secs` (default 100 per 60 s), plus a separate window for unknown senders, on an injected monotonic clock; a clock reading that goes backwards is refused. gchat behaviour is unchanged (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- Google Chat inbound rate limit: each route admits at most 100 messages in any 60 s, and every sender with no route (no email, no route match, or a BOT sender) shares one more window of the same size. The take runs after the route lookup and before any learned space or ledger entry is touched, so a message over the limit resolves no question and learns no space. It is dropped and acknowledged once its `rate_limited` audit line is written; a failed audit write withholds the ack. One audit line is written per bucket per window, and later drops in that window are only counted. A backwards clock drops the message. `BatchReport` and `PollStatus` carry a `rate_limited` count, a limited drop never fails a poller tick, and `gchat-mcp doctor` prints a `limiter:` line. `RateLimiter::take_binding` takes a window by (channel, name) without a policy `Route`. Windows live in memory, so a restart resets them (#8454)
- `policy` gains the two-file route model, still without file I/O: `parse_host` strictly parses the `channels:` section of trusty-mpm's `config.yaml` (unknown keys denied at every level; per-channel `enabled`, `projects`, optional `kinds` ceiling and connection refs; a Slack or Telegram `credential_ref` must name a bot or app token), `parse_project_file` parses a project's `routes.toml` v1 (today's gchat schema, unchanged) or v2 (adds Slack and Telegram routes and per-route rate limits), and `merge` returns a `LoadReport` that always carries a policy, empty on a deny. A host-ceiling fault or a route overlap across two files denies every route; a broken or widening project file (a kind outside the ceiling, a rate limit looser than the host default, a gchat connection that differs from the host's) refuses only that file; a disabled channel or an unlisted project drops its routes with a named finding. A host-file error never repeats a value from the file: a parse error withholds what it quotes and a bad `projects` entry is named by its position, so a token typed into the wrong key never reaches an error or a finding. gchat behaviour is unchanged (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- `policy` gains the route loader's file I/O. `load_effective` reads trusty-mpm's `config.yaml` and each project listed for the consumer's channels, and returns a `LoadReport`; `PolicyLoader` reloads it when the content of a file, a repo's `HEAD` or its default-branch commit changes. A project's `routes.toml` takes effect only when the project dir is the top level of its own git repo, `HEAD` is on the default branch (`origin/HEAD`, else the one of `main`/`master` that exists; a detached `HEAD` is refused) and the bytes read equal the file at that branch's commit, read locally with no fetch; a git step that runs longer than 10 s is killed, with every process it started, and refused (`GitTimedOut`). A missing home directory, a missing or symlinked host file or host config directory, a host file whose real path is not `~/.trusty-tools/trusty-mpm/config.yaml` under the real home directory (such as a symlinked `~/.trusty-tools`, checked on every load and reload), a symlinked `projects` entry on any channel, or an oversized host file denies every route; the host and route files are opened without following a symlink or waiting on a FIFO; a symlinked, oversized, malformed, non-UTF-8 or unreviewed project file refuses only that project, each with a named reason. On reload a refused project keeps its last reviewed routes, marked `Stale`; a host fault denies all at once, including one in an entry the consumer does not serve; a reviewed narrowing applies at once; rate-limit windows are kept. A cross-file overlap now denies only the consumer whose channels it touches, a project listed for two channels no longer overlaps itself, and a project-file error no longer repeats a value from the file. gchat's own load gate is unchanged (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- `policy::load_effective_until(req, deadline)` loads the effective policy with git bounded by the caller's deadline. Each git step runs for at most the lesser of 10 s and the time left, and at the deadline its whole process group is killed. Every project not yet loaded is then refused as `GitTimedOut`, so none is reported effective, and the call returns soon after the deadline with no git process left running. `load_effective` is unchanged (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- New `gchat::api` module: a Google Chat API layer for a Chat app reached over Cloud Pub/Sub. `GchatClient` loads a service-account JSON key from a path (refused unless its mode is exactly 0600, before any network call), mints RS256 JWT-bearer access tokens for the `chat.bot` and `pubsub` scopes and caches them until five minutes before expiry, and pulls and acknowledges a Pub/Sub subscription. Posting a message and minting a token are crate-private, so a message reaches Chat only through `gchat::GchatChannel` and its route check. Pulled messages decode into typed Chat `MESSAGE` events; a malformed message is a per-message error that keeps its ackId. No `Debug`, `Display` or error text carries key material or a token. No binary yet (refs [#9448](https://github.com/bobmatnyc/trusty-tools/issues/9448))
- New `gchat-mcp` binary: a stdio MCP server for one project's Google Chat channel, with exactly four tools. `gchat_ask {to, text}` posts a question through a reviewed route and returns its id and message name; `gchat_notify_review {to, text, url}` posts a review notice with an https link and opens no question; `gchat_answer {question_id}` (read-only) returns `open`, or `answered` with only that question's answer text and time, and its description marks the answer as untrusted text from an external person; `gchat_doctor` (read-only) returns the doctor rows from the server's own channel plus the poller's last error. Every send goes through the route gate. A refused send is a tool error naming the refusal reason, never the message text, and a question that was posted but not recorded is its own `sent_not_recorded` error with the id, never retried. The project dir comes from `--project-dir`, else `TRUSTY_CHANNELS_PROJECT_DIR`, else the current directory. The server holds the project's single channel and is the only Pub/Sub poller (`--poll-interval-secs`, default 5); a second server on the same project exits with a message naming the held state lock, and a second server for the same Pub/Sub subscription from any project dir (a worktree or clone carrying the same `routes.toml`) exits before polling with a message naming the held per-user subscription lock under the user data dir (`trusty-channels/gchat-locks/`). A batch in the Workspace add-on event format is logged as an error naming that setting. A tick that leaves any pulled message unacknowledged because its answer or audit line could not be written counts as a poller failure: `gchat_doctor` shows the error and a `withheld` count, and its result fails while the poller is failing. stdout carries JSON-RPC only; logs go to stderr. `gchat-mcp doctor [--project-dir D] [--offline]` prints one row per route (recipient, kinds, load gate, key file and mode 0600, token mint unless `--offline`, DM space, open questions, subscription) and exits non-zero when the load or any check fails; while a running server holds the state lock, the state columns read "in use by a running gchat-mcp" and do not fail. Doctor releases the state lock before minting a token, so a server started meanwhile is not refused. The `state` module (ledger, spaces file, audit log) is now crate-private, so only a lock-holding channel writes it (refs [#9448](https://github.com/bobmatnyc/trusty-tools/issues/9448))
- New `gchat::GchatChannel`: per-project Google Chat routes, an egress gate and a question ledger. Routes load from `<project>/.trusty-channels/routes.toml` (schema version 1; an unknown key, an empty or unknown kind, a non-email recipient, or a duplicate name or recipient fails the load) and take effect only when the bytes read are exactly the version committed at `HEAD` (compared by git object id, so `--assume-unchanged`, `--skip-worktree` or a revert after the read cannot pass an uncommitted edit). A missing or refused file refuses every send. `send_question` and `send_review_notice` check the route and kind, a review notice's https URL, and the route's learned DM space before any token or Chat request; each refusal is written to `state/audit.jsonl` without the message text. A question carries a visible `[Q-<n>]` token and a thread key; `process_batch` and `poll_once` bind a reply from the route's recipient in its DM by thread name, else by token, resolve exactly that question once, learn a DM space at bootstrap, and drop and audit everything else, including any message from a `BOT` sender. An unparseable pulled message is audited before it is acknowledged, and a batch in the Workspace add-on event format is a distinct error. A question that was posted but whose ledger record could not be written returns `SendError::SentNotRecorded` with its id and message name, so the caller does not resend it. Only one `GchatChannel` may hold a state directory at a time; a second open returns `StateError::Locked`. A torn final ledger line from a crash mid-append is moved to `questions.jsonl.torn` and audit-logged instead of failing every later open. `health` reports one row per route (refs [#9448](https://github.com/bobmatnyc/trusty-tools/issues/9448))
- A `[[gchat.routes]]` entry in `routes.toml` accepts an optional `space = "spaces/<id>"`, validated at load with the same rule as a send target; several routes may share one space. A space route posts to that space with no learned DM binding, accepts a reply only from its recipient in that space with `spaceType` `SPACE` or `GROUP_CHAT`, and never reads or writes `state/gchat-spaces.json`. Refusals are audited as `direct_message_on_space_route`, `space_type_not_allowed`, `configured_space_mismatch` and `space_not_configured`. `gchat-mcp doctor` reports the route's space as `configured`. Routes without `space` behave as before (refs [#9448](https://github.com/bobmatnyc/trusty-tools/issues/9448))

### Fixed

- `slack_search_messages` no longer fails outright for any `count` between 101 and 1000. `count` was clamped against a 1000 ceiling documented as "the widest window Slack's `search.messages` accepts" — that claim was false: Slack documents a maximum `count` of 100 for this method ("the max `count` value is `100` and the max `page` value is `100`", <https://docs.slack.dev/reference/methods/search.messages>). Any larger value passed local validation, was forwarded verbatim, and was rejected live with `{"ok": false, "error": "invalid_arguments"}`, whose slug this adapter surfaces verbatim — so every affected search failed with an opaque error. The ceiling is now a distinct `MAX_SEARCH_COUNT = 100` (never shared with the `conversations.*` family's 999), an over-large `count` is reduced to 100 rather than rejected, and the `slack_search_messages` schema states the cap so callers see it up front. The defect survived review because the only test mounted a mock that answered `ok:true` regardless of `count`; the new tests assert on the outgoing request body
- `src/bin/slack-mcp.rs`'s doc-comment falsely claimed tool calls were "not-yet-implemented" and deferred per ADR-0014; corrected to reflect that all 19 tools are live (closes #3618)
- `slack_read_thread`'s `thread_ts` argument is now validated against Slack's `seconds.microseconds` ts shape before any network call, failing fast with an actionable message (naming the expected format) instead of forwarding a malformed value to Slack and surfacing an opaque `invalid_arguments` (#2996)
- `slack_read_channel`/`slack_read_thread`'s `oldest`/`latest` arguments get the same pre-network ts-shape validation as `thread_ts` — a malformed value (e.g. precision lost via a string→float→string round trip) now fails fast with an actionable error instead of being forwarded to Slack
- `conversations.history` / `conversations.replies` `limit` is now clamped to Slack's documented 999-message ceiling for that method family (previously shared the 1000 ceiling meant for `search.messages`)
- `slack_create_canvas` and `slack_canvas_create` given a `channel_id` now create
  a **channel** canvas via `conversations.canvases.create` instead of a
  standalone one via `canvases.create`. Both tools only ever called
  `canvases.create`, which creates a canvas owned by the acting identity — with a
  bot token, the bot owned it, and the human who asked for the document got it
  view-only and had to duplicate it to edit. Passing `channel_id` looked like it
  should already fix that, but on `canvases.create` that argument only tabs the
  canvas into the channel cosmetically and confers no edit rights. A channel
  canvas ties access to channel membership instead, so every member can edit it
  with no separate share step. Same bot token and same `canvases:write` scope —
  no new OAuth grant. Without `channel_id` both tools keep calling
  `canvases.create` unchanged. Both endpoints return the created id under the
  same top-level `canvas_id`, and one shaping function reads it, so the MCP
  response is identical either way. Slack rejects a second channel canvas for the
  same channel with `channel_canvas_already_exists` — edit the existing canvas
  rather than recreating it. Canvas-create errors now name the endpoint they came
  from (`<slug> (from <method>)`) (closes
  [#5155](https://github.com/bobmatnyc/trusty-tools/issues/5155))
- `slack_create_canvas` / `slack_canvas_create` against a channel that already
  has a channel canvas surfaced a bare `channel_canvas_already_exists` — the
  caller knew a canvas existed but not which one, a dead end for the normal
  usage pattern of repeat delivery to the same channel. The error now follows
  up with a `conversations.info` lookup and names the existing canvas's file
  id and the fix (`channel_canvas_already_exists (from
  conversations.canvases.create) — channel C1 already has canvas F456; use
  slack_canvas_push to update it`). The lookup is a courtesy, not a
  requirement: if it fails (missing `channels:read`/`groups:`/`im:`/`mpim:read`,
  a transport error, or no canvas on the response) the error degrades to the
  original bare slug rather than masking it (Refs
  [#5161](https://github.com/bobmatnyc/trusty-tools/issues/5161))
- Send Slack channel and user listing parameters as GET queries so Slack honors requested limits and channel types.

### Changed

- `slack_send_message_draft` was investigated but not implemented: Slack has no public API to create an editable message draft (`chat.postMessage` sends immediately, `chat.scheduleMessage` schedules a send — neither creates a draft). Deliberately excluded from `TOOL_NAMES` rather than stubbed (#3616)
- `slack::handlers` split from a single file into a `handlers/` module tree (`args`, `clean`, `messaging`, `read`, `lookup`, `search`) to stay under the workspace's 500-SLOC production-file cap; the public `dispatch` entry point is unchanged
- Credential resolution now imports from `trusty_common::credentials` instead of
  `trusty_common::inference::credentials`, which was deprecated in the same
  change (see [#4564](https://github.com/bobmatnyc/trusty-tools/issues/4564)).
  Import-path churn only — no behaviour, precedence, or credential surface
  changes in this crate.
- **MCP protocol primitives now come from the `trusty-mcp` crate instead of `trusty_common::mcp`** — imports move from `trusty_common::mcp::…` to `trusty_mcp::…`, and the `trusty-common/mcp` feature is replaced by a direct `trusty-mcp` dependency. No behaviour change: the types and functions are byte-identical, only their home crate moved (ADR-0040, [#5803](https://github.com/bobmatnyc/trusty-tools/issues/5803))
- The host `channels:` section names a Slack or Telegram credential by role: `connection: { bot_ref: slack, app_ref: slack-app }`. `bot_ref` is the token that posts and is required in any `connection`; `app_ref` is Slack's Socket Mode token and is optional. Both hold a trusty-common provider key, never a value. `credential_ref` is no longer read: a file that still names it is refused with an error naming `bot_ref` and `app_ref`. The host is also refused, denying every route, for a `bot_ref` naming `slack-app` or `slack-user`, an `app_ref` on Telegram, a `secret://` reference, or a value outside the slot's provider keys; the error never repeats the value. `HostChannel::credential_ref()` is replaced by `bot_ref()` and `app_ref()`, which return the provider key as `Option<&str>`, and `HostError::CredentialRef` now carries the key and a `RefFault` (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- `slack-mcp` sends with no route check, so it now builds only with the new non-default `unrouted-slack-mcp` feature: `cargo install trusty-channels --features unrouted-slack-mcp`. A plain `cargo install trusty-channels` installs `gchat-mcp` and `telegram-mcp` only. The `slack::server` and `slack::handlers` modules, which run any Slack tool with no route check, now also need `unrouted-slack-mcp`; `slack::api`, `slack::tools` and `slack::canvas_markdown` stay in the default build (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- The manifest carries the crates.io metadata for a first 0.1.x publish (rust-version, repository, readme, keywords, categories, homepage), and the package ships `src/`, `README.md` and `CHANGELOG.md` only. The README describes what 0.1.x does and does not enforce (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- gchat's `routes.toml` now takes effect only on the project's default branch: the project dir must be the top level of its own git repo, `HEAD` must be on the default branch (`origin/HEAD`, else the one of `main`/`master` that exists; both or neither is refused, and a detached `HEAD` is refused even at the default tip), and the bytes read must equal the file at that branch's commit. A refused load still refuses every send. `RouteError::NotCommitted` is replaced by `RouteError::Gate { path, reason }`, whose `reason` is the gate's typed `policy::GateError`; `gchat::load_gate::check_committed` now takes the project dir instead of the routes-file path, and `GateError::NoParent` is removed. The `gchat-mcp doctor` load row names the refusal reason and reads "committed on the default branch" when it passes (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
- gchat's `RouteError`, `SendError`, `StateError` and `InboundError` are now `#[non_exhaustive]`: a match outside the crate needs a wildcard arm (refs [#8454](https://github.com/bobmatnyc/trusty-tools/issues/8454))
