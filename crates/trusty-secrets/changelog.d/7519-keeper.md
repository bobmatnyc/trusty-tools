Added
- `cli-backends` feature: the `keeper` backend, `store::keeper::KeeperBackend`, which keeps values in Keeper through Keeper Commander, `keeper` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). Shims only and provisional: no test has run against a real Keeper account. One `login` record per key, titled with the key, value in `password`, in the Keeper folder at the vault's path. Writes are one `record-add` or `record-update` line on stdin (`keeper --batch-mode -`) with the value as `$BASE64:`; the value is never in argv or the environment. Every write is read back and every delete re-listed; anything else fails. A key is missing only when a successful listing does not show it. `rm` moves a record to Keeper's trash, which counts as deleted. A logged-out or unapproved `keeper` is `backend_locked`, and the error, and the `backend_locked` reply text, name the one-time device approval and persistent login. Capabilities are `READ | WRITE`.
- The machine config's `secrets.keeper` section or `secrets.default_backend: keeper` enables the backend; it opens only when the section names `program` and `config_path`, both absolute, the config file a regular 0600 file the account owns. `account` there is refused. As for 1Password, the server reads this only from the account's own machine config, and the delete sweep includes Keeper wherever it includes 1Password. `BackendId::KEEPER`, `MachineSecretsConfig::keeper`, and `secrets.doctor` lists `keeper` on a `cli-backends` build without running it.
- `CliCommand::hide`, which refuses a secret in argv and the environment overlay beside the stdin value.
