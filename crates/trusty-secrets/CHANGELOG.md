## [0.4.0] — 2026-10-30

### Added

- `secrets.ticket.mint`, `secrets.ticket.void` and `secrets.ticket.pending`: in-memory, one-use main-thread tickets with a 60 s TTL, bound to the session, prompt and tool-use ids, the redeemer's argv hash, the Architect `claude` (pid and start time), the op, the project and the key. A mint comes only from the installed `tm` running `tm hook --pm-guard` as a fresh direct child of the launched Architect's `claude`; every refusal is `ticket_refused`. Every void cause a hook sends (`pre_tool_use`, `subagent_pre_tool_use`, `stop`) removes the session's tickets. A restart drops every ticket (#10459).
- Audit records `secrets.ticket.mint`, `secrets.ticket.void` and `secrets.ticket.redeem` with a `ticket` object (event, ids, argv hash, `reason_arm`, `void_cause`). Mint and redeem records are written first; a void removes the ticket, then records it. No value and no argv (#10459).

### Changed

- `secrets.set` and a local one-key `secrets.copy` accept any key, including one the operator denied to agents, from a caller whose nearest Claude Code process is the `claude` that `tm fleet init` or `tm fleet relaunch` launched as the Architect, and only when that caller also redeems a main-thread ticket minted for that exact call. The launch-record check reads `~/.trusty-mpm/architect-launch/<pid>.architect` and requires its PID, start time and project directory to match the live process. A missing, unreadable, stale or mismatched record, or no matching ticket, keeps the agent rules (#10459).
- Minting is off in this release (`mint_enabled` defaults to `false` and nothing turns it on), so every caller under Claude Code keeps today's agent rules (#10459).
- Audit records of a write the Architect exemption allowed carry `architect: true`; when an agent caller is refused the exemption, the records name the failed check in `architect_refusal` (for example `start_time_mismatch` or `no_ticket`), with no pid, path or value. `architect: true` is not proof of identity: same-uid code can forge a record or a mint. `delete`, removing a deny and a sync-target copy stay operator-only (#10459).

## [0.3.0] — 2026-10-30

### Breaking

- `SecretBackend` replaces `agents_may_use`/`set_agents_may_use` with `holds_agent_controls`, `control_item` and `set_control_item` over `store::ControlItem`. A backend that stores no control item keeps the defaults, which refuse with `unsupported` (#10386).

### Added

- `secrets.copy` to `vercel` pushes the named keys into the `production` and `preview` environment variables of the Vercel project the account's own machine config maps the checkout to (`secrets.vercel.projects."<owner>/<repo>"`, DOC-74 S6, `cli-backends` builds). The value reaches `vercel env add` on stdin only; `development` is never pushed. No mapping for the checkout is `backend_not_enabled` before the CLI runs (Refs #9069).
- A Vercel push runs the pinned `secrets.vercel.program` in a fresh empty 0700 directory passed as `--cwd`, with `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` from the mapping, every inherited `VERCEL_*`, `NODE_*`, `NOW_*`, `npm_config_*`, `NPM_CONFIG_*`, `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` (either case), `SSL_CERT_FILE` and `SSL_CERT_DIR` variable removed with no setting to keep one, and `PATH` set to the program's directory plus `/usr/bin:/bin` (Refs #9069).
- A key is reported copied only when `vercel env ls` names it on both targets after the push. A failing target fails the key with a reason saying a target may have been written; an unrecognised listing is a failure; a variable that already existed is overwritten in place with `--force` but reported failed, since a listing cannot prove the value changed (Refs #9069).
- `secrets.doctor` lists a `vercel` row, judged without running the CLI. `BackendId::vercel`, `store::vercel`, `store::config::VercelSection`, `store::config::VercelProject`, the `vercel` field on `MachineSecretsConfig`, and `store::cli::WorkDir`; `store::open_sync_target_at` now takes the root each push's working directory is made under (Refs #9069).
- `secrets.set`, `secrets.delete` and `secrets.copy` refuse a caller with a Claude Code ancestor (`agent_use_refused`), directly or through the console bridge; an unreadable ancestry or a missing peer pid refuses (`grant_refused`). A copy to a sync target and removing a deny stay refused to agents; writing a deny is allowed (#10386).
- The file backend persists the per-key agent deny as a 0600 file under `<values root>/.agent-controls/`, so a host with no Keychain can deny a key to agents (#10386, subsumes #10090).
- Grant and resolve allow records for a caller under Claude Code carry `default_policy: true` (#10386).
- `server::serve_without_agent_callers` (`test-support` feature only): a server whose process table reports no Claude Code process, so a consumer's suite that stores keys through a real server passes the same in CI and in an agent session (#10386).

### Changed

- Agents use keys by default (#10386, the `.env.local` model): a key in the caller's project or owner vault is usable under a Claude Code parent through `secrets.grant`, `secrets.resolve` and `tm secrets exec` unless the operator denied it to agents. The stored backend item now means DENY (Keychain service `trusty-secrets.agents-deny`); `secrets.set_agents_may_use` keeps its wire shape, with `allowed: false` writing the deny and `allowed: true` removing it. `list` reports `agents_may_use: true` for a key with no deny.
- A vault written before #10386 is migrated once, recorded per vault. `store::DEFAULT_AGENT_DENY_MIGRATION` selects `OpenAll` (the default: no deny is written, every existing key becomes usable by agents) or `KeepClosed` (a key whose old "agents may use" flag was off gets a deny). The old flag items are removed. An unreadable marker or a failed deny lookup refuses.
- `agent_use_refused` now reads "this key is denied to agents, or the operation is operator-only".
- `mask_secret`, the one-time `secrets.set` confirmation, follows the owner ruling of 2026-10-28 (#10394): a value of 16 characters or more shows its first 4 and last 5 characters and its length, a value of 10 to 15 characters shows its last 5 and its length, and a shorter value shows only its length. It replaced a format that showed the first 8 characters. `MASK_HEAD_CHARS` is now 4. The console bridge uses the same function.
- An agent (a caller under Claude Code) may now `secrets.set` and locally `secrets.copy` a key in its project or owner scope that has no per-key deny; the deny is re-checked under the key index lock and a failed lookup refuses. Its `set` confirmation shows `[N chars]` only and its allow record carries `default_policy: true` (#10459, reverses #10386 Q2 for `set`).
- A per-key deny now refuses with the new wire kind `agent_key_denied` (-32085); `agent_use_refused` now means only an operator-only method (`delete`, removing a deny, a copy to a sync target) (#10459).

### Security

- `secrets.copy` carries a key's agent deny into the destination before the value; a denied key copied into a backend that cannot hold a deny (1Password, Keeper) fails with `unsupported` and nothing is written (#10386).
- `delete` removes a key's deny only after every backend's value delete succeeded, so a failed delete keeps the deny (#10386).
- A new key's `set` no longer clears a deny left from an earlier key of the same name; the deny stays (#10386).
- Every deny the store writes or removes on its own (the `KeepClosed` migration, `delete`, `copy`) has a write-ahead `secrets.set_agents_may_use` audit record with `agents_allowed`; a record that cannot be written leaves the deny unchanged (`audit_unavailable`). `SecretStore::with_deny_audit`, `store::DenyAudit` and `SecretsError::AuditUnavailable` carry it (#10386).

### Documentation

- Comments no longer cite the retired `src/assets/` paths or a private ruling label; they point at `content/` paths or an issue (#10096).

## [0.2.0] — 2026-10-26

### Breaking

- `trusty_secrets::server::backends_for` takes a third parameter, `sandbox: &SandboxEnv`, so the factory and the server agree on whose machine config enables a backend (#9793). Pass the same `SandboxEnv` the binary reads at start and gives `StartEnv`.

### Added

- `secrets.copy` to `github-actions` pushes the named keys into the checkout's origin repository's Actions secrets through `gh` (DOC-74 S6, `cli-backends` builds). The value reaches `gh` on stdin only. A key is reported copied only when GitHub's `updated_at` for the secret advanced after the push; a signed-out `gh` is `backend_locked` and nothing is pushed (Refs #9069).
- A push needs an explicit key list (`invalid_params` otherwise) and is refused with `agent_use_refused` for a caller with a Claude Code ancestor, or on the console bridge when the console judged its client an agent; each refusal and each key leaves an audit record naming the target (Refs #9069).
- The target opens only when the account's own machine config has a `secrets.github_actions:` section; `program` pins `gh` (otherwise the fixed system directories, never `PATH`) and `config_path` becomes `GH_CONFIG_DIR`. Every inherited `GH_*`, `GITHUB_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` variable is removed from `gh`'s environment (Refs #9069).
- `secrets.doctor` lists a `github-actions` row, judged without running `gh`. A sync target is never read back, never swept by `secrets.delete`, and never written to the names-only index (Refs #9069).
- `BackendId::GITHUB_ACTIONS`, `BackendId::VERCEL`, `BackendId::is_sync_target`, `store::sync_targets`, `store::open_sync_target_at`, `store::RemoteIdentity`, `ScopeSet::derive_with_identity`, `ProjectContext::identity`, `CliCommand::env_remove`, the `github_actions` field on `MachineSecretsConfig`, and the `github_actions` and `vercel` fields on `ProjectSecretsConfig` (Refs #9069).
- `trusty_secrets::granted`, the tier-3 client (DOC-74 S9): a process `tm secrets exec` started reads one granted value with `granted::resolve(&key)` or a `GrantedClient`. It reads the grant token from the fd named by `TRUSTY_SECRETS_TOKEN_FD` with `pread` at offset 0, which consumes nothing and changes nothing about the fd, refuses a socket whose directory is not 0700 or which is not 0600 and owned by this user, and waits 135 s, the server's resolve deadline plus its client margin. It resolves only: it never grants, revokes or starts a server. Every failure is a typed `GrantedError`; a refusal carries the wire code and kind. Unix only, blocking, under the existing `api` feature, which now also enables the already-optional `serde_json` and `libc` (Refs #9071).
- The token fd must be a read-only fd on an unlinked regular file holding exactly 64 lowercase hex digits, the form `tm secrets exec` hands down (DOC-74 S10). Every process that inherits it resolves, siblings included: both commands in `sh -c 'migrate && serve'`. A pipe, a named or writable file, a socket or a directory is `GrantedError::TokenUnreadable`; any other content is `GrantedError::InvalidToken` (Refs #9071, #9072).
- `trusty_secrets::api::TOKEN_FD_ENV`, the one name for the variable that carries the grant token's fd number (Refs #9071).
- Under `TRUSTY_SANDBOX=1`, with `TRUSTY_DATA_DIR_OVERRIDE` an existing absolute directory and `$HOME` not the account's home, the server reads `file` consent from `$HOME/.trusty-tools/trusty-common/config.yaml`, so a sandbox can write `file` values (Refs #9793).
- Under `TRUSTY_SANDBOX=1` the server opens only the `file` backend: the Keychain and the CLI backends answer `backend_not_enabled` for every operation, and an active sandbox's delete sweep skips them; with the flag set but `$HOME` the account's own, the delete is refused and the index row kept (Refs #9793).

### Security

- A tracked project file's `secrets.github_actions:` or `secrets.vercel:` section is refused with `tracked_cli_setting_refused`, so a repository cannot aim a push at a destination of its choosing; a sync target named as the project `secrets.backend` or the machine `secrets.default_backend` is refused with `config_invalid` (Refs #9069).

## [0.1.6] — 2026-10-11

### Breaking

- trusty-secrets 0.1.6 ships a public-API break under the internal numbering
  policy (owner ruling 2026-09-26); recorded in `scripts/semver-accepted-breaks/trusty-secrets-0.1.6.txt` (Refs #8699).

### Added

- The `trusty-secrets` server keeps the values `secrets.resolve` reads from 1Password or Keeper for up to the cache max age (600 s by default, counted in both wall time and awake time), so a second resolve of the same key does not run `op` or `keeper` again or ask for another unlock. Keychain and file values are never cached, and neither is a failed read. The grant, ancestry, agents-flag and audit checks still run on every call; a cache hit skips only the backend read, and a one-shot grant is spent by a hit as by a read. Entries are keyed by backend, vault and key, and `secrets.set`, `secrets.delete` and `secrets.copy` evict the key they write (#7520).
- A cached value is dropped when the backend's section of the account machine config changes, or when that file changes at all (by a stat fingerprint), so a value read under one 1Password or Keeper account never answers under another, even if the file is switched and switched back while a backend opens (#7520).
- A cached value is never served once it is 600 s old by wall time or by awake time, so neither a busy server nor a machine asleep with the server running keeps it longer, and a wall clock stepped back is a miss; the next resolve reads the backend again. `trusty-secrets serve --cache-max-age-secs N` sets the max age, and `TRUSTY_SECRETS_CACHE_MAX_AGE_SECS` can shorten it but not lengthen it. A value changed outside the server is seen once its entry reaches the max age or the server exits (#7520).
- A value the server's cache drops — by max age, by an eviction, by a settings change, by replacement, or when the server exits — is overwritten with zeros first, and the server sets its core-dump limit to 0 (soft and hard) at start, before it reads any secret; it exits 1 if it cannot (#7520).
- The `ancestry` feature: the process-ancestry walk (`ancestry::has_agent_ancestor`, `ProcessTable`, `OsProcessTable`, `StartTime`) with std, `thiserror` and libc only, so trusty-console judges its HTTP client with the same walk the socket server uses and links no store, keychain, server or trusty-common. `server` includes it, and `server::ancestry` still resolves to it (#9066).
- `secrets.bridge.list`, `secrets.bridge.set`, `secrets.bridge.delete`, `secrets.bridge.copy` and `secrets.bridge.set_agents_may_use`: the console bridge's entries. Each carries the console's verdict on its HTTP client in a `bridge` field (`agent_parent` and a `source` of `mapped`, `unmappable` or `unreadable`) and gets the direct method's verdict, error text and deadline. Every bridge call is audited: it leaves the direct method's records, and an allowed `secrets.bridge.list`, which leaves none when direct, leaves one allow record; an unwritable audit log refuses every allowed bridge call, list included, with `audit_unavailable`. Like the direct socket, the bridge writes no record and refuses nothing for the audit when the machine config sets `secrets.audit: false`. The server takes the verdict only from a peer running the `trusty-console` executable outside any Claude Code process tree; any other peer is refused with the new `bridge_refused` kind (-32084), and a malformed assertion with `invalid_params`, each with a deny record naming the vault and key the params carried (#9066).
- Audit records of a bridge call carry `source` (`mapped`, `unmappable`, `unreadable` or `malformed`) and the asserted `agent_parent`; a direct call's record is unchanged.
- `api::mask_secret`, `api::BridgeAssertion` and `api::BridgeSource`, so a caller that links only `api` can mask a value and build the assertion. `store::mask_secret` still resolves.
- `ProcessTable::executable`, a provided method that reads the executable a pid runs; the default refuses.
- `secrets.bridge.scopes`: the console bridge's form of `secrets.scopes`, for the Secrets page's scope picker. It is refused with `bridge_refused` from any peer that is not the verified console, answers what a direct `secrets.scopes` answers (project and owner scopes only), and, like every bridge call, leaves one `secrets.scopes` audit record and is refused with `audit_unavailable` when the record cannot be written. A direct `secrets.scopes` still leaves no record (#9067).
- `secrets.bridge.backends`: the console bridge's backend list for the Secrets page's copy dialog. It answers `secrets.doctor`'s rows for the named project as id and availability only, plus the backend the project's writes use (`BackendsResponse`, `BackendChoice`); no path, reason or detail. It is refused with `bridge_refused` from any peer that is not the verified console, leaves one `secrets.backends` audit record per call, and is refused with `audit_unavailable` when that record cannot be written. It has no direct method (#9067).

### Changed

- A bridge assertion with `source: unmappable` must now carry `agent_parent: true`, and `BridgeAssertion::unmappable()` builds it that way: a client the console cannot map is treated as an agent, so `secrets.bridge.set_agents_may_use` ON is `agent_use_refused` and OFF is allowed. `unmappable` with `agent_parent: false` is now `invalid_params` (#9067).

## [0.1.5] — 2026-10-10

### Added

- `GrantRegistry::check_scoped`, which runs `authorize_scoped`'s checks without spending a one-shot grant, and `GrantRegistry::spend`, which spends one use after the caller's own checks passed (#9621).

### Fixed

- A one-shot exec grant is spent only after every `secrets.resolve` check passed and the allow record was written. An unreadable caller ancestry, an audit failure or a backend failure no longer uses it up (#9621).
- Grants whose child process has exited are dropped at the next mint or idle check. They no longer keep the server from its idle exit or hold one of the 1024 grant slots, and their tokens are refused (#9621).
- An npm-installed Claude Code (`node .../@anthropic-ai/claude-code/cli.js`) counts as an agent ancestor. A `node` process is judged on argv[0] and its script operand only, read from `/proc/<pid>/cmdline` on Linux and `KERN_PROCARGS2` on macOS: a `claude-code` path segment, or a basename exactly `claude`, matches. The argument after a node option the matcher does not know is judged as a possible script, and the search for the script goes on past it, so `node --env-file .env /usr/local/bin/claude` counts. A plain `node` does not count, even when a later argument mentions Claude (`node lint.js CLAUDE.md`). A `node` whose argv cannot be read refuses (#9621).
- `secrets.set_agents_may_use` writes its allow record under the key's index lock, after the row check. Records and flag changes for one key land in the same order, and an unindexed key leaves one `not_found` deny with no allow record (#9621).
- The `audit_unavailable` text no longer says the requested change "may already have been applied"; it says a change was made only if the record failed after the backend call (#9621).
- `secrets.resolve` writes its allow audit record before it opens or reads the backend. When the audit log cannot be opened or written, the call answers `audit_unavailable` and reads nothing, so no value is read without a record. A failure after the record (the agents flag, the backend, a spent grant) adds a deny record with its kind (#9621).

## [0.1.4] — 2026-10-10

### Added

- `secrets.set_agents_may_use` on the trusty-secrets socket (DOC-74 §15.8, S8 slice 3, #9070). It takes `project`, `vault`, `key` and `allowed`, and answers the vault, the key and the flag as set. A caller whose own ancestry, read from its socket peer pid, has a Claude Code process may turn the flag off but not on (`agent_use_refused`, -32065); an unreadable ancestry or a missing peer pid refuses with `grant_refused`. The allow audit record is written before the backend call: if the log cannot be opened or the record appended, the flag is not changed (`audit_unavailable`), and a backend failure after it adds a second, deny record with its kind.
- The `api` types `SetAgentsMayUseRequest` and `SetAgentsMayUseResponse` and the method name `method::SET_AGENTS_MAY_USE`.
- Audit: `AuditMethod::SetAgentsMayUse`, and two optional record fields: `agents_allowed`, the flag value a flag-set call asked for, and `agent_parent`, whether the caller had a Claude Code ancestor, on `grant`, `resolve` and flag-set records once judged. Older records decode with both absent.
- `server::grant`: an in-memory exec-grant registry for `secrets.resolve` (DOC-74 §15.8, S8 slice 1, #9070). `GrantRegistry` mints a 256-bit token from the OS CSPRNG and keeps only its SHA-256, compared in constant time. A grant holds its allowed keys, the child pid and that process's start time, an expiry checked on every use and capped at a max TTL, and an optional one-shot flag. A wrong, unknown or expired token, a key outside the grant, a caller outside the child's process tree and a reused child pid all return the one `GrantError::Refused`. A poisoned lock, an unreadable process table or start time, and a clock error each deny with their own variant. `has_unexpired` reports whether any grant is still live.
- `server::ancestry`: `ProcessTable` (Linux `/proc`, macOS `proc_pidinfo`; any other target refuses every read) and `is_self_or_descendant`, which compares the root's recorded start time so a reused pid is refused.
- `secrets.grant`, `secrets.resolve` and `secrets.revoke` on the trusty-secrets socket (DOC-74 §15.8, S8 slice 2, #9070). `secrets.grant` takes `project`, `child_pid`, `keys`, `ttl_secs` and an optional `one_shot`, mints the grant server-side and returns its token. `secrets.resolve` takes a token and one key and is the only method that returns a value: it answers only when the token is live, the key is in the grant, and the socket peer's pid (from the kernel, never the request) is the child or a descendant. Every such refusal is the one new error kind `grant_refused` (-32082) and carries no value. A full registry is `grant_limit_reached` (-32083). `secrets.revoke` removes a grant even when the audit log is unwritable. None of the three has a console route or an MCP tool.
- A registrar with a Claude Code ancestor, judged server-side from its own peer pid's ancestry (`has_agent_ancestor`, `ProcessTable::is_agent`), may grant only keys flagged "agents may use"; any other key is refused with `agent_use_refused` before anything is minted. `secrets.resolve` checks the flag again before each read of such a grant.
- Audit: `AuditMethod::{Grant, Resolve, Revoke}`. `grant` writes one record per granted key or one deny, `resolve` one record per call, allow or deny, `revoke` one per call. An allowed grant or resolve whose record cannot be written returns no token or value. Every audit record, for every method, now carries the caller's pid.
- The `api` types `ExecGrantRequest`, `ExecGrantResponse`, `ResolveRequest`, `ResolveResponse`, `RevokeRequest` and `RevokeResponse`, whose `Debug` redacts tokens and values, and the method names `method::GRANT`, `method::RESOLVE` and `method::REVOKE`.
- The server's 60 s idle exit waits while any exec grant is unexpired, and exits at most one idle window after the last one expires or is revoked.
- On macOS, the ancestry walk reads each parent pid and process name with `PROC_PIDT_SHORTBSDINFO`, which answers across uids, so a grant from a shell under the root-owned `login` (Terminal, iTerm2) or `sshd` reads its whole parent chain. Only the granted child's start time still uses `PROC_PIDTBSDINFO`.

### Changed

- `secrets.resolve` also judges the resolving caller's own ancestry: a caller with a Claude Code ancestor reads only keys flagged "agents may use", even from a grant a non-agent registered for it (#9070). An unreadable ancestry refuses with `grant_refused`.
- `ProcessTable::is_agent` has a default body that answers `ProcessError::Unreadable`, so a process table that does not implement it fails closed in `has_agent_ancestor` instead of failing to compile (#9070).

## [0.1.3] — 2026-10-10

### Fixed

- Every Keychain call (read, write, delete, and the "agents may use" flag item read by `list`) now has a time limit, `KEYCHAIN_CALL_TIMEOUT` (60 s), cut to a server request's deadline when that is sooner ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). A call blocked on an unanswered access prompt no longer holds its caller: past the limit it fails with the new `SecretsError::Timeout`, which names the backend, the operation, the vault and the key, and on the wire with the new kind `backend_timeout` (-32081). A timeout is never a miss, an empty value or a success, and no call starts once the request deadline has passed.
- The timed-out call is abandoned, not stopped: its thread stays blocked until the OS prompt ends, and a write it started may still land then. Until that thread ends, every later call on the same Keychain item (a key's value, or its flag item) fails at once with `Timeout` and is never started, so the late write cannot land after a newer one; calls on other items are unaffected. Both error texts say so.
- A 1Password or Keeper CLI call still running when the server exits (idle, `SIGTERM` after its drain, or a panic) no longer outlives the server process ([#9572](https://github.com/bobmatnyc/trusty-tools/issues/9572)). The server now raises a cancel flag when its serve loop ends; the call kills and reaps the CLI's whole process group within one 10 ms poll, and no new CLI call starts after that. Before, the call's thread was abandoned at exit and the CLI, with any child it started, kept running under pid 1 until its own timeout (60 s by default). A write the CLI had started may or may not land.
- A server request whose backend call never returns (for example the file backend on a hung mount) now answers `deadline_exceeded` (-32079) 2 s after its deadline instead of never answering ([#9572](https://github.com/bobmatnyc/trusty-tools/issues/9572)). The stuck call cannot be cancelled: its thread keeps running until the call returns, and a write it started may still land then.
- Each server process runs at most 64 method calls at once. A call holds its slot until its thread finishes, so calls that never return hold at most 64 threads per server process; a request that waits for a slot past its deadline, or gets one only after its deadline, answers `deadline_exceeded` and runs nothing, never a success or an empty result.
- The server process exits within 2 s (`EXIT_GRACE`) of an idle exit or a signal, however many backend calls are stuck. Calls still running then are abandoned, so a write such a call started may or may not land. Before, the exit waited with no limit for every stuck call, leaving one hung server process per idle cycle.

### Security

- The "agents may use" flag is held by the backend as its own item per key, no longer by the 0600 names-only index file, which any same-uid process could edit to make `resolve_reference(.., agent_parent = true)` return a value ([#9070](https://github.com/bobmatnyc/trusty-tools/issues/9070)). On the Keychain the flag is the item service `trusty-secrets.agents`, account `<vault>/<key>`, present when on; `MemoryBackend` keeps it in memory. A missing item reads off, and a failed lookup is an error, never on.
- `SecretBackend` gains `agents_may_use` and `set_agents_may_use`, with defaults that read every key off and refuse to turn one on; the file, 1Password and Keeper backends use the defaults, so no key on them can be flagged.
- `SecretStore::list`, `SecretStore::set_agents_may_use` and the agent gate take the flag from the backend, and `secrets.list` reads it from the project's backend; when that backend does not open, `secrets.list` still answers from the index with every flag off. A delete removes the flag item from every swept backend, and a new key's stale flag item is removed before its value is written; a removal that fails fails the delete (the index row stays) or the set (no value is stored).
- The index field `agents_may_use` still loads from an existing file but is ignored and no longer written, so every flag set before this release reads off; nothing shipped set one. `NamesIndex::set_agents_may_use` is deprecated: it refuses `true` and never changes the file.

## [0.1.2] — 2026-10-08

### Added

- `cli-backends` feature: `store::cli`, a blocking runner for CLI-backed backends that sends a value only on stdin, refuses a command line carrying the value or an overlay token, keeps all child output out of errors, classifies stderr into missing, locked or other, kills the child's process group on timeout, and caps each stream at 1 MiB; plus a 0600 `TemplateFile` guard and a startup sweep for its leftovers ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `SecretsError::CliNotInstalled` and `SecretsError::BackendLocked`, with wire kinds `cli_not_installed` and `backend_locked` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `cli-backends` feature: the `keeper` backend, `store::keeper::KeeperBackend`, which keeps values in Keeper through Keeper Commander, `keeper` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). Shims only and provisional: no test has run against a real Keeper account. One `login` record per key, titled with the key, value in `password`, in the Keeper folder at the vault's path. Writes are one `record-add` or `record-update` line on stdin (`keeper --batch-mode -`) with the value as `$BASE64:`; the value is never in argv or the environment. Every write is read back and every delete re-listed; anything else fails. A key is missing only when a successful listing does not show it. Nothing in a vault is read, written or removed until listings from the root down show exactly one folder of exactly each segment's name, because `ls` of a missing path may exit 0 with the parent's entries. `rm` moves a record to Keeper's trash, which counts as deleted. A logged-out or unapproved `keeper` is `backend_locked`, and the error, and the `backend_locked` reply text, name the one-time device approval and persistent login. Capabilities are `READ | WRITE`.
- The machine config's `secrets.keeper` section or `secrets.default_backend: keeper` enables the backend; it opens only when the section names `program` and `config_path`, both absolute, the config file a regular 0600 file the account owns. `account` there is refused. As for 1Password, the server reads this only from the account's own machine config, and the delete sweep includes Keeper wherever it includes 1Password. `BackendId::KEEPER`, `MachineSecretsConfig::keeper`, and `secrets.doctor` lists `keeper` on a `cli-backends` build without running it.
- `CliCommand::hide`, which refuses a secret in argv and the environment overlay beside the stdin value.
- `cli-backends` feature: the `onepassword` backend, `store::onepassword::OnePasswordBackend`, which keeps values in 1Password through `op` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). It finds a key's item with `op item list --vault <vault> --format json`, then reads with `op read`, creates with `op item create -` (the JSON item template, value inside, on stdin), edits with `op item edit <id> --template <file>` (a 0600 file removed after the call), and deletes with `op item delete`. The key never reaches argv. A missing item or vault is a miss; a locked or signed-out `op` is `backend_locked`. Capabilities are `READ | WRITE`.
- The machine config's `secrets.onepassword` section (`account`, `config_path`, or `{}`) or `secrets.default_backend: onepassword` enables the backend. Without either, opening it is the new `SecretsError::BackendNotEnabled`, wire kind `backend_not_enabled`, JSON-RPC code -32078. `MachineSecretsConfig::enables` reports it.
- `store::open_backend_at`, `store::swept_backends`, `store::cli_backends`, `server::backends_for`, `ServerSettings::template_root` and `server::template_root_beside`. `secrets.doctor` lists `onepassword` on a `cli-backends` build without running `op`.
- On a `cli-backends` build, `trusty-secrets serve` removes stale template directories under its template root at start. An entry it cannot remove does not stop it: the other stale directories are still removed, and the first failure is printed on stderr.
- The server reads 1Password enablement and its `program` only from the account's own machine config, the one under the home the password database records; a `--machine-config` or `$HOME` file has no say. With that file missing or unreadable, 1Password is off for set, get and list, and the other backends keep serving. A delete skips 1Password when the file is missing, but refuses with `config_invalid` (or `storage_unavailable`) when it cannot be read or parsed, before any backend is touched; the index row stays.
- `secrets.doctor` rows carry a typed `reason` (`not_compiled`, `not_enabled`, `cli_not_installed`, `config_invalid`, `tracked_setting_refused`) and a `detail` naming the fix when a backend is unavailable; the reply adds `account_config` and `headless.onepassword_token` (whether `OP_SERVICE_ACCOUNT_TOKEN` was present at server start, never the token). All fields are additive, so an older client decodes a newer reply ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `server::serve_with` and `server::StartEnv`, so the binary reports what it read from its environment at start ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `secrets.doctor` reports DOC-74 §7's unsupported tools (`bw`, `vault`, `pass`, `gopass`, `doppler`, `infisical`) as `tools`: installed or not, from an absolute-`PATH` lookup at server start that runs nothing ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))

### Fixed

- `secrets.doctor` lists `onepassword` and `keeper` on every build, as `not_compiled` without `cli-backends`, instead of dropping their rows ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- Off macOS the server's factory refuses `keychain`, so doctor no longer shows a healthy Keychain row on a Linux host that has none ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- An unreadable or unparsable account machine config is reported as `config_invalid`, not as a backend that is merely off ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- A project whose tracked config is refused gets a doctor report with the refusal on its selected row, instead of a failed call ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- On a Keychain build, `secrets.doctor` reports a selected `file` backend as `not_enabled`, with the consent refusal as its detail, when the account's own machine config does not select `file`, the same check every write into `file` meets; `tm secrets doctor` then exits non-zero ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- A slow vendor CLI write no longer reaches the client as a transport timeout and then commits ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). The client waited 30 s while one `op` or `keeper` call may take 60 s. The server now gives each request one deadline, 120 s for `secrets.set`, `secrets.delete` and `secrets.copy` and 15 s for every other method, and bounds every CLI call by the time left: none starts after the deadline, and one still running is killed with its process group. Such a request fails with the new `deadline_exceeded` kind (code -32079, `SecretsError::DeadlineExceeded`), whose text says a backend write already under way may have landed; `copy` lists in `failed` each key it did not start and each key whose write the deadline cut short, which may have landed. `OnDemandSecrets::call` waits the method's deadline plus 15 s. Only CLI-backed calls are bounded: a Keychain or `file` call that blocks, for example on an unlock prompt, can still outlast the client's wait.

### Changed

- `server::ErrorKind` variants now carry explicit discriminants, pinned by a test: the 0.1.2 values `InvalidParams = 0` through `Internal = 29` stay as published, and `BackendNotEnabled` is `30`, after `Internal` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519), [#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). `SecretsError::BackendNotEnabled` follows `HomeUnavailable`, so no published `SecretsError` position moves either.

### Security

- `secrets.delete` now removes the key from every backend this build can store values in (the Keychain on macOS, and the file backend on Unix), not only the project's configured one ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519) A5). Before, a value set under one backend stayed there after the project switched backends, or after a `copy`, while the delete answered `removed: true` and dropped the key from `list`. If any backend fails to delete, or cannot be opened, the call now fails with that backend's error and the key stays listed; the other backends are still cleared. A key no backend holds is still answered `removed: false`. The scope check still runs before any backend is touched. The new `SecretStore::delete_across` deletes from a store's backend and a list of others; `store::local_backends` names the backends a delete clears. The names-only index format is unchanged.
- `secrets.delete` now runs the backend sweep and the index row removal in one locked index update ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). Before, a `set` landing between the sweep and the row removal stored a value whose row the delete then dropped, so `list` no longer showed a stored credential. A corrupt or locked index now fails a delete before any backend is touched.
- `secrets.delete` also clears 1Password when the machine config enables it, so a key `copy` placed there is removed ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). This costs one `op item list` per delete on such a machine.
- On a `cli-backends` build, `trusty-secrets serve` removes every inherited `OP_*` variable except `op signin` sessions at start, so a caller's environment cannot pick the 1Password account, config directory or Connect server. The service-account token is kept and reaches `op` only through the runner's environment overlay ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)).
- The 1Password backend runs `op` by absolute path only ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). At open it takes the machine config's `secrets.onepassword.program`, which must be an absolute path to an executable file, or else the first executable `op` in an absolute `PATH` entry. Empty, `.` and other relative `PATH` entries are skipped, so a planted `op` under a project's working directory never receives item templates. With no such `op`, the backend reports `CliNotInstalled`. A tracked project config that sets `program` is refused like `account` and `config_path`. `server::backends_for` and `store::open_backend_at` take the `PATH` value to search.
- A tracked project config that sets a CLI `account` or `config_path`, at the top level or under `onepassword` or `keeper`, is refused on every build with `SecretsError::TrackedCliSettingRefused` (wire kind `tracked_cli_setting_refused`); set them in the machine config instead. A non-mapping `onepassword:` or `keeper:` section, or a non-string `account`, now fails the load closed ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- A tracked project config `.trusty-tools/trusty-secrets.yaml` that is a symlink, a FIFO, a directory, a device or larger than 64 KiB is refused with `SecretsError::Config` (`config_invalid`) before a byte is read, and the read stops at 64 KiB + 1 bytes ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). Before, a cloned repository could track that path as a symlink to `/dev/zero` or as a FIFO and hold a server thread and its connection forever. The machine config gets the same type and size checks and may still be a symlink. A config that is not UTF-8 is now `config_invalid` rather than an I/O error. New: `store::config::MAX_CONFIG_BYTES`.
- `TRUSTY_SECRETS_INDEX_DIR` no longer moves the names index of a server on the default socket ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). The on-demand client passes the caller's environment to the server it starts, so one caller could move the index for every client of the shared server. A server whose socket is in another directory still reads the variable, and `--index-dir` still works on any socket. Any socket in the default socket's directory counts as the default, whatever its file name. The part of the directory that exists is resolved by the filesystem, so a relative path, `.`, `..`, repeated `/` and a symlinked directory reach it, and so does another letter case where the filesystem ignores case. Directory names that do not exist yet are compared ignoring ASCII case. A socket path with a `..` after a directory that does not exist yet, or with a missing directory name that is not ASCII or not UTF-8, counts as the default socket wherever it points, so the variable is ignored for it (fail closed). With `$HOME` unknown, or a socket directory that cannot be checked, the variable is ignored.
- On a build with a Keychain (macOS), the server writes a value into the plaintext `file` backend only when the user's own machine config sets `secrets.default_backend: file` ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524) H1). That is `.trusty-tools/trusty-common/config.yaml` under the home directory the password database records for the server's user; a config named with `serve --machine-config`, or found under a redirected `$HOME`, does not count, and a failed home lookup or an unreadable or unparseable file refuses the write. Before, `secrets.copy` with `to_backend: file` (`tm secrets copy --from keychain --to file`) let any process running as the same user move Keychain values into 0600 files, past the Keychain's access control. A refused `copy` or `set` opens no backend, writes no value file and no index row, leaves one audit denial, and fails with the new `SecretsError::FileBackendNotSelected` (wire kind `file_backend_not_selected`, code -32077), whose text names the machine-config setting. Reads from `file`, deletes from it (including the delete sweep), and every `file` write on a build without a Keychain are unchanged.
- `TRUSTY_SECRETS_INDEX_DIR` is now ignored on the default socket even when the server's `$HOME` is redirected: the server compares its socket with the default socket under the home directory the password database records for its user, as well as under `$HOME`, and treats the socket as the default when that lookup fails ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)).
- A 1Password `delete` whose `op item list` answers "isn't a vault" now fails instead of reporting a miss ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). `op` gives that answer for a vault the current identity cannot see as well as for a missing one, so `secrets.delete` dropped the index row while the item stayed in 1Password. The row now stays and the call fails with the new `vault_not_visible` kind (code -32080, `SecretsError::VaultNotVisible`). The index does not record which backend holds a key, so with 1Password enabled this also refuses a delete of a Keychain or `file` key whose project has no 1Password vault; the error names both ways out: create the vault in 1Password, or remove the `secrets.onepassword` section (and any `secrets.default_backend: onepassword`) from the machine config. A `get` still reads the answer as a miss.
- The 1Password backend no longer searches the spawning process's `PATH` for `op` ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524), Architect Decision A). A planted `op` in any directory on that `PATH`, ahead of the real one, received item templates with values inside. `op` now comes from the machine config's `secrets.onepassword.program` pin, which overrides everything, or else from the first of a fixed list of system directories: `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` on macOS; `/usr/local/bin`, `/usr/bin` elsewhere (DOC-74 §6.2). With neither, the error names the `program` setting. `server::backends_for` and `store::open_backend_at` no longer take a `PATH` value. `CliNotInstalled` now reads "`<program>` was not found; <hint>", and the `cli_not_installed` wire text names the `program` pin instead of `PATH`.

## [0.1.1] — 2026-10-07

### Added

- Credential access audit trail ([#4567](https://github.com/bobmatnyc/trusty-tools/issues/4567), DOC-45 §9, owner Q2): the `trusty-secrets` server appends one JSON line per access to `~/.trusty-tools/trusty-secrets/audit/audit.jsonl` (override with `--audit-log` or `ServerSettings::audit_log`; deliberately no environment variable), discriminator `"stream": "credential_access"`. `secrets.set` and `secrets.delete` write one record per call, allowed or denied; `secrets.copy` one per key; `secrets.list` only when denied; `scopes` and `doctor` none. The new `server::AuditRecord` holds typed fields only (`ts`, `method`, `decision`, `reason`, `vault`, `key`, `backend`, `project_root`, `caller_pid`) and never a value. The log is 0600 in a 0700 directory, refused on a symlink, a wider mode or another owner, synced before each reply, and rotated to `audit.jsonl.1` at 8 MiB when next opened. The log is opened before an allowed `set`, `delete` or `copy` touches a backend; if that fails, the call changes nothing and fails with the new `audit_unavailable` (code -32072). If the record cannot be written after the backend call succeeded, the change stands and the call still fails with `audit_unavailable` (its text says the change may already have been applied), and `copy` stops before its next key. A denial is still answered with its own kind. A torn last line is ended with `\n` before the next record, and the directory is synced after the log is created or rotated. Only the untracked machine config can turn the audit off (`secrets.audit: false`); a tracked project config that tries is refused with the new `tracked_audit_refused` (code -32073).
- File backend for hosts without a Keychain ([#9326](https://github.com/bobmatnyc/trusty-tools/issues/9326), owner ruling f5): `store::FileBackend` (backend id `file`, Unix only) keeps each value in its own plaintext file under `~/.trusty-tools/trusty-secrets/values/<vault>/<key>`, mode 0600 in 0700 directories, created with that mode and never widened. Each write fsyncs the directory after its rename. Every operation refuses a value file or directory that is a symlink, grants more than 0600/0700, or belongs to another user, with the new `SecretsError::StorageRefused` (`storage_refused`, code -32070, on the wire). `set`, `delete` and `list` remove temp files left by a writer process that is no longer running, so a crashed write never leaves a plaintext copy behind a delete. `file` is the default only where no Keychain backend is compiled in (`store::default_backend`); on macOS only the untracked machine config may select it (`secrets.default_backend: file`), a tracked project config naming `backend: file` is refused with the new `SecretsError::TrackedBackendRefused` (`tracked_backend_refused`, code -32071; checked by `store::config::check_project_backend`), and a Keychain failure never falls back to files. `secrets.doctor` lists `file` and reports the selected backend's `posture` (`keychain`, `file_degraded` or `other`; an unknown value decodes as `other`) through the new `StoragePosture`. The names-only index still holds no value.

## [0.1.0] — 2026-10-06

### Added

- In-process `secret://` resolution for `tm secrets exec` ([#7525](https://github.com/bobmatnyc/trusty-tools/issues/7525), DOC-74 §9.4, §15.8):
  - `store::resolve_reference` resolves one reference: an unscoped `secret://KEY` tries the project vault, then the owner vault; `secret://<owner>/KEY` and `secret://<owner>/<repo>/KEY` read only the vault they name. A miss is `SecretsError::NotFound`.
  - With `agent_parent = true`, a key not flagged "agents may use" is refused with `SecretsError::AgentUseRefused`, before the backend is read.
  - `store::resolve_env` resolves an ordered `NAME=raw` env map all or nothing. It validates POSIX names and parses every reference before any read, and passes non-reference values through. Any bad entry fails the whole call with `InvalidEnvEntry` or `EnvResolution`, naming the entry and the reference, never a value.
  - `store::parse_dotenv` reads a documented `.env` subset (`KEY=value`, `export`, `#` comments, single and double quotes). It rejects multi-line values, escapes, `$` expansion and duplicate names with `SecretsError::DotenvSyntax`, naming the line number, never the line.
  - On the `secrets.*` socket these errors map to fixed-text kinds with no fields: `agent_use_refused` (`-32065`, also for a refusal wrapped in `EnvResolution`), `invalid_env_entry` (`-32066`), `env_resolution_failed` (`-32067`) and `dotenv_syntax` (`-32068`).
- New crate `trusty-secrets` (S1 of DOC-74 §15, [#9064](https://github.com/bobmatnyc/trusty-tools/issues/9064)): project- and owner-scoped secret storage with no dependency on trusty-mpm, trusty-console, or trusty-common.
  - `api` feature: validated `SecretKey`, `OwnerName`, `RepoName`, `VaultName` and `BackendId`; the `secret://KEY`, `secret://<owner>/KEY` and `secret://<owner>/<repo>/KEY` reference grammar; a redacting `SecretValue`; `secrets.*` request and response types; and `SecretsError`. Invalid names fail closed, and errors never echo rejected input.
  - `store` feature: the `SecretBackend` trait with `READ`, `WRITE`, `LIST_NAMES` and `SYNC_TARGET` capability flags; an OS Keychain backend over `keyring` (service = vault, account = key, no read cache); a names-only index at `~/.trusty-tools/trusty-secrets/index/` (0600 files, 0700 directory, atomic writes under a file lock, corrupt files fail closed; `set` writes the backend inside the index lock and, if the index write then fails, deletes a new entry again or reports `SecretsError::OrphanedBackendEntry` naming the vault and key); project-over-owner scope resolution from the git remote; `mask_secret`; and machine/project config resolution.
  - Platforms: the Keychain backend links `keyring` on macOS only, with only its `apple-native` backend, so no Linux build pulls libdbus. On any other target every Keychain operation fails closed with `SecretsError::UnknownBackend` instead of writing to `keyring`'s in-memory mock store.
- `trusty-secrets serve` and the default `server` feature (S2 of DOC-74 §15, [#9065](https://github.com/bobmatnyc/trusty-tools/issues/9065)): the `secrets.scopes`, `secrets.list`, `secrets.set`, `secrets.delete`, `secrets.copy` and `secrets.doctor` methods as newline-terminated JSON-RPC 2.0 on `~/.trusty-tools/trusty-secrets/secrets.sock` (parent 0700, socket 0600, every connection uid-checked).
  - The socket starts on the first call through `OnDemandSecrets` and exits after 60 s with no answered request (`TRUSTY_SECRETS_IDLE_TIMEOUT_SECS`), removing its socket file. It has no launchd job, and a second instance never replaces a live one.
  - Each request names its project by directory. The server derives owner and repository from that checkout's git remote and reads the project's `secrets:` config from `<repo>/.trusty-tools/trusty-secrets.yaml`.
  - No method returns a secret value. Every failure is fixed text per method and error kind, so a malformed `set` never echoes its value.
  - An `api`- or `store`-only consumer depends with `default-features = false` and links no tokio or UDS code.
  - A `set` whose index write and cleanup delete both fail after the backend accepted the key reports kind `orphaned_backend_entry`, code `-32064`: the backend may hold an entry that no index row lists. The error carries no key, vault or value.
  - `secrets.copy` writes each key through `SecretStore::set`, so it takes the index lock and deletes a new destination entry again when the index publish fails; an entry that cleanup cannot delete aborts the copy with `orphaned_backend_entry` instead of landing in `failed`.

### Changed

- The `secrets.*` request types `ListRequest`, `SetRequest`, `DeleteRequest` and `CopyRequest` are `#[non_exhaustive]` and gain constructors: `ListRequest::new(vault)`, `SetRequest::new(vault, key, value)`, `DeleteRequest::new(vault, key)`, and `CopyRequest::new(from_backend, to_backend)` with `.with_keys(keys)` ([#9073](https://github.com/bobmatnyc/trusty-tools/issues/9073)). Build a request with its constructor; a struct literal no longer compiles outside the crate. The wire format is unchanged.
- `ErrorKind`, `ClientError`, `SettingsError`, `ServeError`, `ScopeKind`, `BackendStatus`, `DoctorResponse` and the server `State` are `#[non_exhaustive]`, so later error kinds, doctor fields and server state are additive. A `match` on one of these enums outside the crate needs a wildcard arm; build `State` with `State::new`.
- The response types `KeyMeta`, `ScopeInfo`, `ScopesResponse`, `ListResponse`, `SetResponse`, `DeleteResponse` and `CopyResponse`, the config types `MachineSecretsConfig`, `ProjectSecretsConfig` and `ResolvedConfig`, and the enums `SetOutcome`, `SecretRef` and `VarSource` are `#[non_exhaustive]`. Read a response through serde; build a config from `Default` and assign its fields.
- The crate docs gain a "Compatibility" section: adding a field, a variant or a provided trait method is a compatible change and ships as a 0.x patch release; every request denies unknown fields, so a new request field is optional with a serde default and a client must not send it to an older server; a new response field also takes a serde default.
- The server's method table, method bodies, `build_router` and `ErrorKind::to_rpc` are no longer public; the `server` module keeps its re-exports.
- No public signature names a trusty-common type. `ClientError::Rpc` carries the new `RpcFailure` (`code`, `message`, `kind: Option<ErrorKind>`); `ClientError::Spawn`, `ClientError::Transport` and the `ServeError` sources are opaque boxed errors; `serve` returns this crate's own `ServeExit`. `Display` text is unchanged.
- `ServerSettings` and `ResolvedVar` are `#[non_exhaustive]` ([#9328](https://github.com/bobmatnyc/trusty-tools/issues/9328)); build settings with the new `ServerSettings::new(socket, index_root, machine_config, idle_timeout)`. `ResolvedConfig` implements `Default` (the Keychain backend, no vault override), so other crates can build one.
- The `keychain_roundtrip` test target requires the `store` feature, so `cargo test --no-default-features --features api` compiles.

### Security

- Files inside a repository can no longer select another project's vault ([#9328](https://github.com/bobmatnyc/trusty-tools/issues/9328), owner ruling 06). A pinned `secret://<owner>[/<repo>]/KEY` must name the caller's own project or owner vault, else `VaultOutOfScope`; a tracked `.trusty-tools/trusty-secrets.yaml` `secrets.vault` must be `trusty/<owner>/<name>` under the remote's owner, and a wider override is honoured only from the machine config's new `secrets.project_vaults` map; an `origin` remote that is not a github.com `https://`, `ssh://` (or `git+ssh://` / `ssh+git://`) or scp-form URL — including github.com over `http://`, `git://`, `file://` or a `<helper>::` prefix — is refused with the new `UnsupportedRemoteHost` error (`remote_host_unsupported` on the wire). `ScopeSet::derive` and `ScopeSet::from_identity` now take the override's source, and `parse_remote_identity` returns a `RemoteRefusal`; `RemoteRefusal` and `VaultOverride` are `#[non_exhaustive]`.
