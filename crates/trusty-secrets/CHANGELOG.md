## [0.1.2] — 2026-10-08

### Added

- `cli-backends` feature: `store::cli`, a blocking runner for CLI-backed backends that sends a value only on stdin, refuses a command line carrying the value or an overlay token, keeps all child output out of errors, classifies stderr into missing, locked or other, kills the child's process group on timeout, and caps each stream at 1 MiB; plus a 0600 `TemplateFile` guard and a startup sweep for its leftovers ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `SecretsError::CliNotInstalled` and `SecretsError::BackendLocked`, with wire kinds `cli_not_installed` and `backend_locked` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `cli-backends` feature: the `keeper` backend, `store::keeper::KeeperBackend`, which keeps values in Keeper through Keeper Commander, `keeper` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). Shims only and provisional: no test has run against a real Keeper account. One `login` record per key, titled with the key, value in `password`, in the Keeper folder at the vault's path. Writes are one `record-add` or `record-update` line on stdin (`keeper --batch-mode -`) with the value as `$BASE64:`; the value is never in argv or the environment. Every write is read back and every delete re-listed; anything else fails. A key is missing only when a successful listing does not show it. Nothing in a vault is read, written or removed until listings from the root down show exactly one folder of exactly each segment's name, because `ls` of a missing path may exit 0 with the parent's entries. `rm` moves a record to Keeper's trash, which counts as deleted. A logged-out or unapproved `keeper` is `backend_locked`, and the error, and the `backend_locked` reply text, name the one-time device approval and persistent login. Capabilities are `READ | WRITE`.
- The machine config's `secrets.keeper` section or `secrets.default_backend: keeper` enables the backend; it opens only when the section names `program` and `config_path`, both absolute, the config file a regular 0600 file the account owns. `account` there is refused. As for 1Password, the server reads this only from the account's own machine config, and the delete sweep includes Keeper wherever it includes 1Password. `BackendId::KEEPER`, `MachineSecretsConfig::keeper`, and `secrets.doctor` lists `keeper` on a `cli-backends` build without running it.
- `CliCommand::hide`, which refuses a secret in argv and the environment overlay beside the stdin value.
- `cli-backends` feature: the `onepassword` backend, `store::onepassword::OnePasswordBackend`, which keeps values in 1Password through `op` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). It finds a key's item with `op item list --vault <vault> --format json`, then reads with `op read`, creates with `op item create -` (the JSON item template, value inside, on stdin), edits with `op item edit <id> --template <file>` (a 0600 file removed after the call), and deletes with `op item delete`. The key never reaches argv. A missing item or vault is a miss; a locked or signed-out `op` is `backend_locked`. Capabilities are `READ | WRITE`.
- The machine config's `secrets.onepassword` section (`account`, `config_path`, or `{}`) or `secrets.default_backend: onepassword` enables the backend. Without either, opening it is the new `SecretsError::BackendNotEnabled`, wire kind `backend_not_enabled`, JSON-RPC code -32078. `MachineSecretsConfig::enables` reports it.
- `store::open_backend_at`, `store::swept_backends`, `store::cli_backends`, `server::backends_for`, `ServerSettings::template_root` and `server::template_root_beside`. `secrets.doctor` lists `onepassword` on a `cli-backends` build without running `op`.
- On a `cli-backends` build, `trusty-secrets serve` removes stale template directories under its template root at start. An entry it cannot remove does not stop it: the other stale directories are still removed, and the first failure is printed on stderr.
- The server reads 1Password enablement and its `program` only from the account's own machine config, the one under the home the password database records; a `--machine-config` or `$HOME` file has no say. With that file missing or unreadable, 1Password is off for set, get and list, and the other backends keep serving. A delete skips 1Password when the file is missing, but refuses with `config_invalid` (or `storage_unavailable`) when it cannot be read or parsed, before any backend is touched; the index row stays.
- `secrets.doctor` rows carry a typed `reason` (`not_compiled`, `not_enabled`, `cli_not_installed`, `config_invalid`, `tracked_setting_refused`) and a `detail` naming the fix when a backend is unavailable; the reply adds `account_config` and `headless.onepassword_token` (whether `OP_SERVICE_ACCOUNT_TOKEN` was present at server start, never the token). All fields are additive, so an older client decodes a newer reply ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `server::serve_with` and `server::StartEnv`, so the binary reports what it read from its environment at start ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- `secrets.doctor` reports DOC-74 §7's unsupported tools (`bw`, `vault`, `pass`, `gopass`, `doppler`, `infisical`) as `tools`: installed or not, from an absolute-`PATH` lookup at server start that runs nothing ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))

### Fixed

- `secrets.doctor` lists `onepassword` and `keeper` on every build, as `not_compiled` without `cli-backends`, instead of dropping their rows ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- Off macOS the server's factory refuses `keychain`, so doctor no longer shows a healthy Keychain row on a Linux host that has none ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- An unreadable or unparsable account machine config is reported as `config_invalid`, not as a backend that is merely off ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- A project whose tracked config is refused gets a doctor report with the refusal on its selected row, instead of a failed call ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- On a Keychain build, `secrets.doctor` reports a selected `file` backend as `not_enabled`, with the consent refusal as its detail, when the account's own machine config does not select `file`, the same check every write into `file` meets; `tm secrets doctor` then exits non-zero ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- A slow vendor CLI write no longer reaches the client as a transport timeout and then commits ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). The client waited 30 s while one `op` or `keeper` call may take 60 s. The server now gives each request one deadline, 120 s for `secrets.set`, `secrets.delete` and `secrets.copy` and 15 s for every other method, and bounds every CLI call by the time left: none starts after the deadline, and one still running is killed with its process group. Such a request fails with the new `deadline_exceeded` kind (code -32079, `SecretsError::DeadlineExceeded`), whose text says a backend write already under way may have landed; `copy` lists in `failed` each key it did not start and each key whose write the deadline cut short, which may have landed. `OnDemandSecrets::call` waits the method's deadline plus 15 s. Only CLI-backed calls are bounded: a Keychain or `file` call that blocks, for example on an unlock prompt, can still outlast the client's wait.

### Changed

- `server::ErrorKind` variants now carry explicit discriminants, pinned by a test: the 0.1.2 values `InvalidParams = 0` through `Internal = 29` stay as published, and `BackendNotEnabled` is `30`, after `Internal` ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519), [#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). `SecretsError::BackendNotEnabled` follows `HomeUnavailable`, so no published `SecretsError` position moves either.

### Security

- `secrets.delete` now removes the key from every backend this build can store values in (the Keychain on macOS, and the file backend on Unix), not only the project's configured one ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519) A5). Before, a value set under one backend stayed there after the project switched backends, or after a `copy`, while the delete answered `removed: true` and dropped the key from `list`. If any backend fails to delete, or cannot be opened, the call now fails with that backend's error and the key stays listed; the other backends are still cleared. A key no backend holds is still answered `removed: false`. The scope check still runs before any backend is touched. The new `SecretStore::delete_across` deletes from a store's backend and a list of others; `store::local_backends` names the backends a delete clears. The names-only index format is unchanged.
- `secrets.delete` now runs the backend sweep and the index row removal in one locked index update ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). Before, a `set` landing between the sweep and the row removal stored a value whose row the delete then dropped, so `list` no longer showed a stored credential. A corrupt or locked index now fails a delete before any backend is touched.
- `secrets.delete` also clears 1Password when the machine config enables it, so a key `copy` placed there is removed ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). This costs one `op item list` per delete on such a machine.
- On a `cli-backends` build, `trusty-secrets serve` removes every inherited `OP_*` variable except `op signin` sessions at start, so a caller's environment cannot pick the 1Password account, config directory or Connect server. The service-account token is kept and reaches `op` only through the runner's environment overlay ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)).
- The 1Password backend runs `op` by absolute path only ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519)). At open it takes the machine config's `secrets.onepassword.program`, which must be an absolute path to an executable file, or else the first executable `op` in an absolute `PATH` entry. Empty, `.` and other relative `PATH` entries are skipped, so a planted `op` under a project's working directory never receives item templates. With no such `op`, the backend reports `CliNotInstalled`. A tracked project config that sets `program` is refused like `account` and `config_path`. `server::backends_for` and `store::open_backend_at` take the `PATH` value to search.
- A tracked project config that sets a CLI `account` or `config_path`, at the top level or under `onepassword` or `keeper`, is refused on every build with `SecretsError::TrackedCliSettingRefused` (wire kind `tracked_cli_setting_refused`); set them in the machine config instead. A non-mapping `onepassword:` or `keeper:` section, or a non-string `account`, now fails the load closed ([#7519](https://github.com/bobmatnyc/trusty-tools/issues/7519))
- A tracked project config `.trusty-tools/trusty-secrets.yaml` that is a symlink, a FIFO, a directory, a device or larger than 64 KiB is refused with `SecretsError::Config` (`config_invalid`) before a byte is read, and the read stops at 64 KiB + 1 bytes ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). Before, a cloned repository could track that path as a symlink to `/dev/zero` or as a FIFO and hold a server thread and its connection forever. The machine config gets the same type and size checks and may still be a symlink. A config that is not UTF-8 is now `config_invalid` rather than an I/O error. New: `store::config::MAX_CONFIG_BYTES`.
- `TRUSTY_SECRETS_INDEX_DIR` no longer moves the names index of a server on the default socket ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). The on-demand client passes the caller's environment to the server it starts, so one caller could move the index for every client of the shared server. A server whose socket is in another directory still reads the variable, and `--index-dir` still works on any socket. Any socket in the default socket's directory counts as the default, whatever its file name. The part of the directory that exists is resolved by the filesystem, so a relative path, `.`, `..`, repeated `/` and a symlinked directory reach it, and so does another letter case where the filesystem ignores case. Directory names that do not exist yet are compared ignoring ASCII case. A socket path with a `..` after a directory that does not exist yet, or with a missing directory name that is not ASCII or not UTF-8, counts as the default socket wherever it points, so the variable is ignored for it (fail closed). With `$HOME` unknown, or a socket directory that cannot be checked, the variable is ignored.
- On a build with a Keychain (macOS), the server writes a value into the plaintext `file` backend only when the user's own machine config sets `secrets.default_backend: file` ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524) H1). That is `.trusty-tools/trusty-common/config.yaml` under the home directory the password database records for the server's user; a config named with `serve --machine-config`, or found under a redirected `$HOME`, does not count, and a failed home lookup or an unreadable or unparseable file refuses the write. Before, `secrets.copy` with `to_backend: file` (`tm secrets copy --from keychain --to file`) let any process running as the same user move Keychain values into 0600 files, past the Keychain's access control. A refused `copy` or `set` opens no backend, writes no value file and no index row, leaves one audit denial, and fails with the new `SecretsError::FileBackendNotSelected` (wire kind `file_backend_not_selected`, code -32077), whose text names the machine-config setting. Reads from `file`, deletes from it (including the delete sweep), and every `file` write on a build without a Keychain are unchanged.
- `TRUSTY_SECRETS_INDEX_DIR` is now ignored on the default socket even when the server's `$HOME` is redirected: the server compares its socket with the default socket under the home directory the password database records for its user, as well as under `$HOME`, and treats the socket as the default when that lookup fails ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)).
- A 1Password `delete` whose `op item list` answers "isn't a vault" now fails instead of reporting a miss ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524)). `op` gives that answer for a vault the current identity cannot see as well as for a missing one, so `secrets.delete` dropped the index row while the item stayed in 1Password. The row now stays and the call fails with the new `vault_not_visible` kind (code -32080, `SecretsError::VaultNotVisible`). The index does not record which backend holds a key, so with 1Password enabled this also refuses a delete of a Keychain or `file` key whose project has no 1Password vault; the error names both ways out: create the vault in 1Password, or remove the `secrets.onepassword` section (and any `secrets.default_backend: onepassword`) from the machine config. A `get` still reads the answer as a miss.
- The 1Password backend no longer searches the spawning process's `PATH` for `op` ([#7524](https://github.com/bobmatnyc/trusty-tools/issues/7524), Architect Decision A). A planted `op` in any directory on that `PATH`, ahead of the real one, received item templates with values inside. `op` now comes from the machine config's `secrets.onepassword.program` pin, which overrides everything, or else from the first of a fixed list of system directories: `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` on macOS; `/usr/local/bin`, `/usr/bin` elsewhere (DOC-74 §6.2). With neither, the error names the `program` setting. `server::backends_for` and `store::open_backend_at` no longer take a `PATH` value. `CliNotInstalled` now reads "`<program>` was not found; <hint>", and the `cli_not_installed` wire text names the `program` pin instead of `PATH`.

## [0.1.1] — 2026-10-07

### Added

- Credential access audit trail ([#4567](https://github.com/bobmatnyc/trusty-tools/issues/4567), DOC-45 §9, owner Q2): the `trusty-secrets` server appends one JSON line per access to `~/.trusty-tools/trusty-secrets/audit/audit.jsonl` (override with `--audit-log` or `ServerSettings::audit_log`; deliberately no environment variable), discriminator `"stream": "credential_access"`. `secrets.set` and `secrets.delete` write one record per call, allowed or denied; `secrets.copy` one per key; `secrets.list` only when denied; `scopes` and `doctor` none. The new `server::AuditRecord` holds typed fields only (`ts`, `method`, `decision`, `reason`, `vault`, `key`, `backend`, `project_root`, `caller_pid`) and never a value. The log is 0600 in a 0700 directory, refused on a symlink, a wider mode or another owner, synced before each reply, and rotated to `audit.jsonl.1` at 8 MiB when next opened. The log is opened before an allowed `set`, `delete` or `copy` touches a backend; if that fails, the call changes nothing and fails with the new `audit_unavailable` (code -32072). If the record cannot be written after the backend call succeeded, the change stands and the call still fails with `audit_unavailable` (its text says the change may already have been applied), and `copy` stops before its next key. A denial is still answered with its own kind. A torn last line is ended with `\n` before the next record, and the directory is synced after the log is created or rotated. Only the untracked machine config can turn the audit off (`secrets.audit: false`); a tracked project config that tries is refused with the new `tracked_audit_refused` (code -32073).
- File backend for hosts without a Keychain ([#9326](https://github.com/bobmatnyc/trusty-tools/issues/9326), owner ruling f5): `store::FileBackend` (backend id `file`, Unix only) keeps each value in its own plaintext file under `~/.trusty-tools/trusty-secrets/values/<vault>/<key>`, mode 0600 in 0700 directories, created with that mode and never widened. Each write fsyncs the directory after its rename. Every operation refuses a value file or directory that is a symlink, grants more than 0600/0700, or belongs to another user, with the new `SecretsError::StorageRefused` (`storage_refused`, code -32070, on the wire). `set`, `delete` and `list` remove temp files left by a writer process that is no longer running, so a crashed write never leaves a plaintext copy behind a delete. `file` is the default only where no Keychain backend is compiled in (`store::default_backend`); on macOS only the untracked machine config may select it (`secrets.default_backend: file`), a tracked project config naming `backend: file` is refused with the new `SecretsError::TrackedBackendRefused` (`tracked_backend_refused`, code -32071; checked by `store::config::check_project_backend`), and a Keychain failure never falls back to files. `secrets.doctor` lists `file` and reports the selected backend's `posture` (`keychain`, `file_degraded` or `other`; an unknown value decodes as `other`) through the new `StoragePosture`. The names-only index still holds no value.

## [0.1.0] — 2026-10-06

### Added

- In-process `secret://` resolution for `tm secrets exec` ([#7525](https://github.com/bobmatnyc/trusty-tools/issues/7525), DOC-74 §9.4, §15.8):
  - `store::resolve_reference` resolves one reference: an unscoped `secret://KEY` tries the project vault, then the owner vault; `secret://<owner>/KEY` and `secret://<owner>/<repo>/KEY` read only the vault they name. A miss is `SecretsError::NotFound`.
  - With `agent_parent = true`, a key not flagged "agents may use" is refused with `SecretsError::AgentUseRefused`, before the backend is read.
  - `store::resolve_env` resolves an ordered `NAME=raw` env map all or nothing. It validates POSIX names and parses every reference before any read, and passes non-reference values through. Any bad entry fails the whole call with `InvalidEnvEntry` or `EnvResolution`, naming the entry and the reference, never a value.
  - `store::parse_dotenv` reads a documented `.env` subset (`KEY=value`, `export`, `#` comments, single and double quotes). It rejects multi-line values, escapes, `$` expansion and duplicate names with `SecretsError::DotenvSyntax`, naming the line number, never the line.
  - On the `secrets.*` socket these errors map to fixed-text kinds with no fields: `agent_use_refused` (`-32065`, also for a refusal wrapped in `EnvResolution`), `invalid_env_entry` (`-32066`), `env_resolution_failed` (`-32067`) and `dotenv_syntax` (`-32068`).
- New crate `trusty-secrets` (S1 of DOC-74 §15, [#9064](https://github.com/bobmatnyc/trusty-tools/issues/9064)): project- and owner-scoped secret storage with no dependency on trusty-mpm, trusty-console, or trusty-common.
  - `api` feature: validated `SecretKey`, `OwnerName`, `RepoName`, `VaultName` and `BackendId`; the `secret://KEY`, `secret://<owner>/KEY` and `secret://<owner>/<repo>/KEY` reference grammar; a redacting `SecretValue`; `secrets.*` request and response types; and `SecretsError`. Invalid names fail closed, and errors never echo rejected input.
  - `store` feature: the `SecretBackend` trait with `READ`, `WRITE`, `LIST_NAMES` and `SYNC_TARGET` capability flags; an OS Keychain backend over `keyring` (service = vault, account = key, no read cache); a names-only index at `~/.trusty-tools/trusty-secrets/index/` (0600 files, 0700 directory, atomic writes under a file lock, corrupt files fail closed; `set` writes the backend inside the index lock and, if the index write then fails, deletes a new entry again or reports `SecretsError::OrphanedBackendEntry` naming the vault and key); project-over-owner scope resolution from the git remote; `mask_secret`; and machine/project config resolution.
  - Platforms: the Keychain backend links `keyring` on macOS only, with only its `apple-native` backend, so no Linux build pulls libdbus. On any other target every Keychain operation fails closed with `SecretsError::UnknownBackend` instead of writing to `keyring`'s in-memory mock store.
- `trusty-secrets serve` and the default `server` feature (S2 of DOC-74 §15, [#9065](https://github.com/bobmatnyc/trusty-tools/issues/9065)): the `secrets.scopes`, `secrets.list`, `secrets.set`, `secrets.delete`, `secrets.copy` and `secrets.doctor` methods as newline-terminated JSON-RPC 2.0 on `~/.trusty-tools/trusty-secrets/secrets.sock` (parent 0700, socket 0600, every connection uid-checked).
  - The socket starts on the first call through `OnDemandSecrets` and exits after 60 s with no answered request (`TRUSTY_SECRETS_IDLE_TIMEOUT_SECS`), removing its socket file. It has no launchd job, and a second instance never replaces a live one.
  - Each request names its project by directory. The server derives owner and repository from that checkout's git remote and reads the project's `secrets:` config from `<repo>/.trusty-tools/trusty-secrets.yaml`.
  - No method returns a secret value. Every failure is fixed text per method and error kind, so a malformed `set` never echoes its value.
  - An `api`- or `store`-only consumer depends with `default-features = false` and links no tokio or UDS code.
  - A `set` whose index write and cleanup delete both fail after the backend accepted the key reports kind `orphaned_backend_entry`, code `-32064`: the backend may hold an entry that no index row lists. The error carries no key, vault or value.
  - `secrets.copy` writes each key through `SecretStore::set`, so it takes the index lock and deletes a new destination entry again when the index publish fails; an entry that cleanup cannot delete aborts the copy with `orphaned_backend_entry` instead of landing in `failed`.

### Changed

- The `secrets.*` request types `ListRequest`, `SetRequest`, `DeleteRequest` and `CopyRequest` are `#[non_exhaustive]` and gain constructors: `ListRequest::new(vault)`, `SetRequest::new(vault, key, value)`, `DeleteRequest::new(vault, key)`, and `CopyRequest::new(from_backend, to_backend)` with `.with_keys(keys)` ([#9073](https://github.com/bobmatnyc/trusty-tools/issues/9073)). Build a request with its constructor; a struct literal no longer compiles outside the crate. The wire format is unchanged.
- `ErrorKind`, `ClientError`, `SettingsError`, `ServeError`, `ScopeKind`, `BackendStatus`, `DoctorResponse` and the server `State` are `#[non_exhaustive]`, so later error kinds, doctor fields and server state are additive. A `match` on one of these enums outside the crate needs a wildcard arm; build `State` with `State::new`.
- The response types `KeyMeta`, `ScopeInfo`, `ScopesResponse`, `ListResponse`, `SetResponse`, `DeleteResponse` and `CopyResponse`, the config types `MachineSecretsConfig`, `ProjectSecretsConfig` and `ResolvedConfig`, and the enums `SetOutcome`, `SecretRef` and `VarSource` are `#[non_exhaustive]`. Read a response through serde; build a config from `Default` and assign its fields.
- The crate docs gain a "Compatibility" section: adding a field, a variant or a provided trait method is a compatible change and ships as a 0.x patch release; every request denies unknown fields, so a new request field is optional with a serde default and a client must not send it to an older server; a new response field also takes a serde default.
- The server's method table, method bodies, `build_router` and `ErrorKind::to_rpc` are no longer public; the `server` module keeps its re-exports.
- No public signature names a trusty-common type. `ClientError::Rpc` carries the new `RpcFailure` (`code`, `message`, `kind: Option<ErrorKind>`); `ClientError::Spawn`, `ClientError::Transport` and the `ServeError` sources are opaque boxed errors; `serve` returns this crate's own `ServeExit`. `Display` text is unchanged.
- `ServerSettings` and `ResolvedVar` are `#[non_exhaustive]` ([#9328](https://github.com/bobmatnyc/trusty-tools/issues/9328)); build settings with the new `ServerSettings::new(socket, index_root, machine_config, idle_timeout)`. `ResolvedConfig` implements `Default` (the Keychain backend, no vault override), so other crates can build one.
- The `keychain_roundtrip` test target requires the `store` feature, so `cargo test --no-default-features --features api` compiles.

### Security

- Files inside a repository can no longer select another project's vault ([#9328](https://github.com/bobmatnyc/trusty-tools/issues/9328), owner ruling 06). A pinned `secret://<owner>[/<repo>]/KEY` must name the caller's own project or owner vault, else `VaultOutOfScope`; a tracked `.trusty-tools/trusty-secrets.yaml` `secrets.vault` must be `trusty/<owner>/<name>` under the remote's owner, and a wider override is honoured only from the machine config's new `secrets.project_vaults` map; an `origin` remote that is not a github.com `https://`, `ssh://` (or `git+ssh://` / `ssh+git://`) or scp-form URL — including github.com over `http://`, `git://`, `file://` or a `<helper>::` prefix — is refused with the new `UnsupportedRemoteHost` error (`remote_host_unsupported` on the wire). `ScopeSet::derive` and `ScopeSet::from_identity` now take the override's source, and `parse_remote_identity` returns a `RemoteRefusal`; `RemoteRefusal` and `VaultOverride` are `#[non_exhaustive]`.
