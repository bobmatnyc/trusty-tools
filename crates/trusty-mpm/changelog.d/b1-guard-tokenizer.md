Fixed
- `tm hook --pm-guard`'s Bash guards share one tokenizer and token classifier, so shell metacharacters are no longer read as filenames or as executable code. A `sed` expression's regex wildcard (#7839), an `awk` `/regex/{action}` rule's body (#7744) and a `python3 -c` regex literal (#7738) are no longer refused as secret-bearing filenames; `2>&1` is read as a file-descriptor duplication rather than a file named `&1`, so a read-only `ls`/`stat` naming a dotenv path keeps its exemption through the redirect (#7743); and a quoted here-document's body is no longer classified as shell commands by the destructive-deletion rule (#7190). A guard that cannot tokenize a command still refuses, and the refusal now names the parse problem.
- Regression rows verify the two already-closed issues in the same cluster stay closed (#7833, #7479) and record that the two remaining reports (#7728, #7863) are harness refusals this guard classifies and allows.
- The here-document body stripper no longer treats a `<<'WORD'` written inside a quoted string as a real operator (#7190). Its fallback scan runs only when the whole-command quote scan could not balance — not in the ordinary no-here-document case — and it now tracks quote state itself, blanking each body it claims so the body's own apostrophes cannot poison the state of the lines after it. `echo "use <<'PY'"` followed by an `rm -rf /` and a line reading `PY` is refused again.
- A quoted here-document body inside a command substitution or process substitution (`eval "$(cat <<'PY' … PY)"`, `source <(cat <<'PY' … PY)`) is no longer blanked before the destructive-deletion scan, so a deletion written in it is refused, as it was before this change (#7190). The rule keys on the capture, not on the verb that re-executes the captured text.
