Fixed
- The shared-checkout dispatch deny now names each blocking delegation record — agent type, agent id (or delegation id when there is none), owning session by its tmux name, age — and the exact `tm repair delegation` command that clears it (#8257).
- `tm repair delegation --list [DIR]` lists the live delegation records for a directory, read-only, marking the ones that block a dispatch (#8257).
- `tm repair delegation --delegation-id <id>` reaches a record that never learned an agent id, and a record past the 6 h stale threshold is repairable while its session is still live. A record whose stop was matched only by agent type still blocks while its session lives, because that stop can belong to a running sibling; only the owning session can clear it (#8257).
- The session that owns a live, stop-less, under-6 h delegation record may now clear it itself: `tm repair delegation` identifies the caller from the harness's `CLAUDE_CODE_SESSION_ID`, refuses any other session, refuses when no caller session can be established, and records the clearing session and the reason `owner-attested finished (#8257)` on the record. No CLI argument can name the caller session (#8257).
- No refusal a caller reads — the repair's refusal, the shared-checkout dispatch deny and its JSON, the builder-cap deny, or the `--list` output — carries the owning session's UUID, which a denied caller could replay as `CLAUDE_CODE_SESSION_ID`. The owner is named by its tmux name when that name is not itself a session id; each owner-check refusal logs one WARN line carrying the owner's UUID for the operator (#8257).
- Every clear, owner-attested or `--force`, now logs one WARN line per record naming the delegation id, agent, owning session, clearing session, basis and whether it was forced (#8257).
- The repair now refuses while a live process stands in the agent's own tree, or while a harness lock on that tree — or, for an unisolated record, any harness lock naming its agent — has a pid running with the lock's recorded start time, the owning session included, and it refuses whenever one of those probes cannot answer. A directory with no `.git` at or above it holds no harness lock, so git failing there does not refuse; git failing inside a repository still does. The lock's start time is read as UTC, as the harness writes it, so a live lock reads as live on a machine in any time zone (#8257).
