Fixed
- A TUI started with `--url` or `TRUSTY_MPM_URL` (`tm tui`, `tm tui --single-pane`, `tm session tui`, `tm attach`, bare `tm projects`) keeps that daemon after a failed health poll and reports it unreachable; it no longer re-discovers and moves to the daemon the lock file or the default names ([#9556](https://github.com/bobmatnyc/trusty-tools/issues/9556))
- Under `TRUSTY_SANDBOX=1` or `TRUSTY_DATA_DIR_OVERRIDE`, `tm` no longer probes the default trusty-console at 127.0.0.1:7788 when the sandbox records no console address, so a sandboxed `tm` is not routed through the live console to the live daemon; a console address recorded in the sandbox data dir is still used ([#9556](https://github.com/bobmatnyc/trusty-tools/issues/9556))
- Under `TRUSTY_SANDBOX=1` or `TRUSTY_DATA_DIR_OVERRIDE`, with no `--url`/`TRUSTY_MPM_URL`, no recorded console and no live daemon lock of the sandbox's own (a lock under the account's real home, or one naming 127.0.0.1:7880, does not count), `tm` no longer falls back to the host default daemon at 127.0.0.1:7880: commands fail with "no daemon reachable for this sandbox" (bare `tm` exits 75), and `tm start`, `tm restart`, the bare-`tm` autostart and the `tm serve --stdio` bridge refuse to spawn or kickstart a daemon ([#9556](https://github.com/bobmatnyc/trusty-tools/issues/9556))
- In that same sandbox state, the `tm` banner no longer TCP-probes the default console at 127.0.0.1:7788, `tm start --url <sandbox daemon>` checks the URL it was given, and the pm-guard treats the missing daemon as "no daemon" rather than an unanswered one ([#9556](https://github.com/bobmatnyc/trusty-tools/issues/9556))
