Added

- `tm issue epic create --from <plan-doc>` files an epic tracker and its phase issues from a committed plan document, and `tm issue epic sync <epic#>` regenerates the tracker's `phases` block wholesale from live child state ([#8447](https://github.com/bobmatnyc/trusty-tools/issues/8447)). Creation refuses until the plan document is on `origin/main` and links it by a SHA-pinned blob permalink, never a branch path; the tracker is renamed to `[EPIC <n>] <outcome>` in the call immediately after it is filed, so an interrupted run leaves no placeholder-titled issue, and a re-run adopts the existing tracker and files only the phases it is missing. Phase numbers are max+1 over existing children and are never reused. Both verbs refuse to write a body that is empty or that has lost a marker — the fail-open that wiped [#8445](https://github.com/bobmatnyc/trusty-tools/issues/8445)'s body when the hand-run `awk` recipe emitted empty output on BSD userlands. The one permitted degradation is a project attach the token's scope refuses: the run posts a `no-project: <reason>` comment and still exits 0, and a re-run repairs a phase the interruption left with neither a project nor that waiver. The resume lookup enumerates a label-filtered issue listing rather than querying GitHub's eventually-consistent search index, and refuses on a full page instead of reading it as "no tracker exists" — a duplicate tracker cannot be undone. A sub-issue connection whose `totalCount` exceeds its page falls back to the paginated REST endpoint, so a large epic cannot lose rows from the regenerated block.
