Fixed
- Decommission no longer deletes an SM-owned workspace that holds work. The owned-workspace branch removed the directory with `remove_dir_all` and checked nothing, so one `session_decommission` call, CLI decommission or idle-reaper pass deleted an agent's `results/` and its unpushed commits. A workspace that is a git worktree or repository now gets the worktree guard: dirty files, unpushed commits, nested repository work and gitignored output that is not build output each keep it. `--force` excuses tm's provisioning files only, as it does for in-project worktrees, and logs the files it deletes. A workspace that is not a repository is kept unless it holds only harness files (`.trusty-mpm/`, the ownership marker, `.claude/settings*.json`) and build output (`target/`, `node_modules/`, and similar). The refusal names the path and the reason in the decommission report and the daemon log, and the record keeps its workspace pointer (#8663).
- A leftover directory git no longer claims is kept when it holds anything but harness files and build output. An agent that deleted `.git` in its worktree lost its results to the orphan prune. Only `prune-worktrees --discard-dirty` removes such a directory, after logging what it deletes. A content check that cannot complete keeps the directory on both routes (#8663).
