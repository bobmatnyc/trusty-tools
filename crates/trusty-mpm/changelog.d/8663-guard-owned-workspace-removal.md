Fixed
- Decommission no longer deletes an SM-owned workspace that holds work. The owned-workspace branch removed the directory with `remove_dir_all` and checked nothing, so one `session_decommission` call, CLI decommission or idle-reaper pass deleted an agent's `results/` and its unpushed commits. A workspace that is a git worktree or repository now gets the worktree guard: dirty files, unpushed commits, nested repository work and gitignored output that is not build output each keep it, and so does a `git worktree lock`, with or without `--force`. `--force` excuses tm's provisioning files only, as it does for in-project worktrees, acts only on a worktree whose ownership marker names the session, and logs the files it deletes. A workspace that is not a repository is kept unless it holds only harness files (`.trusty-mpm/`, the ownership marker, `.claude/settings*.json`) and build output (`target/`, `node_modules/`, and similar). The refusal names the path and the reason in the decommission report and the daemon log, and the record keeps its workspace pointer (#8663).
- A plain decommission, the idle reaper and the prune sweeps reclaim a freshly provisioned owned workspace again. Each launch now records what it wrote into a ledger in the git admin directory, outside the work tree: the sha256 of `CLAUDE.md`, `.claude/settings.json` and `.claude/settings.json.bak`, and the lines it added to `.gitignore`. Those entries no longer count as work while they match the ledger byte for byte. An edited file, an extra `.gitignore` line, or a workspace with no ledger (provisioned before this release) is still kept (#8663).
- The MCP `session_decommission` result and the `sm.sessions.kill` response now carry `workspace_removed` and `workspace_kept_reason`, so a caller sees a kept workspace and why. The legacy delete reconcile and `tm meta run` log the kept reason (#8663).
- A leftover directory git no longer claims is kept when it holds anything but harness files and build output. An agent that deleted `.git` in its worktree lost its results to the orphan prune. Only `prune-worktrees --discard-dirty` removes such a directory, after logging every top-level entry it deletes with its file count (up to 50, then `+N more`). A content check that cannot complete keeps the directory on both routes (#8663).
