Changed
- A session in a project pinned to a gh account (registry `gh_account`, `github.config_dir`, `--account`, or the `[accounts]` org map) no longer receives a gh token in its environment. tm verifies at launch that `gh auth token --hostname <host> --user <login>` returns that login's own token (`GET /user`), then puts a tm-written `gh` shim first on the session's `PATH`; each `gh` call, and HTTPS git through `credential.https://<host>.helper`, asks the keyring for the pinned login's token and hands it to that one `gh` process. Inherited `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` are removed. The shim lives under `<state_root>/gh-shim/` (dir 0700, script 0755) and holds no token (#9750).
- `tm sessions new`, `tm sessions start` and a bare-`tm` in-place relaunch of a pinned project now exit 1 when the keyring cannot prove the pinned login, with `tm: cannot start session: gh account '<login>' is not logged in as that account on <host> (<reason>). Run: gh auth login --hostname <host> (as <login>) or gh auth refresh -h <host> -u <login>. No token was injected.` Daemon resumes and background spawns keep failing closed with the nobody-token instead (#9750).
