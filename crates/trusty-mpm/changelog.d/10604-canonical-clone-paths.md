Fixed
- The managed clone path is canonical for any owner/repo case: `base_clone_path` slugifies both segments, so `BobMatNYC/Trusty_Tools`, `bobmatnyc/trusty-tools.git` and `bobmatnyc/trusty-tools` name one directory under the projects root.
- A project registered with a `~` path (a flat or hand-cloned checkout, or a `config.yaml` `projects:` entry) now keys by its checkout's origin, the same `owner/repo` key its GitHub URL gives, and resolves to that checkout. It used to be parsed as a URL with host `~`, which gave a key such as `code/trusty-tools` and a clone path nested inside the projects root. The project views also fold a `~` registration with the absolute path it names.
- Registering a `~` path when `$HOME` is relative, or when the checkout cannot be read, is refused with the cause instead of storing a `local:` key for it.
- A key already stored in `projects.json` is not changed. A `~` record keyed the old way still resolves to its checkout, and registering the same checkout by its GitHub URL now finds that record instead of adding a second one.
