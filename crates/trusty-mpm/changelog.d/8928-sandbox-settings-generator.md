Added
- `core::session_launch::write_sandbox_settings` generates the Claude Code sandbox policy for a PM, agent or Architect session (#8928 step 5). The project `.claude/settings.json` gets the `sandbox` block, exact-file `permissions.deny` entries and `env.RUSTC_WRAPPER = ""`, with `allowUnixSockets` naming `trusty-mpm.sock` and, for a PM, the workspace tmux socket, and no `allowLocalBinding`. The sccache socket is never allowed: the sccache server runs whatever compiler a client names, outside the sandbox. tm's user-level `settings.json` gets `sandbox.network.strictAllowlist` and a credentials deny list. The Architect gets `sandbox.enabled: false`. The merge goes key by key: tm's own values win, while the operator's `denyRead`, `denyWrite`, `permissions.deny` and `credentials.envVars` entries are kept alongside tm's. After writing, `verify_sandbox_settings` reads the files back and refuses the launch when the sandbox is off, `allowUnsandboxedCommands` is not `false`, `strictAllowlist` is missing, either tier sets a non-empty `excludedCommands`, `.claude/settings.local.json` sets a `sandbox` key, or a file cannot be read. No launch path calls it yet; that is step 6.
