Added
- Presence device core, with no CLI, daemon method or WebAuthn verifier yet (PR2b-1b adds them): enrolled devices are stored one sealed record per credential in `~/.trusty-mpm/architect-launch/devices/`, and enrol and revoke each need a 10-minute local-presence ticket sealed with the presence key. Revoke deletes the record first and then every grant that names the device; a grant whose removal failed is still refused, because the check re-reads the record (#8878).
- Pending presence requests in `~/.trusty-mpm/architect-launch/pending/`: sealed, expiring after `[presence] request_ttl_minutes` (default 5, clamped to 1-30), at most 16 live, one per `claude` PID per 2 minutes, consumed by an atomic rename so one request yields at most one grant. The caller's action text is always shown labelled "unverified origin" (#8878).
- A device approval becomes a grant only through one fixed check order: the presence key, a challenge the daemon holds in memory for that one request (a restart drops it), the request's seal and dates, the action hash, the requesting `claude`'s PID and start time, the sealed device record, the signature, user verification, a signature counter that moves forward (0 on 0 allowed for synced passkeys) and is saved before the grant. Every refusal writes no grant and leaves the request in place (#8878).
- Grants may name `device:<credential id>`. Whether such a grant lets a call through is one switch, `presence::DEVICE_GRANTS`, pending owner decision D67; it ships `Inert`, so every device grant is refused until the owner rules. The presence key's access list is still unverified (#10865) (#8878).
