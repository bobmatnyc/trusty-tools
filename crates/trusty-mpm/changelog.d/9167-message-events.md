Added
- The tm daemon records inter-session messages on the trusty-events bus as `message` events (#9167). A `SendMessage` call is one `sendmessage` event; a Bash call running `tmux send-keys` that types text is one `tmux` event per call, naming the `-t` target (a follow-up `Enter` adds nothing, and `send-keys` quoted inside another command does not count); a `Notification` that `tm hook` appended to the configured inbox is one `hook_push` event to that inbox. Each event names the sending session, the recipient, and any relay marker (`[<Name> Architect HH:MMZ]`), and is a child of the tool call or hook event that carried it. Only the `PreToolUse` of a call is counted.
- A `message` event carries no message text by default: only its byte count and sha256. Both describe the text after a credential scan: recognised token and key shapes (GitHub, Slack, AWS, LLM API keys, JWTs, PEM keys, credentialed URLs, `Bearer`/`Authorization` values) are masked, and so is the rest of a line whose text before `=` names a KEY, TOKEN, PASS, SECRET or CREDENTIAL. A credential in any other shape is not recognised. Because the digest is over the scrubbed text, it can differ from the digest of the text the recipient saw. The relay marker counts only when it starts the message's first line. The bug-report scrubber's credential rules now also mask fine-grained GitHub tokens (`github_pat_`), Slack refresh and app tokens (`xoxe-`, `xapp-`) and AWS STS keys (`ASIA`). Setting `TRUSTY_MPM_EVENTS_MESSAGE_BODY=1` in the daemon's environment adds the scanned text as `body`, cut to 4096 bytes.
- These events use the same buffer, flush and failure handling as the hook action events: a down or stalled bus never blocks or fails a hook.
