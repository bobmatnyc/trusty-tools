Fixed
- `tm pr merge` refuses while an unresolved code-critic BLOCK holds the PR: a BLOCK pinned to the head with no later APPROVE or WARN on the head, a BLOCK that names no commit with no later APPROVE or WARN on the head, or a BLOCK on an earlier commit with no later APPROVE or WARN on any commit. A push does not resolve a BLOCK. The refusal names the review or comment and the sha. Only verdicts by an OWNER, MEMBER or COLLABORATOR count; a BLOCK whose author role is not reported still holds. A verdict is a line starting `Verdict: <APPROVE|WARN|BLOCK>` outside a closed code fence. APPROVE and WARN take optional leading `#` marks and `**` bold; a BLOCK is read in any case and decoration, such as `- **Verdict:** Block` or ``Verdict: `BLOCK` ``. A BLOCK after a code fence that never closes still counts. A review is pinned to the commit it was submitted on, and `, pinned to <sha>` on the line overrides that. An APPROVE or WARN on an older head only warns that no verdict covers the head. If the comments and reviews cannot be read, or the head changed between the PR read and the verdict read, the merge is refused. The merge passes `--match-head-commit` with the head the verdicts were read against, so a push in between makes GitHub refuse it. A raw `gh pr merge` still bypasses this check.
