Fixed
- Worktree removal no longer deletes gitignored run output. `git worktree remove`, with or without `--force`, deleted gitignored files the dirt check never counted, so a zero-commit tree holding results in a gitignored directory read as clean and lost them. Every automatic removal route now checks first: the `SessionEnd` agent-worktree reap, session decommission (including `--force`), the merged-PR reclaim, the orphan `prune-worktrees` sweep, and `tm pr cleanup` with its supervisor sweep. A gitignored file keeps the tree unless it is harness bookkeeping (`.trusty-mpm/`, the ownership marker, `.claude/settings*.json`), build or tool output named by the directory git matched (`target/`, `node_modules/`, `dist/`, `src-tauri/gen/`, and similar), or inside a directory its tool tagged as a cache (`CACHEDIR.TAG`, cargo's `.rustc_info.json`). A `build/out.json` under a tracked `build/`, or a `target-analysis/` directory, is kept. The refusal names the path and the file count, and a check that fails keeps the tree. Only `prune-worktrees --discard-dirty` discards such output (#8534).
