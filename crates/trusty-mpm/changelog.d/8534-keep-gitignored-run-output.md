Fixed
- Worktree removal no longer deletes gitignored run output. `git worktree remove`, with or without `--force`, deleted gitignored files the dirt check never counted, so a zero-commit tree holding results in a gitignored directory read as clean and lost them. The `git worktree remove` routes now check first: the `SessionEnd` agent-worktree reap, session decommission (including `--force`), the merged-PR reclaim, the orphan `prune-worktrees` sweep, and `tm pr cleanup` with its supervisor sweep. A gitignored file keeps the tree unless it is harness bookkeeping (`.trusty-mpm/`, the ownership marker, `.claude/settings*.json`, the deploy ledgers), an agent or skill file tm's ledger records and nobody edited since, build or tool output named by the directory git matched (`target/`, `node_modules/`, `dist/`, `.vercel/`, `*.egg-info/`, `src-tauri/gen/`, and similar) or by a cache file name (`.eslintcache`, `*.tsbuildinfo`, `.coverage`), or inside a directory its tool tagged with `CACHEDIR.TAG`. A user's own skill or agent under `.claude/`, a `build/out.json` under a tracked `build/`, or a `target-analysis/` directory is kept. A name git quotes, one holding a `"` or a control character, is classified like any other instead of keeping the tree forever. The refusal names the path and the file count, and a check that fails keeps the tree. Only `prune-worktrees --discard-dirty` discards such output. Two `remove_dir_all` routes do not run the check yet: an SM-owned workspace's decommission and a directory no repository claims (#8663) (#8534).
