Fixed
- A project registry record that pins a `gh_account` with no `github.config_dir` no longer refuses every merged-PR lookup when a usable config dir exists (#8510, a regression from #8416). The daemon and the `tm hook --pm-guard` worktree-removal check try the static config's `github.config_dir` for that origin, then tm's own `gh-accounts/<login>` dir. A dir is borrowed only when its local `hosts.yml` names the pinned account as the active `user:` for the repository's host, and `gh auth token --hostname <host>` and `gh auth token --hostname <host> -u <login>` both succeed with the same token. That proof is local, and no token is ever logged. The repository owner never selects the account. When no dir passes, the refusal still fails closed. It names each candidate's failure and the fix command `tm projects register <name> --repo-url <url> --gh-account <login> --gh-config-dir <dir>`.
- A registry record whose `gh_account` and `github.account` name different logins now refuses by name instead of silently using `gh_account` (#8510).
- A session spawned for a project pinned to an account with no `github.config_dir` now runs inside a proven config dir. Failing that, it gets the `gh auth token --hostname <host> -u <login>` token from the daemon's own gh config, used only when proven to be the login's own: the login is the active `user:` for that host, or the `-u` token differs from the active account's token. When `gh` ignores `-u` and returns the active account's token (#5851), or `-u` fails, the session's `gh` gets a token that authenticates as nobody and a warning naming the fix. It no longer runs as the machine's globally active account (#8510).
- Daemon `gh` calls no longer inherit `GH_HOST` from the environment (#8510).
