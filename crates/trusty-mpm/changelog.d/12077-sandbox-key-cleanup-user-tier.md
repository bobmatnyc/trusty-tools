Fixed
- The one-time sandbox cleanup now also cleans tm's own user-tier file, `claude-config/settings.json` in tm's managed Claude config dir. It removes `sandbox.network.strictAllowlist: true`, a `sandbox.network.allowedDomains` list equal to the one tm wrote, and the eleven `sandbox.credentials.envVars` entries tm wrote with `mode: "deny"`, and nothing else. A different value at one of those keys and any `envVars` entry you added stay, and the launch logs them at warn level and lists them in `claude-config/tm-sandbox-cleanup.json`, which marks that file done. A symlinked file is skipped with a warning, and a failed cleanup is retried on the next launch (#12077).
- After the project cleanup has finished, a launch without `TM_CLAUDE_SANDBOX=1` deletes the workspace's `.trusty-mpm/sandbox-roles.json` record. A launch with the switch set keeps it. A launch also keeps a record that names a role it never shared the record with, so `tm fleet init` leaves a PM's record in its directory as it was, and it keeps a record it cannot read, with a warning (#12077).
- A settings file that holds no key tm wrote is never rewritten and stays byte-identical. A file the cleanup rewrites comes back with its keys in sorted order (#12077).
