Fixed

- `tm content update` and the first-use content fetch retry a GitHub 5xx up to 3 times, after 1 s, 2 s and 4 s (#9396).
- A 403 or 429 from GitHub names the rate limit, the `x-ratelimit-remaining`, `retry-after` and `x-ratelimit-reset` headers it sent, and how to authenticate: set `GITHUB_TOKEN` or `GH_TOKEN`, or run `gh auth login` (#9396).
- With neither `GITHUB_TOKEN` nor `GH_TOKEN` set, the content fetch takes its token from `gh auth token --hostname github.com`, with `GH_HOST` removed, so a token for a GitHub Enterprise host is never sent to api.github.com. A missing or failing `gh` leaves the fetch unauthenticated; it is never an error, and the token is never logged. A `gh` that times out or cannot be waited on is killed and reaped (#9396).
- A 401 to a token from `gh auth token`, which is revoked or expired, is retried once without the token, so a public content read still succeeds. A 401 to a `GITHUB_TOKEN` or `GH_TOKEN` token is an error that names the variable (#9396).
- Every network, missing-sidecar and no-content error names the manual install, with the release tag when it is known: `gh release download <tag> --repo bobmatnyc/trusty-tools`, then `tm content install --from <dir>/<tag>.tar.gz` (#9396).
- `tm doctor`, the doctor repairs, skill retirement, the savings row and the SM prompt never fetch the content release; only session composition, `tm install` and `tm reinstall` do. With no lock, the doctor `content` row warns with the same remedy as every not-installed error (#9396).
- A session launch reads its agent roster from the content it resolved for the project, not from tm's working directory, so one launch never mixes two content sources (#9396).
- After a failed first-use fetch, tm does not retry for 60 s from when the fetch failed, so repeated compositions do not each wait on a dead network; callers that waited behind the failing fetch get its failure instead of fetching again, and content installed in the meantime is served at once. The fetch no longer holds a tokio worker thread while it blocks (#9396).
- With no instructional content installed (`~/.trusty-mpm/content/content-lock.toml` missing) and no trusty-tools checkout in use, `tm` now fetches the content release `tm content update` would pick, verifies it and pins it once, before it composes a session's PM instructions or runs the `tm install` gate. A present lock never triggers a fetch, and two first uses racing leave one valid pin. Offline, or when the release fails verification, nothing is pinned or served and the error names `tm content update` and the offline `tm content install --from <bundle.tar.gz>`. Setting `TRUSTY_CONTENT_OFFLINE=1` turns the first-use fetch off; with no content installed, the error then names the switch, `tm content update` and `tm content install --from <bundle.tar.gz>`. `tm content update --help` documents the switch (#9396).
- Every "no content installed" message names `tm content update` first, with `tm content install --from <bundle.tar.gz>` as the offline alternative (#9396).
