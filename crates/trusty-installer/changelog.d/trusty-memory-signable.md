Fixed

- `trusty-memory` is now a signable target — `tctl sign trusty-memory` signs all three binaries `cargo install --path crates/trusty-memory` produces (`trusty-memory` → `com.trusty.trusty-memory`, `trusty-bm25-daemon` → `com.trusty.trusty-bm25-daemon`, `trusty-memory-mcp-bridge` → `com.trusty.trusty-memory-mcp-bridge`), so its macOS TCC grants survive a reinstall instead of being revoked by every fresh cdhash. Its absence from `SIGNABLE_BINARIES` was never a decision: `trusty-memory setup` and `trusty-memory migrate` walk `$HOME` to depth 8 for `.claude/settings*.json`, and that walk skips `Library`/`Applications` but not `~/Desktop`, `~/Documents`, or `~/Downloads` — the same cdhash-keyed TCC exposure that put `trusty-search` (#873), `tm` (#2721), and `tagent` (#4277) in the table. New `scripts/install-trusty-memory-signed.sh` / `make install-memory-signed` cover the local-source install path.
  - Hardened Runtime follows `trusty-search`'s conservative split (explicit `tctl sign` only, not the automatic hook): `trusty-memory` links `ort`/`fastembed` through `trusty-common`'s `memory-core`, so it carries the same unverified ONNX-dylib-under-library-validation exposure.
  - The `tctl sign` targets named in `signing_persistence_tip` had gone stale after [#4277](https://github.com/bobmatnyc/trusty-tools/issues/4277) (`trusty-agents` was missing); the list is now checked against `SIGNABLE_BINARIES` by a test, along with the `SignTargetArg` clap variants, so a set can no longer be added to the table and left unreachable from the CLI.
