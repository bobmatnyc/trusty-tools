Changed
- Inbound dispatch is one selector shared by every channel provider: an assistant's own channel, a global channel naming it in `route_to`, or its legacy absorbed `[[listeners]]` binding — exactly one of the three wakes it per event, so a backfilled `route_to` and the binding it came from never both fire (#7609).
- A global `[[channels]]` entry now fans out to the assistants it names in `route_to`, for Slack and Telegram as well as Gmail; the two-stage opt-in is no longer the required path. The fan-out follows only messages the global's own `target` addresses, and only while the global is enabled and receive-enabled, so a send-only or channel-scoped global no longer wakes every name it routes to.
- Disabling or narrowing an assistant's channel in the UI now actually suppresses its wake: a channel that addresses an event claims it whether or not it also wakes, so the event no longer falls through to the `[[listeners]]` wake and its still-enabled `agent.toml` binding.
- A per-assistant binding that overlays an account-wide global channel is stored in the assistant's channels file instead of being left behind in `agent.toml`, and the startup sweep backfills `route_to` for every such pair. An overlay resolves against the global's `id`, so renaming a global no longer makes the assistant's whole channels file unreadable; an overlay whose global has gone is dropped with a warning rather than failing the file.
- The Gmail channel wake carries the assistant's `events/<connector>.md` instructions, which previously reached only the `[[listeners]]` wake path.
- A `route_to` naming an unknown assistant, an unreadable assistant roster, an unreadable assistant manifest, a `route_to` that is not an array, an unresolvable global config path, and a channel whose provider has no adapter are each logged and claim nothing, instead of being absorbed into a silent no-op.
