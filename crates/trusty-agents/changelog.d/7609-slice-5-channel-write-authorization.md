Breaking
- Channel writes over HTTP now require a bearer credential, even from loopback: `PUT /api/channels`, `PUT /api/agents/{name}/channels` and the deprecated `PUT /api/agents/{name}/listeners` alias all answer 401 without one.
- The `channel` tool's write actions and the turn-originated channel and listener settings patches take the same gate, against the credential the PROCESS resolved at startup. A daemon or REPL that resolved one is unaffected; a process that resolved none — notably `tagent mcp-serve`, which dispatches before startup resolution — refuses those writes. Its reads are unaffected.
- Two credentials are accepted and only one of them ever leaves the process. The operator's own API credential (`--api-token`, or `TAGENT_API_TOKEN`) is accepted on a channel write, is never returned by any route, and is never written to disk. A loopback-bound daemon additionally MINTS a per-boot credential that authorizes channel writes and nothing else; that is the one `GET /api/config` returns, to a same-origin caller only. A non-loopback bind mints nothing and therefore discloses nothing.
- On a daemon that has an operator credential, the bearer middleware still requires it on every `/api/*` request, so the minted value is what a daemon WITHOUT one hands its UI.
- The served Channels and Listeners tabs read the minted credential from `/api/config` and present it on their PUT, so they keep working on the default daemon.
- Reads are unaffected and the same-origin write guard is unchanged. Every accepted write emits one `channel-write` audit line naming route, scope, assistant, the stored count either side, and the caller's address.
