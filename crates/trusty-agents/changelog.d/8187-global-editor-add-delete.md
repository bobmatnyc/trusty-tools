Added
- The Channels view's Global scope can now add and delete a host-wide channel, not only edit one. **Add channel** asks for an ID, a name, a service picked from the providers this daemon actually serves, and the assistants to route to, taken from the dispatch roster `GET /api/channels` publishes rather than the assistant catalog — so a route to `pm`, `ctrl` or a hidden assistant is offered, and a provider this build does not carry is not. A new channel is created switched off, with no destination, so nothing polls or sends until it is enabled and saved.
- **Delete** on a global channel asks first. A channel that per-assistant bindings still overlay is refused by the daemon, and the confirmation then names those assistants and says what forcing costs: the bindings stay on each assistant but address nothing, send nothing and receive nothing until they are removed there. Forcing is a second, explicit click; the first one never forces.
- Adding and deleting go through `POST /api/channels` and `DELETE /api/channels/{id}` under the same compare-and-swap the Save above takes, so either one losing the revision race reloads the list and says another writer changed it instead of republishing a stale one. A duplicate ID is reported inline against the form with the draft kept, whether this page or the daemon catches it.
- Neither action is offered while a field edit is unsaved: both publish the stored list, which would discard that edit without saying so.
- Deleting a channel says only what it can know about when receiving stops. The route removes the declaration, but a receiver already polling keeps polling until the daemon restarts, and only the daemon knows whether one was — so the confirmation neither calls the change immediate nor promises a surviving receiver, and says instead that the result will report it. The success notice then says the receiver runs until a restart stops it exactly when `DELETE /api/channels/{id}` answered `receiving_until_restart: true`.
