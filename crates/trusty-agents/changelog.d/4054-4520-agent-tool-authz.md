Security

- Closed two persona tool-authorization escalation paths (owner rulings 2026-08-31). A user-authored assistant persona's `[tools].allow = ["*"]` no longer reaches the unsandboxed L0 shell `l0_shell_exec`; the L0 execution grant is reachable only when named literally ([#4520](https://github.com/bobmatnyc/trusty-tools/issues/4520)). The exfiltration-capable Google tools now require explicit human confirmation before executing on the persona-chat path and fail closed (deny) where no confirmation channel exists ([#4054](https://github.com/bobmatnyc/trusty-tools/issues/4054)). Read-only tools and non-wildcard grants are unaffected.
- Extended the exfil-capable set from five to seven (owner ruling 2026-08-31): `manage_events` (emails a calendar invite to an arbitrary attendee) and `manage_drive_file` (moves/copies/trashes a Drive file) now gate the same way as `compose_email` and `modify_gmail_messages` ([#4054](https://github.com/bobmatnyc/trusty-tools/issues/4054)).
- Repointed the `/subagents`, `/knowledge`, and `/skills` advisory panes at the real persona-chat gate (`persona_surface_grants_tool`) so a `*` allow no longer DISPLAYS the L0 shell or an exfil tool as available while the dispatch gate denies it ([#4520](https://github.com/bobmatnyc/trusty-tools/issues/4520), [#4054](https://github.com/bobmatnyc/trusty-tools/issues/4054)). A visible consequence on `/skills`: the `google-workspace` bundle now reports `granted_state: "some"` rather than `"all"`, because `gmail-compose` and `gmail-labels-apply` wrap gated tools.
