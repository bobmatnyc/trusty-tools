Fixed

- `tagent --api` now runs the Telegram long-poll gateway in-process, so a channel-bound Telegram chat can reach an assistant on the API host. The `--api`/`--serve` branch previously returned straight into the HTTP server and started the gateway nowhere, which left Telegram receive dead on the production host (`tagent --api --port 8765`) even with a configured bot token and an enabled binding ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- Each assistant now has its OWN Telegram bot. A telegram binding carries its bot token through the binding's `credential_ref`, exactly as a Slack binding carries its workspace token, and the API host runs one long-poll gateway per distinct bound token. Two assistants with two tokens get two pollers; two bindings sharing one token get one poller that dispatches by binding; a binding whose token will not resolve is skipped with its reason recorded. An inbound message on one assistant's bot can no longer wake an assistant bound only to another's, and the gateway lock and the pairing state are per bot — a chat paired to one assistant's bot is not paired on another's. Existing pairings under the old shared `telegram-paired.json` are not migrated; re-pair once per bot. No bot token, and no digest of one, appears in any log line or in `tagent system status` ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- The gateway no longer stands down permanently when another process holds a bot's lock at startup, so an app relaunch racing the previous process's exit no longer leaves Telegram dead until someone restarts it. The supervisor re-scans every 60 seconds: it waits out a live lock holder, picks up a binding enabled after startup, stops a poller whose binding went away, and resets the restart backoff after a healthy run instead of resuming at the five-minute ceiling ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- The gateway's single-instance lock is now an advisory `flock` held by an open descriptor rather than a PID file compared with `kill(pid, 0)`. Two hosts can no longer both acquire it, a loser can no longer unlink the winner's file, a reused PID no longer reads as a live holder forever, and a crashed poller's lock is released by the kernel rather than left behind ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- `tagent system status` and the `system_status` tool now report the Telegram gateway: one row per bound bot with its state and reason, the scan's own warnings, and the PIDs holding a gateway lock on this machine. Every gateway degradation used to be a `tracing` line only, which is invisible on a host that captures no stderr ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- Removing or disabling one assistant's Telegram binding on a bot another assistant also binds now takes effect within a rescan. The rescan reconciled the set of bot tokens only, so a poller already running kept the owner list it was spawned with and went on dispatching to the revoked assistant until the host was restarted ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- A per-assistant Telegram bot no longer lets a chat drive an assistant that owns no binding on it. `/switch` to a name outside the bot's owners is refused, and every other update no binding claims — plain text and slash commands alike, including a REPL command such as `/cost` or free text behind an unknown slash — is dropped rather than falling through to the gateway's own chat session, which would have run it as `ctrl`. A supervised bot has no REPL to issue pairing codes and needs no session of its own. The host-wide `--telegram` and REPL gateways keep their previous behaviour ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- A healthy Telegram poller no longer reports `starting` forever in `tagent system status`. Each rescan republished the placeholder row while the poller records `polling` only when its state changes, so the status surface contradicted a gateway that was working ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- An inbound channel event is no longer claimed by an assistant the caller may not dispatch to. A binding owned by a non-owner assistant used to claim the event and suppress the caller's own fallback, so a Telegram update on another assistant's bot was dropped with no dispatch and no log ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
- The Telegram gateway now says once, at info level, when a bot has no pairing file yet while the pre-per-bot shared `telegram-paired.json` is still present, so "every chat is suddenly unpaired" is distinguishable from a lost state file ([#8190](https://github.com/bobmatnyc/trusty-tools/issues/8190))
