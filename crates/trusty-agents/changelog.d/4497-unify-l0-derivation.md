Changed

- **`pm` and every assistant now reach tier L0 by ONE mechanism.** `AgentTier::for_kind` — the role-derived rule that already made an assistant-kind agent `L0Orchestration` — now recognises the ORCHESTRATOR kind (`role = "orchestrator"` / `"controller"`, i.e. `pm` and a `ctrl` declaring the controller spelling) as well, via the new `agents::delegation::is_orchestrator_kind` predicate sitting beside `is_assistant_kind`. The hardcoded `AgentTier::L0Orchestration` literal in `ctrl::pm_task::dispatch::history::ctrl_delegate_posture` is replaced by a thin delegation to that rule. Previously the two populations reached the same tier by two different mechanisms, so `AgentInfo::tier()` reported `l1` for `pm` while the dispatch path treated it as L0 — and a new call site asking "is this agent L0?" picked up whichever answer it happened to reach. The two kinds stay disjoint: an orchestrator gains the tier only, never the assistant-only peer prohibition (`kind_refuses_delegation`) and never the assistant-only role allowlist (`ASSISTANT_ALLOWED_DELEGATE_ROLES`, which still excludes it as a delegation target)
  - No agent gains a capability. `pm` is the only bundled agent whose resolved tier changes (`l1` → `l0`), and every L0-gated surface — `l0_shell_exec` (#4173), the `gh_*` tools (#4170), the read-only session-state tools (#4171), cross-project git scoping (#4222) — is registered only behind a persona's own `[tools].allow`, which `pm.toml` does not declare. The new `bundled_agent_tier_table_is_pinned` test pins the whole roster's `name`/`role`/`tier` table through the real `AgentConfig::by_name` loader, and `bundled_assistant_personas_resolve_l0_and_gain_nothing` now asserts that zero-delta claim for the orchestrator kind too
  - The replaced branch was a fallthrough (`role != "assistant"`), not a decision, so it handed L0 to ANY non-assistant role. For every config `resolve_agent_config` can actually return — `pm.toml` (`orchestrator`), `ctrl.toml` (`assistant`), `ctrl_default()` (`controller`) — the derived rule returns the identical answer. It differs only for a hand-edited config carrying a specialist role, where it now fails CLOSED to `L1Standard` instead of granting L0 by omission (`ctrl_delegate_posture_specialist_role_is_not_silently_l0`) (closes [#4497](https://github.com/bobmatnyc/trusty-tools/issues/4497))
