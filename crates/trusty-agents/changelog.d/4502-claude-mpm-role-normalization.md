Changed

- **claude-mpm agents now carry a real role instead of a hardcoded `"agent"` — behind a fail-closed normalization layer.** `agents::claude_mpm_loader` never extracted any role field and hardcoded `role: "agent"` in `to_agent_config`, discarding each agent's actual domain at load time. It now reads `role:` (trusty-mpm's source-asset and hand-authored spelling) with a fallback to `agent_type:` (the key trusty-mpm's composer actually emits into the deployed `.claude/agents/*.md` artifacts this loader reads — it does not emit `role:` at all), and translates the result through the new `agents::claude_mpm_role::normalize_role`
  - The declared value is NEVER passed through verbatim. `role` selects the tool-registry branch in `build_registry_for_agent` and is checked against `ASSISTANT_ALLOWED_DELEGATE_ROLES` at every delegation, so it is resolved through an explicit reviewed table — not a suffix or prefix rule, which would be a default-allow in disguise (any future `<anything>-engineer` admitted sight unseen)
  - FAIL-CLOSED: an absent, blank, or unrecognized domain yields `UNMAPPED_ROLE` (`"agent"`), the same literal the loader hardcoded before, which is not a member of `ASSISTANT_ALLOWED_DELEGATE_ROLES`. A declared-but-unmappable `role` does NOT fall through to `agent_type` — a fallback that searched keys until one was eligible would be a widening, not a fallback
  - Mapped: `engineer`, `qa`, `ops`, `documentation`, `ticketing` (identity), plus `research` → `researcher` and `data-engineer` → `engineer`. Deliberately NOT mapped, and therefore still ineligible: `security`, `version-control`, `code-analyzer`, `memory-manager`, `mpm-agent-manager`, `mpm-skills-manager` (real specialists with no coarse counterpart — inventing one is an owner decision, not a translation); `base`, `base-engineer`, `base-ops`, `base-qa`, `base-research` (composition fragments that are appended into other agents, never dispatched); and `universal` / `system` / `trusty-mpm` / the literal `engineer|qa|ops|universal|documentation` template placeholder (not domains at all)
  - `agents::mpm_bridge` (added by [#4498](https://github.com/bobmatnyc/trusty-tools/pull/4498), currently dormant — declared but not yet wired into agent resolution) projected `role` verbatim onto `AgentInfo.role`. It now goes through the same `normalize_role`, so the pass-through cannot go live when that tier is wired in. `AgentMetadata` carries no `agent_type`, so every deployed artifact resolves to the sentinel there today — byte-identical to the literal it replaced
  - NO capability change. Role eligibility is only a coarse pre-filter: a delegation must additionally clear the per-agent `[subagents].delegate_allowed` whitelist and the server-owned `ASSISTANT_REACHABLE_SUBAGENTS` name floor, both deny-by-default and neither touched here. That floor admits exactly `research-agent` and `ticketing-agent`, both of which resolve to bundled TOMLs ahead of the claude-mpm fallback tier, so no bundled assistant gains a reachable target (closes [#4502](https://github.com/bobmatnyc/trusty-tools/issues/4502))
