Fixed
- `search.project.resolve` now sees incremental updates: a committed `index-file` write (including a tombstone that removes rows, or a refused excluded path whose old chunks it purges), a `remove-file` delete (HTTP, socket or MCP), a watcher write or delete (including an edit whose new content lands no chunks), a watcher rescan batch or sweep, and a boot-reconcile file update or delete each stamp the corpus's `reindexed_unix`, as a full reindex already did. A refused, failed or no-op write does not stamp, nor does a write whose redb step failed and was only logged; a failed stamp write is logged and keeps the previous stamp (#9230).
- A delete whose redb step fails is now an error, with the file's chunks left in place, instead of a logged warning that dropped them from memory only. `remove-file` answers `500 remove_file_failed` (socket: internal error) and an excluded pushed `index-file` answers `500 index_file_failed`. Boot reconcile counts the file as failed, the rescan counts it in `files_failed` and retries the pass, and the watcher keeps tracking the file so its next event retries (#9230).
- A full-reindex batch whose redb corpus write failed is now reported as a failed batch, and its files' content hashes are withheld so the next reindex retries them; it used to count as indexed (#9230).
