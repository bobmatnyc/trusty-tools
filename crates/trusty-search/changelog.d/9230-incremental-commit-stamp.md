Fixed
- `search.project.resolve` now sees incremental updates: a committed `index-file` write (including a tombstone that removes rows, or a refused excluded path whose old chunks it purges), a `remove-file` delete (HTTP, socket or MCP), a watcher write or delete, a watcher rescan batch or sweep, and a boot-reconcile file update or delete each stamp the corpus's `reindexed_unix`, as a full reindex already did. A refused, failed or no-op write does not stamp, nor does a write or delete whose redb step failed and was only logged; a failed stamp write is logged and keeps the previous stamp (#9230).
- A full-reindex batch whose redb corpus write failed is now reported as a failed batch, and its files' content hashes are withheld so the next reindex retries them; it used to count as indexed (#9230).
