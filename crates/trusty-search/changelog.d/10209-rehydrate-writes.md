Fixed
- A write issued while an index rehydrates its evicted corpus is no longer lost. `remove-file` during a long rehydrate read the empty in-memory map, deleted nothing and answered `removed_chunks: 0`; it now reads the file's chunk ids from redb and fails visibly if that read fails. An update to an existing chunk, or a delete, that landed between the rehydrate's redb read and its publish was overwritten by the older scanned text; writes now wait for an in-flight rehydrate to publish, then apply. Queries still do not wait for a rehydrate. `search.index.files.remove` can answer `remove_files_busy` while a single-file write is committing, not only during a rehydrate (#10209).
