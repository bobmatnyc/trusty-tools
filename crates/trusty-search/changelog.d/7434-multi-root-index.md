Added
- An index can cover more than one root directory (#7434). `POST /indexes` (and `search.index.create`) takes an optional `roots` list of additional absolute directories; `POST /indexes/:id/roots` (socket `search.index.roots.add`, MCP tool `add_root`) appends roots to a live index, persists them in `indexes.toml`, starts their file watches and queues a background reindex. Each root passes the same gates as `root_path` (denylist, allowlist, the #2336 exact-collision and #4289 overlap guards against every root of every other index), and a root that nests with one of the index's own roots is refused `409 index_root_overlap`. An add is refused `409 reindex_already_running` while a reindex runs, and `roots` on an already-registered id that names a root the index does not hold answers `409 roots_not_applied` instead of being dropped. `GET /indexes/:id/status` reports the full `roots` list (primary first), `missing_index_roots` (additional roots absent at the last walk) and `watcher.roots`, each root's own watch state (`watching` / `degraded` / `failed`). Files under an additional root are stored as `@root<n>/<path>`; the reindex walk, prune, search post-filter, grep, `remove-file` (absolute paths map to the `@root<n>/` key and its hash), project resolution, the per-root file watchers and the dropped-event rescan all honour every root. A pushed `index-file` path of the form `@root<n>/…` is admitted at its own root, so the additional root's ignore rules apply. The reindex prune and the dropped-event rescan both keep the chunks of an additional root that is absent at walk time instead of deleting them. A rescan from a watch spawned before a root was added keys files through the live root table. If `indexes.toml` cannot be read, an add answers `500 roots_not_persisted` and changes nothing. Single-root indexes are unchanged.
