Fixed

- `POST /indexes` and `search.index.create` now honour `colocated: false`. The index keeps its store in the data dir even when `<root>/.trusty-search/` already holds a corpus, and registration writes nothing under the root. A read-only or root-owned root that holds such a corpus now registers, where it answered `500 corpus open failed`. An omitted `colocated` or `true` keeps the #8499 placement unchanged ([#8147](https://github.com/bobmatnyc/trusty-tools/issues/8147))
- Registering a root whose `.trusty-search/` corpus the daemon cannot write now answers `403 permission denied: …`, naming the directory and the `colocated: false` alternative, instead of `500 corpus open failed`. Nothing is registered or created ([#8147](https://github.com/bobmatnyc/trusty-tools/issues/8147))
- `colocated: false` for an id already registered colocated at the same root answers `409` with `registered_colocated` and `requested_colocated`, and changes nothing, even while the embedder is still loading. Before, the field was ignored and the request answered `200`. If `indexes.toml` cannot be read, the request answers `500` and registers nothing ([#8147](https://github.com/bobmatnyc/trusty-tools/issues/8147))
- A reindex after a root move now keeps or clears the file-hash cache by the index's registered layout, not by whether `<root>/.trusty-search/` exists, so a `colocated: false` index over such a root re-relativizes its keys ([#8147](https://github.com/bobmatnyc/trusty-tools/issues/8147))
