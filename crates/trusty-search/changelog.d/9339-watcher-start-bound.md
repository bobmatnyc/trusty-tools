Fixed
- Starting a file watcher no longer waits on fseventsd indefinitely. The start runs on its own thread, and the caller waits at most 5 s for it. A start that outlasts the limit logs one warning naming the root, returns an error, and the index keeps serving without a watcher: `GET /indexes/:id/status` reports `watcher.active: false`. When the late start finally returns, its watcher is shut down on that thread. While a root's start is still stuck, a new start for that root fails at once, so each root leaks at most one thread. Before, a silent `FSEventStreamStart` held the caller forever; a lib test stalled at 0 CPU this way (#9339).
