Fixed
- Starting a file watcher no longer waits on fseventsd indefinitely. The start runs on its own thread, and the caller waits at most 5 s for it on tokio's blocking pool, so no runtime worker waits with it. A start that outlasts the limit logs one warning naming the root, returns an error, and the index keeps serving without a watcher: `GET /indexes/:id/status` reports `watcher.active: false`. When the late start finally returns, its watcher is shut down on that thread. A root is marked in flight from the moment its start thread is spawned until that thread ends, and any other start for the root fails at once without spawning, so a root never has more than one start thread. Before, a silent `FSEventStreamStart` held the caller forever; a lib test stalled at 0 CPU this way (#9339).
