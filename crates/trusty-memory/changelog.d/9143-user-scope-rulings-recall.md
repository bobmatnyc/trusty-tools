Added
- `TRUSTY_MEMORY_RULINGS_PALACES` (optional, comma-separated palace ids, e.g. `<palace>,<palace>`) names user-scope palaces whose ruling-tagged drawers (`bob-ruling`, `owner-ruling`, `ruling`, `bob-decision`, `decision`, `standing-rule`, exact match) join `memory_recall` and `memory_recall_deep` at layer 1. Only those two MCP tools, on their ready path, get this leg; the warming path, `memory_recall_all`, the `MemoryService` methods and the chat surfaces do not. The leg runs only for an unscoped recall (no `room` or `wing`) and never in multi-tenant mode. The daemon reads the variable at startup; an `AppState` built any other way has no leg. Each palace is searched on the blocking pool, with the same BM25 fusion as the project hits, under a 500 ms bound: a third of the prompt hook's 1.5 s budget, so a stalled rulings palace never times the hook out. A failed palace is skipped for 60 s. Overlapping recalls each search a palace. A search that outlives the bound keeps running; while it runs, later recalls report that palace as `in_flight` and start no new search, and its own outcome, success or failure, is what the next recall sees. Rulings are de-duplicated by drawer id and content hash and contribute at most `ceil(top_k / 3)` hits. A palace that is absent, unreadable, failing or slow is reported in a `rulings_degraded` list of `{palace, reason, cached}` in the recall response, where `reason` is a fixed code (`absent`, `unreadable`, `search_failed`, `task_failed`, `timed_out` or `in_flight`) and `cached` is `true` when a recent failure was repeated without trying the palace; the error detail goes to the log only, and the project hits are still returned; the field is absent when nothing failed. Unset or blank, the variable changes nothing: no extra palace is opened and the response has no new field (Refs [#9143](https://github.com/bobmatnyc/trusty-tools/issues/9143))
