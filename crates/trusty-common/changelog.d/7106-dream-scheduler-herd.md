Fixed

- Dream cycles now queue behind a process-wide concurrency bound instead of running one per resident palace at once (#7106). Every path that runs a cycle — the idle loops and the on-demand `palace_dream` / `dream_consolidate_room` tools — acquires a permit from one shared semaphore sized by `TRUSTY_DREAM_MAX_CONCURRENT` (default 2), released on drop so no error or early-return arm can leak one. The transient this bounds was measured at 43 GB on a 61-palace host, because the peak is one cycle's working set times however many cycles run together, and #7115 bounded only the steady state.
- `Dreamer::start_with_shutdown` takes a first-tick stagger, so a cold start spreads the first cycle across the idle window rather than firing every palace in the same second (#7106). Palace k of n waits `idle_secs * k / n` past its first interval and the plain interval thereafter, which keeps the phase offset for the process's life. Deterministic, so a restart reproduces the same schedule.
- The dedup pass embeds in bounded 256-drawer chunks and checks the cycle's `max_cycle_ms` budget between them (#7106). It used to hand a palace's entire corpus to one `embed_batch` call — about six live copies of the corpus at peak, counting the embedder's own — with the budget checked only after that call returned, so a cycle could overrun its budget by minutes in one unbreakable step.
- A dream cycle now clones the drawer table once instead of four times (#7106). The content-prune and prune passes collect victim ids under the read lock, and the closet refresh builds its index straight from the read guard; only the dedup pass, which needs the rows across an await, still snapshots. No lock is held across an await.
- `dream_cycles_in_flight` and `dream_cycles_peak_in_flight` report how many cycles are running and the high-water mark, so a memory spike can be attributed to the dreamer (#7106).
