Fixed

- Registering a trusty-search index no longer reports the index as unregistered when the daemon answers the create after the client's one-second budget. The daemon reloads a cold-parked index inside its `search.index.create` handler — 3.8 s for a 32,754-chunk index — so the registration lands after the client has stopped waiting, and the client was reading that silence as a refusal: it withheld the id, left the session unpinned against an index that existed, then fired a reindex the daemon answered with `unknown index`. `search_index` now tells a create the daemon never ANSWERED (a timeout, a hang-up, or a read that failed part-way) apart from one it REFUSED, and settles the first by re-reading `search.indexes.list` until an index whose `root_path` is this tree appears. An answered create still costs at most the same one second; only an unanswered one pays the confirm poll, whose own deadline is four seconds. A launch that exhausts that deadline still withholds the id, so a genuinely absent index is withheld exactly as before, and confirmation comes only from a registry entry at this root, so no daemon error can produce a confirmed index. The reindex trigger now runs only after a confirmed registration, which removes the misleading `unknown index` warning that followed every failed create (#7237)
