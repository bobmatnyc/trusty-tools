Fixed

- Palace-scoped redb databases now open with an explicit 64 MB page-cache ceiling instead of redb's 1 GiB default (#7106). Three redb files per palace against the default 64 resident palaces left a 192 GiB theoretical ceiling that nothing bounded, and the allocator grew into it — the trusty-memory daemon reached 11–23 GB of heap (35 GB peak recorded) from a 233 MB start. The new `redb_cache` module is the single tuning point every memory-core open routes through, overridable with `TRUSTY_MEMORY_REDB_CACHE_MB`; an unparsable value keeps the bounded default and logs a warning naming it, never falling back to redb's 1 GiB. A `redb_cache_bounds` ratchet test fails if any palace-scoped open goes back to a bare `Database::create` / `ReadOnlyDatabase::open`.
- `KnowledgeGraph::community_count` memoises its Louvain partition per adjacency write generation (#7106). The palace roster asks every resident palace for this on every poll and `kg_graph` asks again on every call; each ask previously re-partitioned the whole graph, so a 94-palace roster ran 94 full partitions per poll with no write to justify one of them. A KG write bumps the generation and forces exactly one recomputation. `KnowledgeGraph::community_computations` reports how many partitions a handle has actually run.
- `PalaceRegistry::release_if_unreferenced` drops one cached palace handle when the cache holds the sole reference, so a startup sweep can hand back what it brought in without racing an in-flight recall or dream cycle (#7106). `remove` is unconditional and `evict_idle` is estate-wide and keyed on an idle clock the sweep's own open just reset, so neither could serve this.
